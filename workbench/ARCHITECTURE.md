# Workbench prototype: architecture and module contract

This is the contract the prototype's modules are built against. Code must match it. Where code and this document disagree, fix one of them; do not leave both.

## What it is

One local program, the **engine**, that launches coding agents, watches them, and shows a person what each one is doing, in plain language.

- `node bin/workbench.mjs --demo` runs with **simulated** agents and machines. Nothing is spent.
- `node bin/workbench.mjs --repo <git repo>` runs **real** agents: Claude Code, and Codex if installed. Each agent works in its own git worktree of that repo, on its own `workbench/<slug>-<id>` branch. Only "Your laptop" appears as a machine; cloud machines exist only in demo mode. `--clone <address>` copies a repository first, then runs as `--repo` on the copy.
- With no agent program ready, live mode starts anyway: the page's **Agents & keys** panel helps install Claude Code and Codex or sign in to them, gives agents the person's keys (kept in the login keychain on a Mac), sets git's name and email, and connects GitHub (see "Connect").

Workbench also does git for the person: they can read an agent's diff, merge its work into their own branch (the work becomes a commit on the agent's branch, joined into theirs by a merge commit), or throw it away (a hidden copy stays in git). The page's git screen shows the commit graph. See "Source control".

The browser UI is served by the engine on `127.0.0.1` and talks to it over HTTP plus Server-Sent Events.

## Rules for all code

- Node 22 or later, ES modules (`.mjs`), **no third-party packages**: only `node:` built-ins.
- Files in `src/shared/` must not import `node:` modules; the browser loads them as-is.
- Tests use `node:test` and `node:assert/strict`, live in `test/<module>.test.mjs`, run with `npm test`, need no network, and never start a real `claude` or `codex`. Use the fixtures in `test/fixtures/` and the fake-binary overrides below. No test depends on the machine's git identity: tests set `GIT_AUTHOR_*` and `GIT_COMMITTER_*`, or pass `-c user.name=… -c user.email=…`, and use temporary folders and a temporary HOME.
- Tests never reach the person's keychain or accounts. Key tests use `test/helpers/security-fake.mjs` and `test/helpers/secret-tool-fake.mjs`, never `/usr/bin/security` or a real keyring. A test that makes git keep, read or forget a sign-in sets `GIT_CONFIG_NOSYSTEM=1` and a `GIT_CONFIG_GLOBAL` of its own: on a Mac, git's system config hands sign-ins to the login keychain. A test never reaches GitHub: it passes Connect a `fetchJson` of its own, or, running the CLI's GitHub helpers as programs, gives them nothing that would be sent (no token, a refused one, no connection). A test never adds a key through the CLI, whose key store uses `/usr/bin/security` (with no keys, it starts nothing). A key-shaped value in a test is built from parts at run time, so no fixture looks like a real key.
- A key's secret value (an API key, a token) never goes into a log line, an argv, an address, a server answer, the event log or the history. What agents and checks print is masked before anyone sees it (see "Keys" and "Keys, masking and the default agent").
- Every child process is spawned with an argument array (`execFile`/`spawn`, never a shell string), with two exceptions. The first is declared checks, which are shell commands the repo owner wrote in `workbench.json`. The second is the agent installers in `src/core/connect.mjs`: two fixed lines Workbench itself carries, `curl -fsSL https://claude.ai/install.sh | bash` and `curl -fsSL https://chatgpt.com/codex/install.sh | sh`, which Terminal runs as `/bin/sh -c <line>` when the person presses Install (see "Terminal"). They are never built from anything a person or an agent typed. Every git call the program makes goes through `git()` in `src/core/workspace.mjs`, or through `gitStream()`, its streaming variant for clones in the same file. Both add `-c core.fsmonitor=false`, scrub the git environment and set a time limit (tests and `scripts/` may run git themselves).
- Plain language in anything a person sees: sentences built from facts (paths, branch names, counts), not identifiers, and never git's own error text (git's words go only in an error's `.detail`, for the log: see "Workspaces and receipt"). Use `src/shared/narrate.mjs`.

## Events (adapters to store)

Adapters and the engine emit **normalized events**, defined in `src/shared/events.mjs` (`EV`). Every event is `{ kind, ts, agentId?, ...fields }`. `ts` is milliseconds since the epoch. With Connect (live mode), every text field of an event reaches the store with the person's stored keys hidden (see "Keys, masking and the default agent").

The store reduces events into **AgentViews** (`newAgentView` in `events.mjs` lists every field) and **Machines**.

**Names.** `name` is short and made without cutting a word in half (`nameFromTask`: at most four words and 30 characters; whole words are dropped from the end, and only a single word longer than 30 characters is clipped, with "…"). `fullName` is the whole description the name was made from (a helper's `description`, in plain prose, at most 200 characters), or the name itself when there is none. The page may show `fullName` in the card, as a tooltip or on a second line; `name` stays the label everywhere else.

Reducer rules (in `store.mjs`):

| Event | Effect on the AgentView |
|---|---|
| `agent.created` | New view. If `parentId` is set: `depth = parent.depth + 1`, `rootId = parent.rootId`, `kind = 'helper'`. Recompute the parent's `helpers`. Ignore a duplicate `agentId`. |
| `agent.state` | Set `state`, `stateReason`, `stateSince`. Entering a state in `ENDED` sets `endedAt`; leaving one clears `endedAt` and `error` (the agent was picked up again). Leaving `needs_ok`, `question` or `maybe_stuck` clears `ask` unless an `agent.ask` follows in the same batch. Recompute the parent's `helpers`. If a root enters `waiting_helpers`, set `now` to what it waits for: "Waiting for " + `waitingFor()` (narrate.mjs) of the working helper views (else the helpers in the split) and of the commands and other background tasks in the latest split (the event's `background`, or `agent.background`): "Waiting for 2 helpers", "Waiting for a background command", "Waiting for its helper and a background command". Without a split (Codex, the simulator) `backgroundTasks` counts helpers. An empty split reads "Its background work is done". |
| `agent.activity` | `phase: 'start'`: `now = sentence`, `toolCalls += 1`, `toolKinds[toolKind] += 1`, add 1 to the current spark bucket, `thinking = false`. `phase: 'end'`: push `{ ts, sentence, ok }` onto `recent` (keep the last 8). Either phase: `lastEventAt = ts`; `starting` becomes `working`. |
| `agent.thinking` | `thinking = on`. If `on` and no tool is in progress, `now = 'Thinking'`. |
| `agent.usage` | `mode: 'set'` replaces token totals; `'add'` adds. `costUsd` is what the harness reported: `null` until it reports any (a new view starts at `null`, never `0`), and replaced when the field is present (it may be `null`: not reported). `unreportedUsd` (Workbench's estimate of what the harness spent but has not reported yet; `0` when none) is replaced when present. `contextTokens` and `contextWindow` set `contextPct = contextTokens / contextWindow`. |
| `agent.turn` | `phase: 'start'`: `turns += 1`; a root in `question`, `done_*`, `checks_failed`, `waiting_helpers` or `failed` returns to `working`, because a new turn means it is working again (a message that waited while a turn failed starts the next one: `now` is "Working on your message"). Other states are kept: `stopped` comes back only through a message from the person, and `needs_ok` and `maybe_stuck` keep their ask. `now` says what it takes up: "Reading what its helpers found" after waiting on helpers, "Reading what came back" after waiting on commands only, "Picking up where it left off" for a done root (no message from the person started that turn: the engine sets `working` first for those, with "Working on your follow-up"). `phase: 'end'`: no state change (the engine decides). |
| `agent.background` | A root's background work now, from Claude Code's `background_tasks_changed`: `{ helpers, commands, others, work, ids }`. Kept with the view's meta; while the root is `waiting_helpers`, `now` is worded again from it. Not part of the AgentView. |
| `agent.plan` | `plan = { items, done: <completed count>, total: items.length }`. |
| `agent.says` | `says = text` (plain prose, the engine strips markdown). |
| `agent.ask` | `ask = { ...ask, createdAt: ts }`. The state is set by a separate `agent.state`. A permission ask also carries `why`, the permission check's reason in plain words (the simulator gives the words the check would). |
| `agent.askCleared` | `ask = null` if `ask.id === askId`. |
| `agent.files` / `agent.checks` / `agent.rules` / `agent.model` / `agent.session` | Set the field. `agent.session` is `{ sessionId, version? }`: `version` is the harness's own version when it says (Claude Code's `claude_code_version`, see the Claude Code adapter). The view keeps only `sessionId`; the engine keeps `version` with that run (see "Agents from an earlier run", step 3). |
| `agent.work` | `{ agentId, work }`: `work` replaces the view's `work` as a whole (see "Work" below). Only its known fields are kept, as copies; a field the payload leaves out is `null` (`folder`: `false`). Ignored for helpers: a helper works in its agent's folder. |
| `agent.resumed` | An earlier agent (restored from history, see "History") is picked up: `earlier = false`, `canContinue = null`, `continueReason = null`, `now = 'Picking up where it left off'`, and `budgetUsd` is replaced when the event carries one (the fresh limit for this run). The engine sends it with `agent.state working` in one batch. |
| `agent.approval` | `approvals.auto`, `.byYou` or `.denied` += 1 (`denied` for any `decision: 'deny'`). |
| `agent.ended` | `endedAt = ts`; `error` from the event. |
| `machine.update` | Insert or replace the machine by `id`. |
| `notice` | Pass through to the UI as a notice. |

**Work.** `AgentView.work` says what became of a root's work in git. It is `null` for helpers, for demo agents the simulator gave no branch, and before a root has a folder. Otherwise:

```js
work: {
  branch: 'workbench/search-cleanup-a1b2c3', // its branch; null once thrown away, or once its folder and branch are gone
  from: 'main',            // the person's branch when it started (null when detached or unknown)
  folder: true,            // its folder is still there
  merged: { into: 'main', merge: '<commit id>', at: ms, files: 3, adds: 40, dels: 2 } | null,  // the last merge that went through
  problem: { why, sentence, paths: [], into: 'main', at: ms } | null,  // why the last merge did not go through, until it clears
  thrownAway: { at: ms, saved: 'refs/workbench/discarded/<id>' } | null,  // saved: the hidden copy
}
```

`merge` is the merge commit's id. `problem.why` is one of `conflict`, `blocked`, `ancestry`, `moved`, `identity`, `detached`, `busy`, `git`; `sentence` is the reply the person got, `paths` the files git named (both changed, or in the way), `into` the branch the merge went into. When `problem` clears, and who sets these, is in "Source control in the engine". `store.restore()` puts a record's `work` back. Besides `agents`, `machines`, `notice` and `removed`, the store emits `repo` (`repoChanged(repo)`): a copy of `{ name, head, branch, dirty, identity }` whenever the engine finds the person's repository changed; the server sends it to every page (see "HTTP server").

Every second the engine calls `store.tick(now)`. That rolls spark buckets (`SPARK_BUCKET_MS`, `SPARK_BUCKETS`) so `sparkEndsAt` stays current. Only views whose spark changed are reported as changed.

**Ids.** Root agents: 6 lowercase hex characters from `crypto.randomBytes`. Helpers: `<rootId>-<first 8 chars of the harness task id>`, or of the launching tool_use id (without `toolu_`) when the helper's messages arrive before its task id is known. A helper keeps its first id. Ids never contain `/` or `:`.

**Sorting.** `store.list()` returns roots ordered by `PRIORITY[state]` and then newest first, each root followed by its descendants in creation order.

## Agent lifecycle (engine)

The engine creates every root agent. It emits `agent.created` (with, in live mode, `agent.work` for its new folder and branch), then `agent.state starting`, then starts the adapter's runner. Runners create helpers themselves.

**A new turn clears the last turn's receipt.** When a root's turn starts (`agent.turn` `phase: 'start'`), and when a message brings an ended root (done, failed or stopped) back to `working`, the store clears `says`, `files` and `rules` to `null`, and `checks` to `{ state: 'none', results: [] }` if it had any. So a follow-up that fails, waits for background work or is stopped never shows the earlier turn's "checks passed" or its words as current; the next receipt fills them again. Helpers keep theirs. A turn start also clears `work.problem`: a merge that did not go through no longer describes work that changes again.

**Starting.** A root leaves `starting` for `working` on any output: `agent.session` (Claude Code's init), a turn start, thinking switching on, text (`agent.says`) or a tool call, not only a tool call. A root still `starting` is checked for silence like a `working` one: with no event for `stuckSilenceMs` it is asked "has not done anything for 4 minutes" (`maybe_stuck`), which a later step clears.

When a **root's** turn ends (`agent.turn` with `phase: 'end'`), the engine decides the state, in this order:

1. If `backgroundTasks > 0`: `waiting_helpers`, with the turn end's `background` split on the state event. Claude Code runs sub-agents in the background, and also shell commands the agent left running (Bash `run_in_background`, a command moved to the background at its timeout, a `Monitor`): the root's turn ends while they run, and Claude Code starts a new turn when they end. That new turn is recorded for sub-agents (fixture lines 297-298); for commands it is read from 2.1.221's code, not recorded. A command may never end (a dev server), so:
   - once the root has no helper working and nothing has happened for `stuckSilenceMs` (4 minutes; counted from its last event, its state change, the last change to its background list and the end of its last helper), it is asked once: `agent.ask { type: 'stuck', about: 'background', sentence: '<Name> has finished, but a command it started is still running.', detail: <what each command does, in Workbench's own words>, options: ['It is done', 'Keep waiting'] }` and `agent.state maybe_stuck` (reason "It left something running");
   - "It is done" (or "done") decides the turn as if nothing were left: the receipt below. The root leaves `maybe_stuck` at once (`agent.ask.cleared` and `agent.state working` in one batch), so the receipt is built while it is `working`, as after any turn, and a turn that starts during its checks is `working` and watched by the usual stuck rules. Its `now` keeps its last words ("Waiting for a background command") until the next step. The command keeps running until the person stops the agent or closes Workbench, and later turns do not wait again for the same task ids. "Keep waiting" goes back to `waiting_helpers` and is not asked again in that turn. "Stop it" stops the agent. Other words are a message for it;
   - a new turn takes the question back (the root works again); a process that exits cleanly while any stuck ask shows (background, repeats, errors or silence) makes the root `failed` ("It stopped before finishing its work.") and clears the ask, since nothing is left to answer it. "It is done" or "Keep waiting" that comes between the exit and that change does nothing: the reply is "<Name> stopped running before your answer reached it." (`ok: false`);
   - if the background list is empty by then but no new turn came, the turn is decided without asking.
2. If `isError`: `failed`, with `stateReason` from the result. Examples: budget reached, model error.
3. Record what changed so far, whether or not a question follows: files changed and not merged yet (`diffStats` from the run's `since`: the commit it started from, or its last merged work commit; see "Source control in the engine") and rules (`checkRules`).
4. Read the closing ask with `extractQuestion(finalText)`. It looks at the last paragraph that is not only courtesy, and at its last three sentences. A sentence ends at `.`, `!` or `?` followed by a space or the end, so "node test.mjs?" stays whole; never after "e.g.", "i.e.", "vs." or "cf.", nor after "etc." or an initial ("A.", "U.S.") when the next word starts in lower case ("the U.S. date format" goes on; "I went with option A. Should I continue?" is two sentences). These count only as words of their own, so "src/main.cf." still ends one. Known limit: an initialism before a capital still ends a sentence ("Should I use the U.S. English spelling?" reads "English spelling?"). A courtesy asks nothing and is skipped ("Let me know if you need anything else.", "Is there anything else...?", "Anything else?", "Want me to do anything else?", "Need anything else?", "Can I help with anything else?", "What else can I do?", "Feel free to...", "Hope this helps."; when the question names something, "Want me to also fix the lint errors?", it stays a question); a line that names a decision ("should", "which", "whether", "prefer", "proceed", "continue", "before I") is never a courtesy. The ask is the last remaining sentence that ends with `?` or asks for a decision ("how would you like to proceed" included). An offer of more work ("Would you like me to also add a test?") is a question too.
   If there is one: emit `agent.says firstSentence(finalText)` when it differs, `agent.checks null` when older checks are showing, `agent.ask { type: 'question', sentence, options: [] }`, then `agent.state question`. The declared checks do not run: they judge finished work, and half-done work fails them. If step 3 failed, the question is still asked.
5. Otherwise run the declared checks (`runChecks`, with `agent.checks state: 'running'` while they run, and the agent's own `WORKBENCH_AGENT_ID` in their environment; with Connect, also the keys that agent gets and the mask that hides them, see "Keys, masking and the default agent"). Then:
   - all checks passed: `done_checked`;
   - a check failed: `checks_failed`;
   - no checks declared: `done_claimed` (also when step 3 or the checks could not run, with a plain reason: "Workbench could not run the checks.", the sentence of a plain error step 3 met, or else "Workbench could not check its work.");
   - and `agent.says firstSentence(finalText)`.

**One receipt at a time per agent.** Steps 3 to 5 are one receipt. A new turn, a message the agent took (`runner.send` succeeded), stopping the agent, or shutdown cancels a receipt still being built: the engine aborts the signal it gave `runChecks` (its checks' process groups are ended), applies nothing more from that receipt, and sets `agent.checks` to `{ state: 'none', results: [] }` if it said running. A newer receipt starts its checks only after the cancelled ones have ended, so two sets never run in one folder, and while a receipt is being built the agent is not checked for being stuck and a clean exit is not a failure (Codex exits after every turn). `agent.ended` does not cancel it.

**Held requests come first.** If the root is showing a held permission request when its turn ends (a helper's request Workbench could only show on the root), the decided state and the question's `agent.ask` wait: the engine applies them once the person has answered the last held request, and drops them if a new turn starts or the agent is stopped first. Files, checks, rules and `agent.says` show at once. A `failed` turn goes through at once, and the root's held requests are answered no. See "Held requests stay in view" below.

The engine gives a **helper** its final state when its runner reports the helper's task completed: `finished`, `failed` or `stopped`.

**Agent folders after Workbench stops.** An agent's worktree and its `workbench/<task>-<id>` branch are the only copy of its work until the person merges it into their branch or throws it away (see "Source control"), so they are kept: Workbench removes neither while it runs (stopped, failed and done agents take follow-ups in the same folder), except when the person throws the work away. It removes a folder and its branch only when they hold nothing: at once when the agent could not start, and at shutdown, after the agent's process has stopped, for every agent of this run and for the earlier agents merged in this run (`removeWorkspace` with `onlyIfUnchanged`). "Nothing" counts from where the agent's unmerged work starts (`since`: the commit it started from until its first merge, then its last merged work commit), so a merged agent that did nothing more goes, with its branch. Once it was merged, git also hears `since`, and the folder and branch go only while a branch of the person's (any local branch outside `workbench/`) still holds that commit: a merge the person undid never takes the only copy of the work with it. A folder that holds files git ignores is kept, even a merged agent's (a `.env` it made), and the CLI then lists it with the folders that hold work. When an earlier agent's folder goes, its view gets `folder: false` and `branch: null`, and its record keeps no folder, so it can no longer continue ("Its folder was not kept, so it cannot continue."). Earlier agents this run did not merge are left alone: another Workbench on the same repository may be running them. An agent whose work is being merged or thrown away is not tidied. Shutdown first lets a launch under way finish (up to `stopTimeoutMs`, 8 s), so no agent starts unseen after it began: an agent whose folder git was still making starts nothing, and that folder and branch go again (listed with the kept folders if they cannot), and one whose process was starting is stopped with the others. Then it waits for a merge or throw-away under way (each of its git commands has its own time limit), and starts no new one. At exit the CLI prints where the kept work is (`keptFolders()` lists this run's folders only). A forced exit (a second Ctrl-C, or 12 seconds) skips the tidying: every folder stays, and the CLI lists them all from `keptFolders()` without claiming they hold work. Known limit: a forced exit during a merge leaves git to finish on its own (it runs in a process group of its own, so the Ctrl-C does not reach it); Workbench does not record that merge, and the next proposal says the work is already in.

**Agents from an earlier run.** In live mode the engine restores the repository's history when it starts (see "History"): each saved root becomes a view with `earlier: true`, the state it ended in, `endedAt`, and no process, no runner and no ask (`store.restore`, not an event). An agent that was still active when the file was written (a forced exit, a crash) comes back `stopped`, with the reason "Workbench was closed while it was working.". It is never stuck-checked, never needs the person, and its checks do not run again. Its `work` is the saved one, with `folder` as it is on disk now; a record from before Workbench kept `work` gets `{ branch, from, folder, merged: null, problem: null, thrownAway: null }` from its workspace when it has a branch, so that branch can still be shown, merged or thrown away. A message to it (`say`, an answer on a finished agent, the page's "Continue", or the words "continue <name>") **continues** it (`_continueEarlier`):

1. It must be continuable now (`canContinue`, checked again at that moment): its work was not thrown away, its harness is available, it has a saved session id, its folder is still there (a directory with a `.git` entry), and Claude Code still has its conversation (`sessionExists` of the Claude adapter; `null` means it cannot tell, and does not block). Otherwise the reply is "<Name> cannot continue. <reason>" (`ok: false`) and nothing changes. Reasons: "Its work was thrown away, so it cannot continue.", "Its folder is gone, so it cannot continue.", "Its folder was not kept, so it cannot continue.", "It never saved its conversation, so there is nothing to pick up.", "Claude Code no longer has its conversation, so it cannot continue.", "Claude Code is not available on this computer.". While its work is being merged or thrown away, the reply is the busy sentence ("<Name> is being merged now."), and while Workbench shuts down, "Workbench is shutting down.".
2. A new runner is made in the same folder with `sessionId` set to the saved Claude session id or Codex thread id, and the message goes to it with `send()`: Claude Code resumes with `--resume <sessionId>` (the runner's own resume path), Codex runs `codex exec resume <thread>`. If `send` refuses (for example no spending left, or Claude Code cannot be found), the reply is the runner's own sentence and the agent stays earlier. The run's places are the record's (`{ path, branch, base, since, from }`; a record from before Workbench kept `since` counts its unmerged work from `base`).
3. **Budget.** It gets a fresh spending limit for this run: the engine's `--budget` (`defaultBudgetUsd`), whatever the earlier run had. The reply says so: "<Name> is continuing in its own folder. It has a new spending limit of $2.00 for this run." The lid says it before the person presses Continue. A resumed Claude Code process counts its totals from zero (observed with 2.1.221), so the engine adds the earlier run's reported and estimated spend (`costUsd + unreportedUsd`) and tokens to every `agent.usage mode:'set'` of that run (`_withEarlierSpend`). The docs say Claude Code 2.1.277 and newer restore a resumed session's totals themselves: when the resumed process's own session line reports such a version (`agent.session` `version`, read as major.minor.patch, a leading "v" and trailing text allowed), nothing is added. An unknown or unreadable version adds it; Codex always adds it. *Not yet recorded:* the 2.1.277 threshold comes from the docs; record a stop-then-continue run on 2.1.322 to settle it. When the gate applies, the earlier run's `unreportedUsd` (Workbench's estimate of spend the earlier process never reported) is not carried over either.
4. `agent.resumed` and `agent.state working` are applied, `work.problem` clears (it took a message), the receipt, checks and stuck rules work as for any root, and the folder is tidied at shutdown like any other.

"Forget" (the page's button, or "forget <name>") always asks first, with an ordinary confirm card ("Forget Invoice export?"). Its detail promises only folders that are really kept: "It will not show here again. Its folder and branch stay on this computer.", or "It will not show here again." for an agent whose work was thrown away or whose folder was not kept; for several, "They will not show here again. Their folders and branches stay on this computer.", "They will not show here again. The folders still on this computer stay there." or "They will not show here again.". Yes removes the earlier agent from the store (`store.remove`, which emits `removed`: the server sends every page a fresh `snapshot`), writes the history at once, and keeps it out of the file. It never touches the worktree or the branch. The reply is "Forgot <Name>." followed, the same way, by "Its folder and branch are still on this computer." ("Their folders and branches are still on this computer.", "The folders still on this computer stay there.") only for what is kept. An agent from this run is not forgotten ("<Name> is from this run, so it stays. It is kept for next time."), nor one being merged or thrown away (the busy sentence); stopping an earlier agent says "<Name> is from an earlier run, so nothing is running.".

**Stuck** (`stuck.mjs`, called from the engine's tick). An active agent is possibly stuck when any of these holds:

- the same tool sentence and input started 3 times in a row with no successful step in between;
- the same error text came back 3 times, each time within 10 steps of the time before and from a step started after it. A step is one tool call that finished, whatever its outcome; calls made together count as one step, so a batch that fails the same way counts once. Other steps succeeding in between do not reset the count: that is the agent editing and retrying into the same error. Only failed steps with error text count, and counts start afresh each turn. The same error now and then over a long turn is not a loop;
- it is `working` with no event for 4 minutes and no helpers working.

The engine then emits `agent.ask { type: 'stuck', sentence: '<name> has hit the same error three times.', options: ['Stop it', 'Let it keep trying'] }` and `agent.state maybe_stuck`. The state clears when the person answers, or when any step succeeds (after a silence, also when any step starts), whichever rule flagged it. So in an edit-and-retest loop the flag can come and go: the next edit that works clears it, and three more of the same error raise it again. Only `working` agents are checked, and never while their receipt is being built; a root that is `waiting_helpers` gets the question about background work in step 1 above instead.

## Permission flow (Claude Code)

Every Claude Code agent runs with a `PreToolUse` hook that calls `src/adapters/claude/hook-bridge.mjs`:

1. The bridge reads the hook payload from stdin. A payload whose `hook_event_name` is not exactly `PreToolUse` is blocked (exit 2) without asking the engine. It POSTs `{ agentId, payload }` to `WORKBENCH_HOOK_URL` with header `X-Workbench-Token: $WORKBENCH_HOOK_TOKEN`, which is that agent's own hook token, then waits as long as it takes.
2. The engine checks who is asking, then calls `policy.decide(...)`:
   - Only a live Claude Code root the engine launched may ask ("Workbench does not know this agent, so it said no." otherwise, for a Codex or simulated agent too). A stopped agent gets "This agent was stopped."; a request that arrives after the agent's process has gone (its runner's `info().alive` is false) gets "This agent is no longer running."; a helper the person stopped gets "The person stopped this helper.", even for tools the rules allow (a live helper from the moment its agent is asked to stop it; checked again after the policy, in case the stop came while the request was being checked). None of these shows anything.
   - The policy gets `cwd` (the engine's workspace, never the payload's), `extraAllow` (workbench.json), `readAlso` (the runner's `readAlso()`: Claude Code's own folders for this agent's session, keyed by the runner's session id, never the payload's) and `recipients` (`"main"`, the root's helper ids from the store, and the runner's `recipients()`: the helpers' task ids and the names their Agent calls gave them, read from Claude Code's own output, never from the payload).
   - **allow**: answer at once and emit `agent.approval how:'auto'`.
   - **deny**: answer at once.
   - **ask**: emit `agent.ask { type: 'permission', sentence: '<Name> <sentence>', detail, why, options: ['Allow', 'Deny'], primary: 'Allow' }` and `agent.state needs_ok` on the agent that asked. `why` is the policy's `reason` ("The file is outside the agent's own folder."), so the page can say why it asks. Who asks: without `payload.agent_id`, the root. With it, the runner names the agent from Claude Code's own output (`agentFor({ toolUseId: payload.tool_use_id, taskId: payload.agent_id })`), whatever id the helper got; a runner without `agentFor` gets the helper `<rootId>-<agent_id[:8]>`. If no helper is found within 1.5 seconds, the root asks in its place. A request from a helper that has already ended (`finished`, `failed` or `stopped`), checked again just before holding, is denied at once with "The helper is no longer running.": it is not asked about and does not bring the helper back. Then hold the HTTP response until the person answers, or until 25 minutes pass, which counts as a deny with the reason "No answer from the person in time".
   - **Held requests stay in view.** After every batch of events, each held request shows on its agent (its `ask`, with `agent.state needs_ok`) or waits behind another held request of the same agent that shows. While an agent shows one, the engine's other `agent.state` and `agent.ask` events for it wait (`finished`, `failed` and `stopped` go through); after the last request is answered the agent goes on to what was decided meanwhile, else to `working` if its turn is running, else back to `waiting_helpers` or `working`. An agent that finishes, fails, is stopped or is gone has its held requests answered no. Anything else that hid a held request (it should never happen) shows it again, with a warning in the log.
3. The engine responds with `{ hookSpecificOutput: { hookEventName: 'PreToolUse', permissionDecision: 'allow'|'deny', permissionDecisionReason } }`. The bridge prints it to stdout and exits 0.
4. **Fail closed.** On any bridge error (unreachable engine, non-200, bad JSON, a payload that is not `PreToolUse`), the bridge writes a one-line reason to stderr and **exits 2**, which blocks the tool. This was verified against Claude Code 2.1.221: exit 2 blocks the call; exit 1 falls back to Claude Code's own permission check, which in headless mode refuses anything that needs approval. It was verified again on 2.1.322 (2026-11-12): a PreToolUse hook that exits 2 blocks a Bash call, and Claude Code passes the hook's stderr on as the tool's error ("PreToolUse:Bash hook error: …").

The hook is registered with `"timeout": 1800` (seconds). Holding a request for more than 60 seconds was verified to work.

**Hook tokens.** Each Claude Code agent gets its own token: an HMAC-SHA256 of `workbench-hook:<agentId>` under a key that only the Workbench process holds (`bin/workbench.mjs`). The server accepts it on `/hook/pretool` only for that `body.agentId`, compared in constant time, and never on `/api`. So an agent's own environment cannot put asks on another agent's card. This does not separate agents that run as the same user: code an agent runs can read a sibling's environment (`ps eww`).

## Claude Code adapter

Facts below were observed in real runs of Claude Code 2.1.221. Fixtures: `test/fixtures/claude-*.jsonl` (one stdout JSON object per line) and `test/fixtures/hook-pretool-*.json`. Claude Code 2.1.322 (the VS Code extension's native binary) still lists every launch flag in `--help` and parses the whole launch, and one real acceptance run against it (`scripts/accept-real.mjs`, haiku) passed: a helper showed, a held command waited for Allow, and the receipt, the diff, the merge and the throw-away were as expected. On 2.1.322 the hook's exit-2 fail-closed was checked on its own (see "Fail closed" above), and a real haiku agent working on Workbench's own repository ran `npm test` in its worktree (773 tests passed) with node only on the PATH Workbench gives it. Not yet recorded on 2.1.322: spend on resume (a stop-then-continue run).

**Launch** (`args.mjs` builds this; `runner.mjs` spawns it in the agent's workspace):

```
claude -p --input-format stream-json --output-format stream-json --verbose --forward-subagent-text
       --setting-sources project --permission-mode default --strict-mcp-config
       --disallowedTools "Workflow CronCreate CronDelete CronList ScheduleWakeup PushNotification EnterWorktree ExitWorktree AskUserQuestion RemoteTrigger DesignSync SendFile SendToProject PublishPlugin ListAgents WrapUp"
       --settings '{"disableAllHooks":false,"env":{"WORKBENCH_HOOK_URL":"<url>","WORKBENCH_AGENT_ID":"<id>"},"hooks":{"PreToolUse":[{"matcher":"*","hooks":[{"type":"command","command":"<hook command>","timeout":1800}]}]}}'
       --append-system-prompt '<WORKBENCH_PROMPT>'
       --max-budget-usd <budget> --session-id <uuid> --name <name> [--model <model>]
```

- `--setting-sources project` and `--strict-mcp-config` keep the person's own plugins, hooks and MCP servers out of launched agents. Without them, the plugins on this machine injected instructions, an extra Stop hook and Slack tools into every agent. `project` loads the repository's committed `.claude/` settings, `CLAUDE.md`, rules, skills, agents and commands. `local` is left out: `.claude/settings.local.json` is the person's own, and in a worktree Claude Code reads it from the person's main checkout.
- `--settings` also carries `WORKBENCH_HOOK_URL` and `WORKBENCH_AGENT_ID` in its `env`. Settings given on the command line outrank the project's, so an `env` block in a committed `.claude/settings.json` cannot point the bridge at another address or speak for another agent (`test/live-fake.test.mjs` tries it). The hook key `WORKBENCH_HOOK_TOKEN` is in the process environment only, never in argv, which other programs on the machine can read; a repository that overrides it only makes every request fail, so the call is refused. The launch checks of `test/helpers/claude-fake.mjs` require the pinned values.
- `--permission-mode default`: no settings file can choose `bypassPermissions`, which would switch off Claude Code's own refusal to change protected files (`.git`, `.claude`, `.vscode`, `.npmrc`, shell rc files and the like). 2.1.322's `--help` lists `manual` instead; `default` is still accepted (it is the mode `manual` stands for), and 2.1.221 knows only `default`.
- **`--settings`** carries `disableAllHooks: false` next to the hook. Settings given on the command line outrank the repository's, so a `disableAllHooks: true` in any settings file cannot remove the workbench's check (it would fail open).
- **Hook command:** `'/usr/bin/env' '-u' 'NODE_OPTIONS' '<node>' '<bridge>'`, every word quoted for the shell Claude Code runs it through. Claude Code takes the hook's environment from settings files, and a planted `NODE_OPTIONS` could load a script into node that prints "allow" without asking the engine.
- **`--disallowedTools`** (16 tools): tools that schedule work outside the workbench's view (`Workflow`, `Cron*`, `ScheduleWakeup`, `RemoteTrigger`), change worktrees (`EnterWorktree`, `ExitWorktree`), wait for a terminal (`AskUserQuestion`), send notifications (`PushNotification`), need a sign-in that cannot finish in a headless run (`DesignSync`), or reach past this agent, new in 2.1.322: `SendFile` sends files to another Claude Code session, on this machine or another; `SendToProject` sends the session's work to a Claude Project on claude.ai; `PublishPlugin` publishes a folder to the organisation's plugin library; `ListAgents` lists the person's other sessions; `WrapUp` draws a next-step box in the app and is told to run in every turn. The list is pinned in `args.mjs` (`DISALLOWED_TOOLS`), in `test/claude-runner.test.mjs` (the exact argv, and the count of 16) and in `test/helpers/claude-fake.mjs` (a subset that includes the five new names). The runner warns when `system/init` still offers one of them (see Runner below).
- **Environment.** Copy `process.env`, delete the markers a surrounding Claude Code session or its editor/SDK host sets for the programs it runs (`SCRUB_ENV_RE` in `args.mjs`: `CLAUDECODE`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDE_JOB_DIR`, `CLAUDE_AGENT_SDK_*`, and `CLAUDE_CODE_` + `CHILD_SESSION`, `SESSION_*`, `BRIDGE_SESSION_ID`, `MESSAGING_*`, `REMOTE*`, `ENTRYPOINT`, `EXECPATH`, `SSE_PORT` and a few editor-host switches), the editor's own variables (`VSCODE_*`, `ELECTRON_RUN_AS_NODE`, `GIT_EDITOR`: present when Workbench was started from VS Code, or from Claude Code inside it) and Workbench's own choice of programs (`WORKBENCH_CLAUDE_BIN`, `WORKBENCH_CODEX_BIN`, so a Workbench an agent starts inherits neither), then the person's keys for this agent (see "The person's keys" below), then `WORKBENCH_HOOK_URL`, `WORKBENCH_HOOK_TOKEN` (this agent's own hook token) and `WORKBENCH_AGENT_ID`. Never put the token in the command line or `--settings`: other users can read command lines with `ps`. The person's own settings and credentials stay: `CLAUDE_CODE_OAUTH_TOKEN` may be the only login on a cloud machine, and `CLAUDE_CODE_USE_BEDROCK`/`_VERTEX` choose the provider. (Codex agents and declared checks still get no `CLAUDE_CODE_*` at all.)
- **The person's keys** (`keysEnv` in `createRunner` and `buildClaudeLaunch`; `withKeys(env, keysEnv, refused)` in `args.mjs`): `{ NAME: value }`, which the engine gives for this agent and repository (see "Keys, masking and the default agent").
  - They go after the scrub and `withNodeOnPath`, and before `WORKBENCH_HOOK_URL`, `WORKBENCH_HOOK_TOKEN` and `WORKBENCH_AGENT_ID`, so no key can replace those three.
  - Left out: a name that is not a variable name (`/^[A-Za-z_][A-Za-z0-9_]{0,127}$/`), any `WORKBENCH_*`, a name the scrub removes (`SCRUB_ENV_RE`), and a value that is not a string or holds a NUL.
  - Never in argv or `--settings`. Keys never feed `findClaude` or `sessionFolders` (`readAlso`): those read `env`, the base environment, so a key cannot choose the program or move the policy's own folders.
  - A relaunch (`--resume`) gets the same keys.
- **Masking** (`mask` in `createRunner`; `safeMask`, `maskParsed`, `maskCut`, `maskedTail` and `MASK_MARGIN` in `args.mjs`).
  - Each stdout line is parsed as JSON, then every string of 8 or more characters in it goes through `mask` before the parser reads it. A key that the parser (300 characters of tool input) or `narrate()` cuts short later never shows in part. A line that is not JSON is masked before its first 120 characters are logged.
  - Stderr is kept with `MASK_MARGIN` (2048) characters to spare beyond the 4096 shown, and masked when it becomes `agent.ended`'s error. When earlier stderr was dropped, the start of what is kept may lie inside a cut key, which no mask can find, so it is left out: up to its first line break (a key holds none), or 2048 characters when there is none that near, and never past where the mask first hid something, since a whole key began there.
  - A mask that throws, or returns anything but text, hides nothing. Without `mask`, nothing changes.
- **Node on the PATH** (`withNodeOnPath` in `args.mjs`). When the PATH holds no `node` program (only absolute folders count, and the file must be executable), the folder of the node running Workbench (`dirname(process.execPath)`) goes first; with no PATH at all it becomes `<that folder>:/usr/bin:/bin`. So the agent's `npm test` and `node --test` run, and the policy approves them by those words. A PATH that has a node is left exactly as it is. `available()` runs `--version` with the same environment. Recorded on 2.1.322 (2026-11-12): Claude Code's Bash tool keeps this PATH. With no node on the person's own PATH, a real agent's `npm test 2>&1 | tail -n 60` ran the suite in its worktree. Claude Code needs `USER` in its environment to find its login in the macOS keychain; a terminal always has it, and the agents' environment keeps it.
- **The session's own folders** (`sessionFolders` in `args.mjs`, the runner's `readAlso()`): `{ root: <CLAUDE_CONFIG_DIR or ~/.claude>/projects, session }` for long tool results and `{ root: realpath(<CLAUDE_CODE_TMPDIR or /tmp>)/claude-<uid>, session }` for background task output, with the runner's own session id. Nothing before the session id is known or when it is not a UUID; no temporary folder without a user id. Workbench does not set `CLAUDE_CODE_TMPDIR`.
- **`WORKBENCH_PROMPT`:** "You are running inside Workbench, which shows your progress to a person in plain language. Work only inside the current folder. If you need a decision from the person, end your turn with one short, clear question. When you finish, begin your final message with one plain sentence, understandable by someone who does not write code, saying what you did."
- **First message.** Written to stdin as `{"type":"user","message":{"role":"user","content":[{"type":"text","text":"<task>"}]}}` plus a newline. Further messages (answers, hints) use the same shape. The process stays alive between turns while stdin is open. Closing stdin ends it.
- **Binary** (`findClaude({ flag, env = process.env, cwd = process.cwd() })` in `args.mjs` -> `{ path, from, reason? }`). In this order:
  1. the CLI's `--claude <path>` (`from: 'flag'`);
  2. `WORKBENCH_CLAUDE_BIN` (`'env'`; empty counts as unset);
  3. `claude` on the PATH (`'path'`; folders written as relative paths never count);
  4. the newest `<HOME>/{.vscode,.vscode-insiders,.cursor}/extensions/anthropic.claude-code-<x.y.z>[-<os>-<arch>]/resources/native-binary/claude` (`'vscode'`). Folders listed `true` in that folder's `.obsolete`, builds for another operating system (`alpine` counts as linux) and programs that cannot run are skipped; on the same version, a build for this processor wins, then one that is not for Alpine. Without `HOME` in a given environment, no home folder is read.

  A given path is read from Workbench's own folder (`cwd`), with `~/` expanded; a bare name is looked up on the PATH. A given path that is not there, or is a folder, is reported as it is, never swapped for another Claude Code: "Claude Code is not at <path>, the path given with --claude." ("…, the path in WORKBENCH_CLAUDE_BIN."), "The path given with --claude, <path>, is a folder, not the Claude Code program.", "There is no <name> command on the PATH (the name given with --claude)." ("(the name in WORKBENCH_CLAUDE_BIN)"). Nothing found anywhere (`CLAUDE_NOT_FOUND`): "Claude Code was not found: there is no claude command on the PATH, and no Claude Code extension in VS Code or Cursor. Tell Workbench where it is with --claude <path>, or with WORKBENCH_CLAUDE_BIN." `claudeBin(env, { flag })` is `findClaude(...).path || 'claude'`, and `buildClaudeLaunch` takes an optional `bin`. Tests point `WORKBENCH_CLAUDE_BIN` (or `--claude`) at a script that replays a fixture, with a temporary HOME. `~/.vscode-server/extensions` (VS Code Remote) is not searched.

**Parsing** (`parse.mjs`; pure; `createClaudeParser({ rootId, now })` returns `{ push(obj) -> Event[] }`):

- **`system/init`.** Comes once per turn. Emit `agent.model` with `obj.model` and `agent.session` `{ sessionId: session_id, version? }` for the root (no session id, no session event), then `agent.turn phase:'start'`. `version` is `claude_code_version` when it matches `/^\d{1,4}\.\d{1,4}\.\d{1,6}(?:[-+][0-9A-Za-z.-]{1,40})?$/`, else left out. Each process reports its own, since a relaunch may run a newer Claude Code; the parser's `info().version` keeps the last good one.
- **Root assistant messages** (`parent_tool_use_id` null). For each content block:
  - `thinking`: `agent.thinking on`.
  - `text`: remember it as the latest root text.
  - `tool_use`: `agent.activity start` with `narrate(name, input)`. Remember `id` mapped to `{ agentId, sentence, toolKind }`. A shell command reads as what it does ("Running the tests"), a package script by its name ("Running the db:migrate script"), or else as the command itself, clipped ("Running make deploy"); never as the agent's own `description` of it, which the agent writes.
    - The script name is the word right after `run` or `run-script`. If that word is an option (`npm run -w api test`), the line shows the command itself, since the next word may be the option's value.
    - Control, line-separator and direction-changing characters (Unicode's Bidi_Control set) become spaces before a command is clipped, for Bash and Monitor alike.
  - `Agent` or `Task` tool_use: remember it as a pending helper, keyed by tool_use `id`, with the `name` the call gives it (`SendMessage` can reach the helper by that name).
  - `TaskCreate { subject }`: add a plan item `{ id, text: subject, status: 'pending' }`. The id comes from the tool result `"Task #N created"` or the item's position.
  - `TaskUpdate { taskId, status, subject? }`: update that item.
  - `TodoWrite { todos: [{ content, status }] }`: replace the plan.
  - Emit `agent.plan` after any change.
- **Usage dedupe.** One assistant message is split across several stream objects that repeat the same `message.usage`. Count usage once per `message.id`. For the root, `contextTokens = input_tokens + cache_read_input_tokens + cache_creation_input_tokens` of the latest message.
- **Spend not reported yet.** Observed: `total_cost_usd` and `modelUsage` come only on `result` lines, so before a turn ends nothing is reported (the view's `costUsd` stays `null`, "not reported yet", never `$0`). A message's input-side tokens are exact, but its `output_tokens` is only the count when the message began. *From the docs, not yet recorded:* a turn stopped with SIGTERM records no result. Each new message (root or helper) adds to an estimate, priced with `PRICES` in `parse.mjs` (`estimateUsd`); a model not listed is priced as the most expensive. Root `agent.usage` events carry it as `unreportedUsd`. In the recorded runs the result reported 6 to 14 percent more than the estimate, so it is a lower bound.
- **Tool results** (`type: 'user'`, `tool_result` blocks). `agent.activity end` for the remembered `tool_use_id`, with `ok = !is_error`. The Agent tool's result is metadata ("Async agent launched"), not an end of work.
- **`system/task_started { task_id, tool_use_id, description, subagent_type }`.** `agent.created` for a helper: `agentId = <rootId>-<task_id[:8]>`, `parentId` = the agent that issued `tool_use_id`, `name = nameFromTask(description)`, `fullName` = the description in plain prose (at most 200 characters), `helperType = subagent_type`, `harness: 'claude'`. Then `agent.state working`. Keep the map `task_id` and `tool_use_id` to helper id. If the helper already exists (made from its forwarded messages), only map `task_id` to it: no new helper, no new id. A task that is not a sub-agent (a shell command, `task_type: 'local_bash'`) makes no helper; its task id is mapped to what the shell call that started it does, in Workbench's own words.
- **`agentFor({ toolUseId, taskId })`** returns the agent that issued that tool call (the root or a helper, while the call is open), else the helper with that task id, else null. The PreToolUse hook payload carries both (`tool_use_id`, `agent_id`).
- **Messages with `parent_tool_use_id = X`** belong to the helper whose `tool_use_id` is X. Their tool_use, tool_result, thinking and usage become that helper's events. Usage uses `mode: 'add'`, deduped by `message.id`.
- **`system/task_progress { task_id, description, usage: { total_tokens, tool_uses, duration_ms }, last_tool_name }`.** Emit `agent.activity start` on the helper.
  - Claude Code builds `description` from the call's input for Read, Write, Edit, NotebookEdit, Glob, Grep, WebFetch and WebSearch ("Reading greet.js"); that sentence is used as it is.
  - For any other tool, Claude Code uses words the agent wrote: "Running <the Bash call's description>", "Monitoring: <description>", an Agent call's description, or the helper's task. Those lines, and lines without `last_tool_name`, are not shown. The forwarded call names the step by what it really does, so each step still starts once (the store counts every start).
  - Do not double count a tool start: `usage.tool_uses` numbers the helper's steps, and forwarded tool_use blocks are counted the same way. A forwarded call for a step a progress line already described from its input is not shown again. A forwarded call for any other tool is always shown, even when a later step's progress line came first. Without a count, compare against the helper's last sentence.
- **Helper ends.** On `system/task_updated` with `patch.status` in `completed | failed | killed | stopped`, or on `system/task_notification { status, summary }`, emit `agent.says firstSentence(summary)` (when there is a summary), then `agent.state finished | failed | stopped` and `agent.ended` for the helper. Ignore duplicates.
- **`system/background_tasks_changed { tasks: [{ task_id, task_type, description }] }`.** Track the root's running background tasks. A task is a helper when the parser shows a live helper for its id; otherwise it is a command (`task_type: 'local_bash'`: Bash `run_in_background`, a command moved to the background at its timeout, a `Monitor`) or another background task (any other kind; unknown kinds are never taken for helpers). After any stream object that changed it, emit `agent.background { helpers, commands, others, work, ids }` for the root: `work` is up to three lines saying what the commands do, in Workbench's own words (never the task's `description`, which the agent wrote), `ids` the task ids that are not helpers. *These shapes come from 2.1.221's code and were never recorded for commands; record one run with Bash `run_in_background`, a timeout and TaskStop before relying on them.*
- **`system/thinking_tokens`.** Emit `agent.thinking on` only when it was off. A later tool_use or text turns it off.
- **`result { total_cost_usd, modelUsage, num_turns, is_error, result, permission_denials, subtype }`.**
  - `total_cost_usd` is **cumulative for the session**: set it, never sum it.
  - Token totals are the sums over `modelUsage[*]` of `inputTokens`, `outputTokens`, `cacheReadInputTokens` and `cacheCreationInputTokens` (also cumulative): `agent.usage mode:'set'`, with `unreportedUsd`.
  - A result covers what its totals grew by; the estimate keeps only what they do not include yet (a helper's message can stream before a result and be billed after it).
  - After a relaunch, the first result shows whether the new process counted what the stopped one spent after its last result (the same input-side token test as for the totals). If not, its tokens stay in the totals and its estimate stays in `unreportedUsd` for good. *From the docs and the 2.1.221 bundle, not yet recorded:* a `-p --resume` process starts its totals at zero; the docs say totals are restored from v2.1.277, which is why the engine adds an earlier run's spend only for an older or unknown version (see "Agents from an earlier run", step 3). Follow-up: record one stop-then-resume run as a fixture.
  - `contextWindow` comes from `modelUsage[*].contextWindow`.
  - Then `agent.turn phase:'end'` with `finalText: result`, `backgroundTasks: <count>`, `background: <the split, as in agent.background>`, `isError: is_error || subtype !== 'success'`.
- Unknown message types are ignored.

**Runner** (`runner.mjs`; `createClaudeRunner(opts)` returns a Runner, see below):

- Split stdout on newlines, buffering partial lines. Keep the last 4 KB of stderr (with a mask, 2 KB more: see "Masking" above).
- On exit with code 0: `agent.ended outcome:'ok'`, unless the engine already ended it. On non-zero exit: emit `agent.ended outcome:'error'` with the stderr tail, then `agent.state failed`.
- `stop()` sends SIGTERM to the process group (spawn `detached: true`; kill `-pid`), then SIGKILL after 3 seconds.
- `send(text)` writes to stdin if the process is alive. Otherwise it relaunches with `--resume <sessionId>` (same flags, no `--session-id`) and writes the message.
- **Claude Code is looked up again at every launch and relaunch** (`findClaude`, with `opts.claudePath`, the CLI's `--claude`): the VS Code extension moves to a new folder with each update. When it is not found, `start()` and `send()` reject with that plain sentence (`err.plain`, the reason or `CLAUDE_NOT_FOUND`) and emit nothing: the engine shows "It could not start: <sentence>" and removes the empty folder, or replies with the sentence and leaves the agent as it was (an earlier agent stays earlier). A spawn that fails for another reason (the program gone in between, permission refused) rejects with "Claude Code could not be started: …".
- **What Claude Code offers**, logged once per process from its `system/init`: "Claude Code <version> (permission mode <mode>) offers <n> tools: <names>" (info); "Claude Code offers tools Workbench turned off for its agents: <names>" (warning) when it lists one of `DISALLOWED_TOOLS`; "Claude Code runs this agent in permission mode <mode>, not the default mode Workbench asked for." (warning) when the mode is neither `default` nor `manual`. Each launch logs "started Claude Code from <path> (pid <n>[, resuming its session])". Log lines go to `log[level]` when the logger has it (the CLI's shows warnings without `--verbose`), else to `log(line)`.
- `available({ env = process.env, timeoutMs = 5000, claudePath })`: finds Claude Code, then runs `<path> --version` (5 s, the scrubbed environment with node on the PATH). It answers `{ ok, version?, reason?, path?, from? }`, with `path` and `from` (`'flag'`, `'env'`, `'path'` or `'vscode'`) also when that program cannot be used. Reasons: the finding reasons above, "Claude Code could not be started: <path> was not found.", "Claude Code could not be run: permission was refused.", "Claude Code did not answer when asked for its version.", "Claude Code could not be started. It said: <first line it wrote to stderr>".
- **Budget on a relaunch.** `--max-budget-usd` counts only the new process's own spend (from the docs, not yet recorded: totals restored on resume don't count toward it, and in the 2.1.221 bundle the check is the process's running total against the limit). So a relaunch gets the budget minus the reported cost minus `unreportedUsd`. If less than one cent is left, `send` refuses with a plain error the engine passes on as it is: "<Name> has used its whole spending limit, so it can’t continue."
- `readAlso()`: `sessionFolders` for its current session id and the environment it launched Claude Code with.
- `recipients()`: the parser's list of what `SendMessage` may call this root's own helpers: each helper's workbench id, its full task id (Claude Code tells the agent to continue a helper with `to: '<task id>'`) and the `name` its Agent call gave it. Helpers that have ended count too.
- `agentFor({ toolUseId, taskId })`: the parser's answer, for the hook.

## Codex adapter

Facts observed with `codex-cli 0.166.0`. Fixtures: `test/fixtures/codex-run.jsonl`, `test/fixtures/codex-resume.jsonl`.

- **Launch:** `codex exec --json -C <workspace> --sandbox workspace-write [-m <model>] -- <task>`, with stdin ignored. Otherwise Codex waits for stdin. `--` ends the options, so a task that starts with "-" or is a subcommand name ("review") stays text.
- **Follow-up:** `codex exec resume --json -c sandbox_mode="workspace-write" [-m <model>] -- <threadId> <text>`, spawned with its cwd set to the workspace. `resume` accepts neither `-C` nor `--sandbox`, so the folder is the process's cwd and the sandbox a config override. It worked without `--ephemeral`.
- **Environment** (`buildEnv(base, agentId, keysEnv)`). A copy of the base environment (the runner's `env` option, `process.env` unless given, as for Claude Code) without Claude Code's session markers (`CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDE_AGENT_SDK*`), without the variables a running Codex sets for its commands (`CODEX_THREAD_ID`, `_SESSION_ID`, `_TOOL_CALL_ID`, `_SANDBOX`, `_SANDBOX_NETWORK_DISABLED`, `_PERMISSION_PROFILE`, and `CODEX_EXEC_SERVER_*`, `CODEX_NETWORK_PROXY_*`, `CODEX_SNAPSHOT_*`, `CODEX_SHELL_SNAPSHOT_*`), without `WORKBENCH_HOOK_URL`/`WORKBENCH_HOOK_TOKEN` (Codex has no hook; its commands must not reach the engine), and without the editor's variables and Workbench's own choice of programs (`VSCODE_*`, `ELECTRON_RUN_AS_NODE`, `GIT_EDITOR`, `WORKBENCH_CLAUDE_BIN`, `WORKBENCH_CODEX_BIN`, as for Claude Code), plus `WORKBENCH_AGENT_ID`, with node put on the PATH by the same rule (`withNodeOnPath`, imported from `../claude/args.mjs`). `CODEX_HOME`, `CODEX_API_KEY` and other sign-in and config variables stay. `test/live-fake-codex.test.mjs` runs the whole chain against `test/helpers/codex-fake.mjs`.
  - **The person's keys** (`keysEnv`) come after the scrub, by the Claude Code adapter's rules (`withKeys`; a name Codex's own scrub removes is left out too), and before `WORKBENCH_AGENT_ID`, which no key can replace. Every turn's process gets them.
- **Masking** (`mask`), as for Claude Code: each parsed line's strings before the parser reads them, the "not JSON" log line, and the stderr tail (4096 shown, 2048 more kept). So the failure reason, its log line and `agent.ended`'s error carry no stored key.
- **Events:**

  | Codex event | Normalized |
  |---|---|
  | `thread.started { thread_id }` | `agent.session` |
  | `turn.started` | `agent.turn start` |
  | `item.started` / `item.completed` with `item.type` `command_execution { command, exit_code }` | `activity start` / `end`, with `ok = exit_code === 0` |
  | `agent_message { text }` | remember as final text; `agent.says` |
  | `reasoning` | `thinking on` |
  | `file_change { changes }` | activity, kind edit |
  | `todo_list { items }` | `agent.plan` |
  | `web_search`, `mcp_tool_call` | activity |
  | `turn.completed { usage: { input_tokens, cached_input_tokens, output_tokens, reasoning_output_tokens } }` | `agent.usage mode:'add'` with `costUsd: null` (Codex reports no cost); `contextTokens = input_tokens`; then `agent.turn end { finalText }` |
  | `turn.failed`, `error` | `turn end { isError: true }` |

- **No permission asks.** Codex runs inside its own `workspace-write` sandbox.
- **Binary:** `codexBin(env)`, `WORKBENCH_CODEX_BIN` in the runner's base environment, else `codex`.

The adapter modules are `src/adapters/claude/runner.mjs`, `src/adapters/codex/runner.mjs` and `src/adapters/sim/simulator.mjs`. The simulator exports a `Simulator` class whose instance has `createRunner(opts)`.

## Engine (`src/core/engine.mjs`)

```js
export class Engine extends EventEmitter {
  constructor({ store, mode, repo, hook, defaultBudgetUsd, defaultModel, adapters, machines, deps, connect, log, options })
  // hook: { url, tokenFor(agentId) }  where the hook posts, and each agent's own hook token. Read at each launch;
  //        a live Claude Code runner gets { url, token: tokenFor(id) } (null when tokenFor is missing or fails, and
  //        Claude Code then refuses to start); every other runner gets hook: null.
  // adapters: { claude?, codex?, sim? }  (claude/codex: the runner modules; sim: a Simulator instance)
  // deps: { policy, commands, workspace, receipt, history? }  injected so the engine can be tested with fakes;
  //        bin/workbench.mjs passes the real modules. engine.mjs must not import them directly.
  // connect: the Connect service (src/core/connect.mjs), or null: envFor({ repoRoot, harness }) gives the keys an agent and
  //        the checks of its work get, mask(text) hides the stored keys, defaultAgent() says where new work goes. Null (and
  //        the demo): no keys, nothing hidden, new work goes to the first ready agent ("Keys, masking and the default agent")
  // options: { permissionTimeoutMs = 25 min, stuckSilenceMs = 4 min, tickMs = 1000, tidyTimeoutMs = 3 s, historyDir?, historyDebounceMs? } (tests shorten these)
  async start()                                   // demo: seed the simulator; live: read the repository and whether git knows the
                                                  //    person's name and email, check adapters, open the history; start the 1 s tick
  async shutdown()                                // -> { kept: [{ id, name, path, branch }] }  stop every runner and every running
                                                  //    check, and wait for them; resolve held hooks as deny; remove the agent
                                                  //    folders that hold nothing; `kept` lists the ones that hold work.
                                                  //    A launch under way finishes first, then a merge or throw-away under way
                                                  //    (see "Agent folders after Workbench stops")
  keptFolders()                                   // -> [{ id, name, path, branch }]  the agent folders still on disk, now
                                                  //    (synchronous: a forced exit lists them too; untidied ones included)
  killAllSync()                                   // on process exit: SIGTERM every agent's process group, SIGKILL every check's
  async startAgent({ task, harness, model, machineId, budgetUsd, name }) // -> AgentView  (no harness: the default agent; a
                                                  //    refusal for want of an agent is a plain error with .openConnect)
  async answer(agentId, { askId, answer })        // -> { ok, reply, openConnect? }  (openConnect: a typed key was refused)
  async say(agentId, text)                        // -> { ok, reply, openConnect? }
  async stop(agentId)                             // -> { ok, reply }

  async command(text, { focusId, confirmId, askId }) // -> { reply, confirm?: { id, sentence, detail, kind, yes?, no?, danger?, agentId? }, focusId?, review?, openConnect? }

                                                  //    openConnect: true asks the page to open Agents & keys
  setHarnesses(map)                               // -> boolean  live only: which agents can start, from Connect's 'agents' event
  async changes(agentId)                          // -> { ok: true, agentId, name, branch, into, live, diff } | { ok: false, reply }  read-only
  async gitGraph()                                // -> { ok: true, repo, commits, more, agents } | { ok: false, reply }  read-only

  async proposeDiscard(agentId, { state })        // -> { reply, confirm } | { ok: false, reply }  a card, never a throw-away by itself

  async setMachineAwake(machineId, awake)         // -> { ok, reply }
  snapshot()                                      // -> { mode, repo, harnesses, harnessInfo, connect?, agents, machines, spendTodayUsd, spendTodayEstimated, defaultBudgetUsd }
                                                  //    repo: { name, head, branch, dirty, identity } (null in the demo); identity: git knows the
                                                  //    person's name and email (true or false), null while Workbench cannot tell
                                                  //    harnesses: { claude, codex, sim } as plain booleans; harnessInfo: each harness's available()
                                                  //    answer ({ ok, version?, reason?, path?, from? }), or Connect's word for it (with loggedIn,
                                                  //    signedIn, how, ready); in live mode a Claude Code session line's version replaces version
                                                  //    connect (live, with Connect only): { ready, defaultAgent, agents: [{ id, name, ready }] }
                                                  //    agents include the earlier ones (`earlier: true`)
```

- **Launches always go through a confirm step** when they come from `command()`, whether typed or spoken. `startAgent` itself does not ask; the HTTP route that calls it is only used after a confirm.
- **So do stops and messages whose words did not name the agent** (`sure: false` from the parser: "stop the stuck one", "tell the flaky test keep going"). `command()` returns a confirm card ("Stop Flaky test?"; "Tell Flaky test “keep going”?"; for one agent, both carry the detail "Its task: “…”", since two agents can have the same name), and `confirm(id, true)` then stops or sends. Cancel replies "OK, I won’t stop it.", "OK, I won’t stop them." or "OK, I won’t send it.".
- **So do merges and throw-aways, always**, from a button or from words: `proposeMerge`, `proposeDiscard` and `command()` only ever return a card, and only `confirm(id, true)` acts (see "Source control in the engine").
- **A yes or no answers only the confirm on screen.** `confirmId` is the card the page shows. `ctx.pendingConfirm` is that confirm, or `{ id, gone: true }` when the id is unknown or has run out (so "yes" hears "That request is no longer waiting. Ask again if you still want it."), or null when no id comes. A confirm is never picked because it is the newest. With a card shown:
  - "do it", "yes", "cancel" and the like settle it, and so do the card's own words (while a stop card shows, "stop" and "stop it" mean yes; while a message card shows, "send it" does; "start it" and "launch it" are a yes only to a launch; "merge it" and "land it" to a merge card; a throw-away card takes only "throw it away", "discard it" or "do it", never a bare "yes": see "Card words" in "Natural-language commands");
  - a yes asked rather than said ("is that right?", "right?", "is that the right one", "that the right one", spoken without a "?") settles nothing, and keeps it like words not understood; so does a yes that is not enough for the card (a bare "yes" to a throw-away);
  - words not understood keep it: the reply is "I did not catch that. Say “do it” to <verb>, or “cancel”." with the card's verb (`confirmVerb`: "start it" or "start them", "stop it" or "stop them", "send it", "forget it", "merge it", "throw it away"; "go ahead" for any other kind), carries the same `confirm`, and is not sent as a notice;
  - any other command withdraws it, without a notice, and the reply carries no `confirm`. One exception: words about an agent's changes (`changes`) are read-only, so the card keeps waiting and the reply carries it (with `review`), as for words not understood ("show me the changes" before saying yes to a merge).
  Confirms the page lost (a reload, a second tab) can be answered only by their id and run out after 10 minutes. When a typed or spoken yes starts agents, the reply's `focusId` is the first one, so a second "yes" said out of habit finds nothing to answer.
- **Answers are bound to the ask on screen.** An ask is answered only by its own id, never as "whatever is showing now":
  - `answer(agentId, { askId })`: `askId` must be the agent's ask on screen or one of its held requests. Without it, an agent that has an ask is not answered ("Have a look at what Checkout fix is asking first."); an id that names something else is refused ("Checkout fix is asking something else now. Have a look, then answer again.", or "… is not waiting for that any more." when nothing is asked). Refusals are `{ ok: false, reply }` and leave the request waiting.
  - `command()`: the intents that answer (`allow`, `deny`, `answer`) need `askId`, and it must be the ask the parser read the words against (`intent.askId`); the same two refusals apply, with `focusId` set to the agent. When `confirmId` comes too, `askId` is not used: with a card on screen, no ask was. Commands that are not answers (stop, tell, status, start, sleep) act on what the words and `focusId` name, even when the ask on screen has changed since: "stop it" still stops the agent the person was looking at.
- **Answers:**
  - permission: from a button (`answer()`), exactly "Allow" or "Deny" (any case); anything else ("Yes", "OK", another ask's "Keep it working" or "Stop it") is refused with "Choose Allow or Deny." and the request stays held. Typed or spoken words reach it only through `command()`: a plain yes allows ("OK, Checkout fix can go ahead."); a no denies; a no with words denies and passes them on ("The person said no, and added: use the staging database"); a yes with conditions ("yes but only in the tests folder") is a no that passes on the whole reply ("The person did not allow this step as asked. They said: “…”", reply "OK, Checkout fix will not do it as asked. I passed on your words."). A yes asked rather than said ("is it okay?", "is this allowed?", "do you allow it", "yes?", "yes is that right", "you sure", "that okay", spoken without a "?") answers nothing: the reply is the request's status (below), and it stays held. An allow never carries words, and free text never allows;
  - question: any text (an option, or the person's own words) is sent with `runner.send(answer)` and clears the ask;
  - stuck: "Stop it" (or "stop") means `stop`, "Let it keep trying" clears the ask, and any other text is sent as a hint and clears it. The question about background work (`about: 'background'`) takes "It is done" (or "done"), "Keep waiting" (or "wait"), "Stop it", or a message (see Agent lifecycle, step 1);
  - done states (no ask, no `askId`): "Looks good" (or nothing, "lgtm", "thanks", "fine", "ok" and the like: `LOOKS_GOOD_RE`) leaves it as is: "Good. <Name> stays as it is."; "Not now" (those words alone: `NOT_NOW_RE`), the lid's quiet link on work that can be merged, leaves it as is too and sends it nothing, in words that are no approval: "OK. <Name>’s work stays on its branch for now." ("OK. <Name> stays as it is." when it has no branch); any other text is sent as a follow-up message.
  - `say()` is a message: it answers a question, but never settles a permission or a stuck ask (a held request stays held).
  - The demo follows the same rules: the simulator hears "Allow", "Deny" or the words of a no, and allows only on "Allow", and the person gets the same replies as in live mode ("OK, Checkout fix can go ahead.", "OK, Checkout fix will not do that."); a message to a seeded agent answers only a question; a stuck demo agent stops only on "Stop it" (or "stop").
- **Stopping a helper** (`stop()`, or "stop it" with the helper in the centre). In live mode a helper runs inside its agent's Claude Code process, so the engine asks the agent to stop it ("I asked Fix login redirect to stop its helper List repository files.") and, at once, says no to the helper's held requests and to every tool it asks for after that, even the ones the rules allow ("The person stopped this helper."). The helper's request leaves the centre and the helper goes back from `needs_ok` to `working` (it is not marked `stopped`): it ends when its agent reports it ended. A simulated helper, or one whose agent cannot be reached, is stopped by the engine itself.
- **Status of a held request** names the exact command, path or address: "Checkout fix wants to run a command: “npm run db:migrate -- --env test”. It needs your OK." Hidden characters become spaces, and a long one keeps its start and its end around "…" (`quotable` in narrate.mjs).
- **On process exit** (`SIGINT`, `SIGTERM`, `exit`), stop every runner and every running check (`killAllSync` also calls `receipt.killChecksSync()`). Orphaned agents keep spending; orphaned checks keep running with nothing left to time them out. After a clean shutdown the CLI prints the folders that hold an agent's work ("What the agents did stays on this computer, each in its own folder:"); after a forced exit, every folder still there (`keptFolders()`: "The agents’ folders are still on this computer:").
- **Spend** says "about" while part of it is Workbench's estimate: "You have spent about $0.62 today." Less than a cent is "under $0.01", estimated or not (`spentAmount` in `format.mjs`). A message an agent cannot take because its spending limit is used up gets the runner's own sentence as the reply.

**Keys, masking and the default agent (Connect).** With `connect` in live mode, the engine gives agents and checks the person's keys, hides those keys in everything it keeps, and sends new work to the default agent. Without it (the demo, or a Workbench whose Connect did not load), agents get no keys, nothing is masked, new work goes to the first ready agent, and the snapshot has no `connect`.

- **Agents.** `AGENT_HARNESSES` is every name in `HARNESS_NAMES` but `sim`, in order (`claude`, `codex`). `_checkHarnesses`, `_harnessFlags`, the default agent and "I don’t know that kind of agent. Choose Claude Code or Codex." are built from it, so a new kind of agent joins by its name in `HARNESS_NAMES`.
- **Keys** (`_keysFor(harness)`): `connect.envFor({ repoRoot: repoInfo.root, harness })`, checked again. Only variable names and string values without a NUL are kept, and never `WORKBENCH_*`, `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `NODE_OPTIONS`, `NODE_PATH`, `LD_*`, `DYLD_*`, `CLAUDE_CONFIG_DIR` or `CLAUDE_CODE_TMPDIR`, whatever the key store allows. They go as `keysEnv` to a launch and to a continued earlier agent (`_runnerKeys`), and to `runChecks` for the checks of that agent's work, whose `env` still carries `WORKBENCH_AGENT_ID`, which no key replaces. When the keys cannot be read, the agent starts without them and a warning is logged (it holds no value).
- **Masking** (`connect.mask`). The engine passes `mask` to runners and to `runChecks`.
  - Events: `ingest()` masks each event first, and `_apply()` masks every event the engine makes itself, so the store, the event log, history, the page and `'event'` listeners never hold a stored key. Every string of 8 or more characters, at any depth, goes through the mask, except fields read back as names of things (`MASK_SKIP`: `kind`, `agentId`, `parentId`, `rootId`, `id`, `askId`, `toolUseId`, `taskId`, `sessionId`, `harness`, `model`, `machineId`, `workspace`, `branch`, `from`, `base`, `since`, `head`, `path`, `state`, `type`, `phase`, `toolKind`, `outcome`, `mode`, `ts`). Both copy; the event they were given is never changed.
  - A held permission request: the policy judges the raw input. When the input holds a stored key, the ask's detail is described from a masked copy of it, so a key the description's clip cuts in two is still hidden.
  - Not masked: `changes()` and `gitGraph()`. A reviewer must see a key an agent wrote into a file before merging it.
  - A mask that throws: the text is kept as it is, and one warning is logged, never with the text.
- **Typed keys.** `command(text)` checks `looksLikeSecret(text).secret` (`src/shared/secretshape.mjs`) before it parses anything. The reply is `{ reply: 'That looks like a key, so it was not sent. Keys go in Agents & keys, where they are kept safe.', openConnect: true }`, with the card on screen when one is shown (it keeps waiting); without a card the reply is posted as a notice. Nothing else is kept or logged. `say()` and `answer()` refuse the same way (`{ ok: false, reply, openConnect: true }`), and `startAgent` throws the same sentence as a plain error. This holds with or without Connect, in the demo too.
- **The default agent** (`_defaultHarness()`).
  - Live, with Connect: `connect.defaultAgent()` when the engine can start that agent (`_canRun`); null when it answers null; anything else (an agent with no adapter, an unknown name, `undefined`, a throw) falls back to the engine's own rule.
  - The engine's own rule, used without Connect too: the first agent of `AGENT_HARNESSES` that is `_ready`: `_canRun`, and its info is not known to be signed out (`ready === false`, `loggedIn === false` or `signedIn === 'no'`). In the demo every harness can run, so it is Claude Code, which the simulator plays.
  - It applies to a task whose words name no agent (`_proposeStart`) and to a launch with no harness (`startAgent`). Naming an agent in the words still wins.
  - No agent ready: `_proposeStart` replies "No coding agent is ready yet. Connect one in Agents & keys." with `openConnect: true`, and `startAgent` throws that sentence as a plain error with `.openConnect`. A start with no task gets this reply too when no agent is ready, and "What should the agent work on?" when one is.
  - A named agent that cannot run, in live mode: `_proposeStart` replies "<Name> is not available on this computer. Connect it in Agents & keys." with `openConnect: true`; `startAgent` throws "<Name> is not available on this computer." with `.openConnect`. The yes to a launch card whose agent went away meanwhile carries `openConnect: true`.
- **`setHarnesses(map)`**, from Connect's `agents` event (`{ claude: info, codex: info }`; the CLI wires it). Live only; false in the demo or for anything that is not an object.
  - Each agent the map names gets its info as `harnessInfo[h]`, with only `ok`, `version`, `reason`, `path`, `from`, `loggedIn`, `signedIn`, `how`, `ready` and `simulated` kept (`INFO_FIELDS`), so nothing else (an account's email) reaches the snapshot. `null` reads "<Name> was not found on this computer.".
  - Agents already running, and agents the map leaves out, are untouched. Earlier agents of an agent whose `ok` flipped are told again whether they can continue (`markContinue`).
  - `_checkHarnesses()` at start asks only the adapters Connect has said nothing of, and drops an answer for one Connect spoke of meanwhile, so Connect's word is never replaced by an older one.
  - Only an agent whose adapter the engine was given can start, whatever the map says.
- **`snapshot().connect`** is `{ ready: defaultAgent !== null, defaultAgent, agents: AGENT_HARNESSES.map(h => ({ id, name, ready })) }`, where an agent's `ready` is `ready && (h === defaultAgent || _ready(h))`. It is worked out afresh at each snapshot, by the rule a start uses, so the page's light and a start never disagree. The server sends a fresh snapshot on Connect's `agents` and `changed` events (see "HTTP server").
- **Words.** `{ kind: 'help' }` gets the parser's `HELP_REPLY` when `deps.commands` exports one, else the same words kept in the engine: "Say what to work on, like “fix the login bug”. Or ask “what needs me”, or “stop everything”. Agents & keys sets up agents." `{ kind: 'connect' }` gets `{ reply: 'Opening Agents & keys.', openConnect: true }`. `{ kind: 'start', tasks: [], task: null }` asks what to work on (above). Words not caught keep "I did not catch that. Try …".

**Source control in the engine.** The engine reads the person's repository, keeps where each root's work is, shows its changes and the commit graph, and merges or throws away its work, always after a card. Each git function it uses is checked with `typeof` first, so an older workspace module gives a plain refusal instead of a crash. What git itself does is in "Source control".

- **The person's repository.** Live mode keeps `repoInfo` (`prepareRepo()`) and whether git knows the person's name and email (`gitIdentity`). Both are read at `start()`, then afresh (`_freshRepo`) on the 15 s tick, before every merge card and launch, after every merge, and for the git screen. Reads can overlap: one that began before the last one kept is dropped, so the page never steps back to a head the branch has left. `_repoView()` is `{ name, head, branch, dirty, identity }`. `identity` is true or false once known, and null while Workbench cannot tell (before `start()`, or a workspace module without `gitIdentity`); only `false` refuses a merge card, and git checks again at yes. When the view changes, the store emits `repo`. It is also `snapshot().repo` and the command context's `repo`.
- **Where a root's work is.** A live launch reads the person's branch afresh, makes the folder, and records `run.workspace = { path, branch, base, since, from }`. `base` is the commit it started from; `since` is where its unmerged work starts (`base` until its first merge, then the work commit that merge joined in); `from` is the person's branch at launch (null when detached). The batch that creates the view carries `agent.work { branch, from, folder: true, merged: null, problem: null, thrownAway: null }`. The receipt's `diffStats` and the shutdown tidy count from `since`. An earlier agent's places are its history record's `workspace`.
- **`changes(agentId)`** (GET /api/agents/:id/changes): what a root changed that is not merged yet, for the git screen's diff. Read-only: it takes no lock, posts no notice and works in any state; a helper's id gives its agent's. It answers `{ ok: true, agentId, name, branch, into, live, diff }`: `diff` is `workDiff({ repoRoot, path, since })`, `into` the person's branch, and `live` is true while the agent is at work (an active state, its receipt being built, or being picked up), so the page says its work may still change. Refusals: "I can’t find that agent.", "Workbench is shutting down.", "<Name>’s work was thrown away, so there is nothing to show.", "Its folder is gone, so there is nothing to show." (the view's `work.folder` becomes false), "Workbench does not know which commit <Name> started from, so it cannot show its changes.", "Workbench cannot show changes right now.", git's own plain sentence named after the agent (see below), else "Workbench could not read <Name>’s changes.". In the demo the simulator answers, or "This is the demo, so there are no real changes to show.".
- **`gitGraph()`** (GET /api/git): the repository read afresh, then `workspace.gitGraph({ repoRoot })`, answered as `{ ok: true, repo, commits, more, agents }`. `repo` is `_repoView()` with the head and branch the graph was read at, so the commits and the top band agree. `agents` lists every root with a branch, this run's and earlier ones, never a thrown-away one: `{ id, name, state, earlier, harness, branch, from, base, since, files, work }`. When git refuses, its own plain sentence is the reply ("The repository at … has no commits yet."); otherwise "Workbench could not read the git history.", or "Workbench cannot show the git history right now." without the function. In the demo, the simulator's graph, or "This is the demo, so there is no git history to show.". Neither `changes()` nor `gitGraph()` waits for the git lock: one read during a merge may show the work from just before it or just after.

**Merge.** `proposeMerge(agentId, { state })` (POST /api/agents/:id/merge, and the words "merge it") never merges: it answers with a card, or with a refusal it also posts as a notice. `state` is the state the page drew its button for (null: not checked). Refusals, in this order:

1. The demo without the simulator's `merge`: "This is the demo, so nothing is really merged."
2. "I can’t find that agent.", "Workbench is shutting down.", and for a helper "Helpers work in their agent’s folder. Merge the agent instead."
3. A busy agent (see "One git job at a time"): "<Name> is being merged now." or "<Name>’s work is being thrown away now."
4. An agent at work (an active state, its receipt being built, or being picked up): "<Name> is still working. Merge it when it is done."
5. Another state than `state`: "That changed. Have another look."
6. "<Name>’s work was thrown away, so there is nothing to merge."; no folder (none recorded, removed, or not on disk, and then `work.folder` becomes false): "Its folder is gone, so there is nothing to merge."; no `since`: "Workbench does not know which commit <Name> started from, so it cannot merge its work."
7. A workspace module without `snapshotWork` or `mergeWork`: "Workbench cannot merge work right now."; a repository that cannot be read: "Workbench could not read your folder, so it cannot merge right now."
8. Not on a branch: "Your folder is not on a branch, so there is nowhere to merge it."; words that named another branch than the one the folder is on: "Workbench merges into the branch your folder is on, which is <branch>. Switch to <into> first to merge there."; `identity` false: "Git does not know your name and email yet, so Workbench cannot make the merge commit. Set user.name and user.email with git config, then try again."
9. `snapshotWork` fails: "Its folder is gone, so there is nothing to merge." (its folder is gone), git's own plain sentence named after the agent, or "Workbench could not read <Name>’s work, so it cannot be merged right now.". Steps 2 to 6 are checked again once git has read: the agent may have moved on meanwhile.
10. Nothing to merge: "<Name>’s work is already in <branch>." when it was merged before, or when merging would bring in no file (merged by hand, say); "<Name> changed nothing, so there is nothing to merge." when it was never merged. Either way `work.problem` clears.

The card is `{ kind: 'merge', sentence: 'Merge <Name> into <branch>?', detail, yes: 'Merge', no: 'Cancel', danger: false }`, kept with `{ agentId, state, expect: { workId, into, intoHead } }`. Its detail starts with the counts of what the merge brings in (`snapshotWork`'s files), then says what applies, in this order:

- "3 files, +40 −2. Its work becomes a commit on its branch, joined into main by a merge commit."
- "A check failed: unit tests." or "2 checks failed: unit tests and lint."; when its checks did not pass, "Nothing checked its work."
- "It broke a rule you set: Do not touch migrations/." or "It broke 2 rules you set: … and …": the rules of `workbench.json` from the commit it started from, checked again against the files it would merge.
- "It changes workbench.json, which sets the checks for later agents." (the top-level file only), "It changes .claude/, which holds Claude Code’s settings for this repository." (any `.claude` folder) and "It changes .mcp.json, which can give Claude Code new tools here."
- "2 files stay out: hidden by a .gitignore." ("1 file stays out: …"), and "1 folder stays out: it is a git repository of its own." or "2 folders stay out: each is a git repository of its own."
- "Your 2 uncommitted changes stay as they are." ("Your 1 uncommitted change stays as it is.")

`confirm(id, true)` on a merge card checks every refusal again, the card's state included, then marks the agent busy (`merge`) and queues the job on the engine-wide git chain. The job checks again, then quiets the agent: it closes its idle process (`_closeIdle`, which marks it stopped, so a turn that process starts by itself counts for nothing) and waits for stopped checks to end (`run.checksDone`). A process still alive: "Workbench could not pause <Name>, so nothing was merged.". After one more check it calls `mergeWork({ repoRoot, path, branch, since, expect: { workId, into, intoHead }, message: { subject, body, name }, agentId, harness })`, and reads the repository again whatever the outcome. `subject` is the first sentence of the task's first non-empty line (a sentence ends at ".", "!" or "?" followed by a space and a capital, a digit, a quote or a parenthesis, or at the end), without hidden and direction-changing characters, a closing full stop dropped, cut at a word boundary to at most 72 characters, its first letter capitalised; "Work by <Name>" when nothing is left. `body` is the agent's `says` on one line of at most 2000 characters, or nothing when it starts like a git trailer ("Key:"). `name` is the agent's name.

- **Merged:** one batch of `agent.work` (`merged: { into, merge, at, files, adds, dels }`, `problem: null`) and `agent.files { changed: 0, adds: 0, dels: 0, list: [] }`: nothing is left unmerged. `run.workspace.since` becomes the work commit; an earlier agent's record is rebuilt with that `since`, and the agent joins the shutdown tidy. The agent's other merge and throw-away cards are withdrawn (a yes to one hears "That request is no longer waiting. Ask again if you still want it."), and the history is saved at once. Reply: "Merged <Name> into <branch>.", with `focusId`.
- **Not merged:** the reply is the sentence for git's `why` (below), with `focusId`. `conflict`, `blocked`, `ancestry`, `moved`, `identity`, `detached`, `busy` and `git` keep `work.problem = { why, sentence, paths, into, at }` (at most 50 paths); `gone` sets `work.folder` false; `nothing` clears `problem`; `changed` and `git-old` leave it as it was. A `moved` for an agent whose work is merged, whose files are known and of which nothing is unmerged is no problem (its own merge went in after the card was drawn): the reply is "<Name>’s work is already in <into>.". A `mergeWork` that throws: "Something went wrong during the merge. Have a look at your folder before you try again."

The sentences by `why` (`mergeSentence`; `<into>` is the branch on the card):

| `why` | Reply |
|---|---|
| `detached` | "Your folder is not on a branch, so there is nowhere to merge it." |
| `busy` | "Your folder is in the middle of a merge or rebase. Finish that first." |
| `identity` | "Git does not know your name and email yet, so Workbench cannot make the merge commit. Set user.name and user.email with git config, then try again." |
| `git-old` | "Workbench needs git 2.38 or newer to merge." |
| `changed` | "<Name>’s work changed since you looked. Have another look." |
| `moved` | "<into> changed since you looked. Have another look." |
| `nothing` | "<Name>’s work is already in <into>." |
| `ancestry` | "<Name> started from a commit that is no longer in <into>, so merging it would bring in other work." |
| `conflict` | "<Name>’s work does not merge cleanly into <into>." |
| `blocked` | "Your own changes are in the way: a.js, b.js and c.js. Commit or put them aside, then merge again." (three paths at most, then "and 2 more") |
| `gone` | "Its folder is gone, so there is nothing to merge." |
| `git` | "Git could not finish the merge. Nothing in your folder changed." |

For `git`, `busy` and `changed`, the git module's own plain sentence is used instead whenever `mergeWork` gives one (it always does): only it knows what happened, such as another git command holding the index, unresolved conflicts in the person's folder, a merge that may have stopped part-way, what merging would bring in being no longer what the card showed, or the agent's folder now being on another branch. A sentence of the git functions that begins "Its …" is named as "<Name>’s …", and "It …" as "<Name> …" (`aboutAgent`).

**Throw away.** `proposeDiscard(agentId, { state })` (POST /api/agents/:id/discard, and the words "throw it away") answers with a card, or with a refusal it also posts as a notice. An agent at work is not refused: it is stopped first, and the card says so. Refusals, in this order:

1. The demo without the simulator's `discard`: "This is the demo, so nothing is really thrown away."
2. "I can’t find that agent.", "Workbench is shutting down.", and for a helper "Helpers work in their agent’s folder. Throw away the agent’s work instead."
3. A busy agent (the busy sentence); one being picked up: "<Name> is already being picked up."; another state than `state`: "That changed. Have another look."; "<Name>’s work was already thrown away."
4. No folder recorded, or removed: "Its folder is gone, so there is nothing to throw away."; no branch: "Workbench does not know <Name>’s branch, so it cannot throw its work away." (its folder is there), else the same gone sentence; its folder there but no `since`: "Workbench does not know which commit <Name> started from, so it cannot throw its work away."
5. A workspace module without `snapshotWork` or `discardWork`: "Workbench cannot throw away work right now."; `snapshotWork` fails: "Its folder is gone, so there is nothing to throw away.", git's own plain sentence named after the agent, or "Workbench could not read <Name>’s work, so nothing was thrown away." (steps 2 to 4 are checked again once git has read).

The card is `{ kind: 'discard', sentence: 'Throw away <Name>’s work?', detail, yes: 'Throw it away', no: 'Keep it', danger: true }`, kept with `{ agentId, state, active, expect: { workId } }`. Its detail: "Its folder and its branch workbench/search-cleanup-a1b2c3 are deleted, with 3 changed files. Workbench keeps a hidden copy in git." ("with no changed files"; the count is `snapshotWork`'s files); then, when files stay out of the hidden copy, "The hidden copy leaves out 2 files that a .gitignore hides and 1 folder that is a git repository of its own."; then, for an agent at work (`active`), "It is still working: it will be stopped first.". A root whose folder is gone but whose branch is still there can have its branch thrown away: the detail is "Its folder is already gone. Its branch <branch> is deleted. Workbench keeps a hidden copy in git.", and the card is kept with `folderGone: true` and `expect: { workId: null }`.

`confirm(id, true)` on a throw-away card checks every refusal again. The card's state is compared only for a card made at rest, and such a card for an agent that went back to work answers "That changed. Have another look.". The agent is marked busy (`discard`) and the job queued on the git chain. The job checks again, then stops an agent at work (`_stopRoot(v, 'Stopped by you')`, which says no to its held requests and its helpers') or closes an idle one (`_closeIdle`), and waits for stopped checks to end. A process still alive: "Workbench could not stop <Name>, so its work was not thrown away.". Whether its folder is there must still be what the card said, or "That changed. Have another look.". A card made while it worked reads the work again once it has stopped and binds to that: what it holds then is what goes into the hidden copy. Then `discardWork({ repoRoot, path, branch, since, expect: { workId }, agentId })`.

- **Thrown away:** `run.folderRemoved = true` (out of `keptFolders()` and the tidy); `agent.work` with `branch: null, folder: false, problem: null, thrownAway: { at, saved }`; the agent's other merge and throw-away cards are withdrawn; an earlier agent's record keeps no folder, and it cannot continue ("Its work was thrown away, so it cannot continue."); the history is saved at once. Reply: "Threw away <Name>’s work. Its folder and branch are gone." The agent stays on the board and in the history, marked thrown away. A message to it is refused ("<Name> cannot continue. Its work was thrown away, so it cannot continue."), and so are its changes and a merge.
- **Not thrown away:** git's own plain sentence named after the agent (it always gives one); without one, "<Name>’s work changed since you looked. Have another look.", "Its folder and its branch are already gone." or "Git could not throw away <Name>’s work. Nothing was deleted.". A `gone` marks the work gone: `folder: false` and `branch: null`, this run's agent leaves the kept folders, and an earlier agent's record keeps no folder ("Its folder is gone, so it cannot continue."). A `discardWork` that throws: "Something went wrong while throwing away <Name>’s work. The details are in the log."

A message to a root of this run whose folder Workbench removed is refused: "<Name> cannot continue. Its folder is gone, so it cannot continue.".

**`work.problem` clears** on the next merge that goes through, on any turn start, on a message the agent takes (Continue of an earlier agent too), on a throw-away, and when nothing is left to merge (a proposal that finds nothing, or git's `nothing` at yes). An earlier agent's saved record is rewritten with it cleared, so it does not come back at the next start.

**One git job at a time.** Every merge and throw-away runs as one job on an engine-wide promise chain (`_gitJob`), one after the other, whatever became of the one before: each touches the same repository, and a merge the person's own folder. `_busy` maps a root to `merge` or `discard` while its job waits or runs. While a root is busy, these refuse with the busy sentence ("<Name> is being merged now.", "<Name>’s work is being thrown away now."): a message or an answer (`_sendTo`, so Continue too), continuing an earlier agent, stopping it or one of its helpers, forgetting it, and another merge or throw-away proposal. "Stop everything" leaves it to its job (a throw-away stops it itself). `_gitWork` holds the jobs waiting or running: `shutdown()` waits for them after the launches under way and before it stops the runners, and no job starts once shutdown began (each checks before it is queued and again inside). The tidy skips busy roots. Every git command of a job runs in a process group of its own, so a Ctrl-C in the terminal reaches only Workbench, which waits (see "Source control"). In the demo the busy flag is held but nothing is queued: no git runs. Known limit: there is no lock across processes. Another Workbench on the same repository may be running an agent this one shows as earlier, and merging or throwing it away here would act on a live agent's folder (continuing it has the same hazard).

**Confirm kinds.** `confirm()` handles each kind by name: `forget`, `stop` and `say`, `merge`, `discard`, and `start` only with its `tasks`. Any other kind answers "That request is no longer waiting. Ask again if you still want it." and launches nothing. Cancel replies: "OK, I won’t merge it." and "OK, I won’t throw it away.", besides "OK, I won’t start it." ("… start them."), "OK, I won’t stop it." ("… stop them."), "OK, I won’t send it." and "OK, I won’t forget it." ("… forget them."). Every reply that shows a card carries it as `{ id, sentence, detail, kind, yes?, no?, danger?, agentId? }` (`_card`): `kind` is always there (`start`, `stop`, `say`, `forget`, `merge` or `discard`), `yes` and `no` are the buttons' own words when they are not "Do it" and "Cancel", and a merge or throw-away card names the agent it is about (`agentId`, on those two kinds only, the demo's cards too), so the git screen can show it in that agent's detail. The parser hears the card shown as `{ id, kind, sentence, detail, tasks, agentIds, agentId?, yes?, no?, danger? }` (`_shownConfirm`).

**Words** (`command()`). `changes` replies "Here is what <Name> changed." with `review: <the root's id>` and `focusId`, so the page opens the git screen on that agent, or with the refusals of `changes` (in the demo without the simulator's `changes`, "This is the demo, so there are no real changes to show."). `merge` (with the words' `into`) and `discard` always give a card, or a refusal with `focusId`. With no agent (two roots share the name, or nothing is focused): "Which one do you mean? Pick it on the board, then ask again.". A helper's id means its root.

**Status words.** For an ended or earlier root, `_describe` adds what became of its work: " Its work was thrown away.", " The last merge did not go through: <sentence>", " Its work was merged into main." (only while nothing new is unmerged, as the page's card says it), " Its earlier work was merged into main, but 1 changed file is not merged yet." ("… 2 changed files are …"), or " Its earlier work was merged into main. Anything it changed since is not merged yet." when its files are not known. "What needs me" leaves out a `checks_failed` root whose work is settled (merged with nothing new since, or thrown away), as the page's `needsPerson` does.

**The demo.** The simulator's optional git methods stand in for git, and are called only when they are there (see "Simulator and machines"). A card the simulator proposes gets the engine's own id and sentence, with the simulator's detail and `expect`; without `proposeMerge` or `proposeDiscard`, the engine makes its own demo card, whose detail ends "This is the demo, so nothing is really merged." (or "… thrown away."). Replies are the simulator's own, else "Merged <Name> into <into>. This is the demo: nothing was really merged." or "Threw away <Name>’s work. This is the demo: nothing was really thrown away.". The simulator records an outcome with its own `agent.work` and `agent.files`; when they did not land (events of an agent the engine stopped are filtered), the engine records it. A refusal whose `why` a real merge keeps is kept as `problem`; any other is only passed on. The page offers Merge and Throw it away only in live mode, so in the demo they are reached by words alone ("merge invoice export").

## Natural-language commands (`src/core/commands.mjs`)

`parseCommand(text, ctx)` returns an intent. `ctx` is `{ agents: AgentView[], focusId, machines: Machine[], harnesses: { claude, codex, sim }, pendingConfirm, repo }`: `pendingConfirm.kind` picks the card's own words (a card without a kind is a launch), and `repo` is the person's repository (`{ name, head, branch, dirty, identity }`, or null), of which the parser reads `repo.branch`. Rule-based, no model calls.

| Intent | Example wording |
|---|---|

The engine asks "What should the agent work on?". It wins over a waiting question only with a start verb and an agent named, or as "new agent": "start", "start one", "use codex", "ask claude" and "have codex" are the answer then. "start the agent" (one that exists), "codex" and "agent" alone stay `unknown` |

| `{ kind: 'stop', agentIds, sure? }` / `{ kind: 'stop_all' }` | "stop the flaky test", "stop the flaky test immediately" / "stop everything", "pause everything". A launch phrase after the verb is work: "stop an agent to fix the login" is a `task` with the whole sentence (see "Launch phrases") |

| `{ kind: 'changes', agentId }` | "what did search cleanup change"; "what changed", "what's changed", "what has it changed", "which files changed", "show me what changed" (the focused agent); "show me the changes", "show search cleanup's changes", "show me what invoice export changed", "what are its changes", "what changed in invoice export", "let me see the diff", "diff it", "diff invoice export". Read-only: the engine answers at once, and the reply carries `review`. "show …" needs a word for the work (changes, change, diff, edits, work, commits, branch): "show search cleanup" stays a `status`, "show the error on the login page" work. A question ("what did … change") may find the agent by its task words or by part of its name, as status questions do |
| `{ kind: 'merge', agentId, into? }` | "merge search cleanup", "merge it", "land it", "merge" (bare: the focused agent), "bring its changes in", "bring in its changes", "merge the changes from search cleanup", with an optional target at the end: "into main", "onto master", "to the main branch", "into my branch", "here", or the person's current branch by name (`ctx.repo.branch`: "into feature/login-v2", "into the feature/login-v2 branch"). `into` is "main", "master" or the current branch as named, and is left out for "my branch", "mine", "here", "my repo" and the like. Any other target keeps the old meaning: "merge it into develop" is work (unless the person is on develop). Always a merge card |
| `{ kind: 'discard', agentId }` | "throw away search cleanup's changes", "discard it", "throw it away", "throw it out", "throw out its work", "scrap it", "trash it". It needs an object: "discard" alone is nothing, and "scrap that" and "trash this" mean never mind (`unknown`). Always a throw-away card |
| `{ kind: 'spend' }` | "how much have I spent today" |
| `{ kind: 'sleep', machineIds }`, `{ kind: 'wake', machineIds }`, `{ kind: 'sleep_idle' }` | "sleep cloud 2", "wake cloud 2", "sleep idle machines": only when every word is about machines ("turn off the laptop screen saver" is work) |
| `{ kind: 'confirm', go }` | "do it", "yes", "cancel", "never mind", "make it so" (only when `pendingConfirm` is set: a confirm card is on screen), and each card's own words (see "Card words" below): "stop it" to a stop card, "send it" to a message card, "merge it" to a merge card, "throw it away" to a throw-away card; "start it" and "launch it" are a yes only to a launch. A yes asked rather than said ("is that right?", "right?", "is that the right one", "merge it is that right", "discard it?") and a yes that is not enough for the card (a bare "yes" to a throw-away) are `unknown`, so the card stays |
| `{ kind: 'unknown', text }` | anything else |

Agent references resolve by fuzzy word overlap with `name` and `task`. "it" and "this one" resolve to `focusId`. A launch's `harness` is the agent the words named ("claude", "claude code", "codex", "code x", and the mishearings), or `null` when they named none; "codex" anywhere in the clause picks Codex. Nothing in the parser names `'claude'` as a default: the engine gives a `null` harness to the person's default agent (see "Keys, masking and the default agent"). "cloud" picks `machine: 'cloud'`.

Help and connect are matched first, right after stop-all and before every other matcher, because they take only their own whole words: otherwise "open agents and keys" would launch an agent on "keys", and "connect github" would be work.

A stop or a message acts at once only when the words **name** the agent: its id, "it" for the focused agent, or two or more words of its name (all of a one-word name) and nothing else, with no other running agent's name having all of them (a helper does not count against its root). A message also needs a clear break before the text ("tell search cleanup **to** …"). Words of how soon ("immediately", "right away", "at once") are not part of the reference. An agent found by its task or state words, or by one loose word, gets `sure: false`, and the engine asks first. Words left over beside an agent's words mean work, not a stop: a `task` ("stop the flaky test from timing out"). Words that match no agent at all are work too: a `task` with the whole sentence, so the person gets the launch confirm ("Start Claude on “stop the flaky test from timing out”?", with Claude Code the default agent). Only a bare "stop", or "stop it" and the like with nothing to refer to, give a stop with no agent, and the engine says it could not tell which one. While a question waits, a stop that does not name an agent is the answer.

Changes, merge and throw-away are matched after stop, forget and continue, and before status, tell and start: "what did search cleanup change" and "show search cleanup's changes" were status questions, and still are when they name no agent.

**Merge, throw-away and changes name their agent** (`namedRoot`, `workRef`). The words must name a root:

- its id (a helper's id stands for its root);
- a pronoun for the focused root ("it", "this one", "that agent"; a helper in the centre stands for its root);
- a phrase for the focused root's work ("its changes", "the diff", "the branch", "all of its work");
- or words of a root's name and nothing else, two or more of them (all of a one-word name), that no other root's name also has. Ended and earlier roots count. A word heard as two counts ("the check out fix" for Checkout fix), and hyphenated words split.

When several roots' names have all the words, the one whose whole name they are is named ("merge search cleanup" names Search cleanup beside Search cleanup v2); two roots with that same whole name give `agentId: null`, and the engine asks which one. Words that several names share and that are none's whole name name no agent and keep their old meaning: "merge the config files", beside Update config files and Split config files per, is work. Task words, state words, a helper's name and work words alone ("the changes", even beside an agent called "Changes") never name a root here. A name said alone that is exactly an agent's whole name ("merge command" for the agent Merge command, "diff viewer") keeps its old meaning. Words left over that are neither a work word nor a target keep the old meaning: "merge the two config files", "merge branch main into feature" and "merge invoice export and help pages" (one agent at a time) are work; "discard unused imports", "throw away the old logs", "throw an error when …" and "land the plane" are `unknown`. "bring" means a merge only with "in" or "over" and a work word or "it": "bring invoice export in" is work. With nothing focused, a pronoun, a work phrase or a bare "merge" gives `agentId: null` ("merge the changes", "what changed"), and the engine asks which one.

**Strength.** An id or the whole name is strong: it wins over a waiting question or stuck ask ("merge search cleanup" while a question waits proposes the merge). Part of the one root's name ("the unused imports" for Remove unused imports) names it, but keeps its old meaning while a question, a stuck ask or a permission waits from the focused agent or its one waiting helper (it is the answer, or the permission's reply); on a card, or with nothing waiting, it acts like a name. A pronoun, a work phrase and a bare "merge" or "land" are weak: while anything else is on screen (a card, or a question, stuck ask or permission of the focused agent or its one waiting helper), they keep their old meaning. So "merge it" while a question waits is the answer, at a permission it is `unknown`, and "sure, land it" and "yes merge it" at a permission stay a conditional no. Stop and tell keep their own rule (above). A `changes` question that finds the agent by its task words is read-only, and strong when it is sure.

**Where to merge.** A target at the end ("into", "onto", "to", "in" or "on", then "main", "master", "the main branch", "my branch", "mine", "here", "my repo", "the repository" and the like, or the current branch by name, also "the <branch> branch") is taken off before the agent is read; so is a last "here" ("merge it here"). "in to main", "on to main" and "over to main" (a particle before the target) mean "into main". The particle is dropped only when the words with it name nothing, so a name that ends in "over" keeps its word; "merge in to main" merges the focused agent. On a branch whose name is a word ("wizard"), "merge it into the wizard" and "merge help pages into wizard" are merges into wizard; "merge main into wizard" stays work, since no agent's name or "it" comes before the target.

**Card words** (`confirmReply`), while a card is on screen:

- "start it" and "launch it" (and "start" or "launch" anywhere in a yes) are a yes only to a launch card. On any other card they keep the card (`unknown`), and so does "start it is that right".
- Stop card: "stop" and "stop it" are a yes; "don't stop it" is a no. Message card: "send it" is a yes; "don't send it" is a no.
- Merge card. Yes: "merge", "merge it", "land it", "bring it in", "merge its changes", "yes merge it", "sure, land it", "merge it into my branch" (or "here"), "merge both", "merge them all", and the plain yes words ("yes", "do it", "okay", "make it so"). A branch named ("merge it into main") keeps the card, even when it is the card's own branch: "do it" agrees with what the card says. No: "don't merge it", "do not merge it", "never merge it", "not on main", "cancel".
- Throw-away card. Yes, and only these: the button; "throw it away" (also "throw away", "throw it out", "throw away its work", "throw it all away"); "discard it" (also "discard", "discard the changes", "discard all changes"); "do it" or "do that" (also "yes do it", "just do it", "please do it"). A bare "yes", "okay", "sure", "go ahead", "confirm", "sounds good" or "make it so", a "do" or "throw" cut short ("do", "do so", "sure do", "yes do", "you do", "throw", "throw it"), and "scrap it", "trash it" or "scrap that" keep the card (`unknown`), and never reach a request behind it. No: "keep it", "keep its work" (the Keep it button, said), "don't throw it away", "do not discard it", "cancel", "no".
- Forget card: only the plain yes words. "forget it" is a no on every card (never mind).
- A yes asked rather than said ("merge it is that right", "discard it?", "you sure") keeps any card.
- Other words on a card: a whole name is another command, and the engine withdraws the card; weak forms keep it (`unknown`). If a merge or throw-away card sits over a permission or a question in the context, the card's own words answer the card first (the page sends no `focusId` with a card).

**Review words on a card** (`cardReview`). While a merge or throw-away card is shown, review words that mean "it" show the work of that card's agent (`{ kind: 'changes', agentId: pendingConfirm.agentId }`, strong), and never start anything: "show me the changes", "show me the diff", "show me its changes", "open the diff", "look at the changes", "let me see the changes", "pull up the diff", "what changed", "what did it change", "which files changed", "diff it", "diff". On such a card only, "review", "check", "check out", "read", "read through", "inspect", "examine", "view", "go over", "go through", "look over" and "look through" (with or without "let me") and then the changes, the diff or its work do the same; so do review words followed by when ("first", "again", "real quick", "quickly", "one more time", "for a second", "so far", or a "before …" clause such as "before I merge it"). Review words about the work that are still not understood ("show me the changes to the login page"), and any review words on a card that names no agent, keep the card (`unknown`), never a launch. Other cards, and no card, keep the old meanings ("review the changes" with no card is work).

**Launch phrases.** A launchable noun (a harness, "a", "an" or "new" agent, "someone") followed by "to", "that", "which", "who", "for", "on" or "and" starts new work and never names an agent to stop, forget, merge or throw away: "stop an agent to fix the login" is a `task` with the whole sentence, so the start card asks "Start Claude on “stop an agent to fix the login”?" (with Claude Code the default agent); "forget an agent to fix the login" is `unknown`; "bring in an agent to fix the login" stays a launch. While a question waits, they are the answer.

**`describeIntent`** words these kinds too: "Show what <Name> changed?" ("Show what an agent changed? It is not clear which one."), "Merge <Name> into <into>?" ("your branch" when there is no `into`, `into` cut at 60 characters; "Merge an agent? It is not clear which one."), and "Throw away <Name>’s work?" ("Throw away an agent’s work? It is not clear which one."). The engine words its own merge and throw-away cards. A start with no harness reads "Start an agent on “…”?" ("Start two agents on “…”?"; a mix reads "Start an agent on “the parser” and Codex on “the docs”?"), and a `task` intent reads the same way; the engine fills in the default agent before it asks for a card's sentence, so cards still name Claude or Codex. `help` reads "Show what you can say?" and `connect` "Open Agents & keys?".

## Permission policy (`src/core/policy.mjs`)

`decide({ tool, input, cwd, extraAllow, readAlso, recipients })` returns `{ decision: 'allow'|'ask'|'deny', reason, sentence, detail }`.

- `readAlso`: the agent's own scratch folders, which it may read without asking. A string is a folder that belongs to this agent alone. `{ root, session }` covers `<root>/<any key>/<session id>/…`, where Claude Code keeps one session's tool results and task output; the session id must be a UUID, and other sessions under the same key still ask. Entries that are not absolute paths are ignored.
- `recipients`: the names `SendMessage` may reach without asking: `"main"` and this agent's own helper ids, task ids and names.
- `sentence` and `detail` come from `describeRequest` and the policy, never from the agent's own `description` of a command, which the agent controls. `detail` is the exact command, path or address. `reason` says why it was allowed, asked or refused. The sentence says what the call does in plain words, and where:
  - An edit or read outside the folder, an edit in `.git` or to a hard-linked file says so ("wants to change app.js outside its own folder").
  - A command that waits is named by what it does ("wants to delete files", "wants to install packages", "wants to run code from the internet"). An everyday word ("read a file", "run the tests", "search the code") is used only when the policy, judging each part of the command on its own, would allow it or asks only because of where it reaches. A part with a risky option, a value the shell fills in (`$HOME`), a variable set before it, or a command that is not on the safe list never gets one, and neither does any part of a command that uses another command's output as words (`$(…)`, backticks, `<(…)`).
  - When an option is what makes it wait, the sentence names what the option does: "write to a file" (`sort -o`, `git log --output`, `find -fls`, uniq's second file), "delete files" (`find -delete`, `pytest --basetemp`), "run another program" (`rg --pre`, `git grep -O`, `go test -exec`), "run a script" (a `node` option that loads code), with where the file is when the command names it. Anything else is "wants to run a command".
  - Where a command reaches is added even when it chains or redirects: the words of every part are checked, with `~` and `$HOME` expanded and relative words also tried from any folder it `cd`s into ("wants to read a file outside its own folder" for `cat ~/.ssh/id_ed25519 | head`). A place that cannot be checked (`~user`, a link to something missing) or links that are followed add ", which may reach outside its own folder". A `Monitor` sentence ends ", using something outside its own folder".
  - `SendMessage` says only what is known: "to another Claude session" for an address, "to someone other than its helpers" for a name not in `recipients`, and just "wants to send a message" when the engine passed no `recipients`.

- **Allow:**
  - Tools that only plan, look up tools or skills, report, search the web or manage the agent's own background tasks: `ToolSearch`, `TaskCreate`, `TaskUpdate`, `TaskGet`, `TaskList`, `TaskOutput`, `TaskStop`, `TodoWrite`, `Skill`, `WebSearch`, `ReportFindings`. A tool that can run a command, read or change files, or send a message never goes on this list: the hook is the only gate.
  - `Agent` and `Task` (helpers) without `isolation`. Each step a helper takes passes the hook too.
  - Reads (`Read`, `NotebookRead`, `Grep`, `Glob`, `LS`) when every place they look is inside the **real path** of `cwd` (its `.git` and `.claude` included) or in `readAlso`. The place is `file_path`, `notebook_path` or `path`; for `Glob` also the folder before the pattern's first wildcard. `Grep`, `Glob` and `LS` with no place look in `cwd`. A `Glob` pattern containing `..` asks. A place with blank space at its start or end asks: Claude Code trims it before it searches (`" ~/.ssh"` is the home folder's `.ssh`; JavaScript's `trim()` strips exactly the same). An absolute `Glob` pattern is also judged by the folder Claude Code searches for it: the text before the last `/` ahead of its first `*`, `?`, `[` or `{` (or the pattern's own folder when it has none), which asks when it ends in blank space. Each place is also judged as Claude Code reads it: `~` expanded and `..` taken away as text before any link is followed, so `deep/../..` asks when `deep` is a link that leads deeper inside the folder (the system would land back inside; Claude Code searches the folder above it).
  - `Edit`, `MultiEdit`, `Write` and `NotebookEdit`, when the **real path** of the target (or of its nearest existing parent folder) is inside the real path of `cwd`, not inside `.git/` or `.claude/`, and not a file that is hard-linked elsewhere. A link to something missing is judged by where it points, since writing through it creates that file. A target with blank space at its start or end asks, and is refused when it would be either as written or trimmed.
  - `Bash`, only when the command is a **single command with no shell metacharacters** (`; & | \` $ ( ) { } < > ` and newline) and its words match the safe list:
    - read-only commands: `ls pwd cat head tail wc echo which file stat tree diff sort uniq cut grep rg`, plus `find` without `-exec`, `-execdir`, `-delete`, `-rm` or `-ok`. Every word that names an existing file or folder must be inside `cwd` or `readAlso` (a wildcard counts as the folder it searches; `echo`, `which` and `pwd` are exempt). A relative word that climbs out of `cwd` asks even when nothing is there: after a `cd`, Claude Code runs the next command in that subfolder, where the same words can reach an existing file outside. After a wildcard, `..` or a segment that could match it asks: bash before 5.2, sh, dash and ksh expand `.*`, `..*`, `.?` and `.[.]` to `..` (`.env*` cannot match it and stays automatic). The slashes after `scheme:` in a web address (`grep "https://"`) are not a path. Options that follow links while walking folders (`grep -R`, `rg -L`, `find -L`, `tree -l`, `ls -L`, `diff -r`) and options that read a list of file names from a file (`--files0-from`, `file -f`) ask. In an agent's shell, Claude Code replaces `find` and `grep` with its own bfs and ugrep, so their extra options are covered too (`find -rm`, `find -files0-from`, `grep --dereference-files`, `grep --from`);
    - `git` with one of `status diff log show rev-parse ls-files blame grep`, or `branch` without `-d`, `-D` or `--delete`, with the same rule for the files it names (`diff --no-index`, `blame --contents`);
    - test runners: `npm test`, `npm run test|lint|build`, `pnpm test`, `yarn test`, `node --test …`, `node <path inside cwd>`, `pytest …`, `python -m pytest …`, `go test …`, `cargo test …`, `make test`, `npx jest|vitest …`. Their paths must stay inside `cwd`, out of `.git` and `.claude`, and not at a hard-linked file. An argument that is an address code could be loaded from (`data:`, `file:`, `http:`, `https:`, `blob:`, in any case, after any spaces) asks. `node --test` takes only the test options that `node --help` lists, each with a value that fits (a value given as the next word must not start with `-`), and `--test-reporter` only with Node's own reporters (`spec tap dot junit lcov`). Every option that loads a module asks: `--import`, `--require`, `--test-global-setup`, and a reporter given as a module or a `data:` URL. The words after `--` of a package script go to the script, which is often `node --test`, so they follow node's rules as well: an option that loads or runs code (`-r`, `-e`, `-p`, `--import`, `--loader`, `--env-file`, `--inspect` and the like, with `_` read as `-` as node does) asks, and node's own `--test-*` options must fit as above. Other programs' options, such as `--watch=false` or `-t login`, stay automatic;
    - any exact prefix listed in `extraAllow`.
  - `Monitor` (a command run in the background) when `Bash` would allow its `command`, with the same reason. A `ws` Monitor, or any field other than `command`, `description`, `timeout_ms` and `persistent`, asks.
  - `SendMessage` to a name in `recipients`. An address (anything with `:` or `/`, such as `uds:…`) never counts as a helper.
- **Ask:** everything else, including reads outside the folder, `WebFetch`, `SendMessage` to anyone not in `recipients` (it could be another Claude session), every `mcp__*` tool and unknown tools. The launch refuses `CronList` and `DesignSync`; should one reach the hook anyway, it asks.
- **Deny** (answered at once, and the agent hears why):
  - edits to Claude Code's own settings: any path through a `.claude` folder at any depth, or a file named `.mcp.json`, compared case-insensitively, in the agent's folder or anywhere else. They could switch this very check off. Commands that would run code from there or write there ask, like `.git`;
  - `Agent` or `Task` with `isolation` set (a separate worktree, or a cloud session): the workbench could neither show nor limit that work. The agent starts the helper again without isolation.
- **What it cannot see.** Test runners and `node <script>` run code from the agent's folder, which the agent may have written or changed, with the person's own rights. That code can read, change and send anything the person can. On a laptop, a repository or web page that tricks the agent is therefore a real risk; running the workbench on a cloud machine keeps that away from the person's own files. The same goes for the checks in `workbench.json` and for any command the person allows. A prefix in `extraAllow` allows any words after it, as the owner listed it. Git read commands also see the whole repository, including branches and stashes outside the agent's worktree. A wildcard, or a non-recursive `diff` of two folders, can still read through links that the repository itself contains. Skills' inline shell blocks (the `!` commands in a skill's text) run under Claude Code's own permission check, not through the workbench hook, so the policy never sees them.

## Workspaces and receipt

`src/core/workspace.mjs` runs git only through `git(args, { cwd, timeout, input, okCodes, env, encoding, detached })`: `execFile('git', …)` (or `spawn`, for git in a process group of its own) with `-c core.fsmonitor=false` first, an environment without the variables that would point git at another repository (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the like) plus `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` and `LC_ALL=C`, and a timeout (30 s unless given). It resolves `{ stdout, stderr, code }`, where `code` is 0 or one of `okCodes`; `env` adds variables after the scrub (an undefined value takes one away); `encoding: 'buffer'` gives stdout as bytes; `detached: true` starts git as the leader of a process group of its own, ending the same ways as `execFile` (exit code, timeout, a missing git, too much output). Source control is in its own section below.

- `prepareRepo(path)` -> `{ root, name, head, branch, dirty }`. It throws a plain-language error if the path is not a git repo or has no commits. `branch` comes from `git symbolic-ref --quiet HEAD` with `refs/heads/` taken off, so it is never git's "heads/main" when a tag has the same name; it is null when HEAD is detached.
- `createWorkspace({ repoRoot, agentId, slug })` -> `{ path, branch, base }`. Runs `git worktree add -b workbench/<slug>-<agentId> <path> HEAD`, with `path` under `~/.workbench/worktrees/<repoName>-<hash of repoRoot>/`.
- `createWorkspace` removes the new worktree and its branch again (`worktree remove --force`, `branch -D`) if it cannot finish making it after `git worktree add` succeeded: nothing has run in it yet. It does the same when `git worktree add` itself fails part-way (a Ctrl-C in the terminal reaches git too, which leaves the branch it made first; a failing post-checkout hook leaves the whole worktree), but only when the branch was not there before it began (`git rev-parse --verify --quiet`): a branch that was there could hold kept work, and is never touched.
- `removeWorkspace({ repoRoot, path, deleteBranch?, onlyIfUnchanged?, base?, since? })` -> `{ removed, branch?, kept? }`. It removes only folders git lists as worktrees of this repository, never the main folder; a path git does not list gives `{ removed: false }` and runs nothing. With `onlyIfUnchanged` nothing that might hold work is removed: the folder goes only if its HEAD is still `base`, `git status --porcelain --ignored --untracked-files=all` is empty (an ignored `.env` or build may be work too), no tracked file differs from `base` where git status cannot see it, and `git worktree remove` without `--force` succeeds. For the third condition: when `git ls-files -v` tags any file other than `H` (an assume-unchanged or skip-worktree bit an agent set, or the assume-unchanged bit the person's `core.ignoreStat` gives every file git writes), the files are judged again in a new index that only `read-tree <base>` wrote, with no hook running, and `update-index --refresh` must exit 0; then the branch only through `git update-ref -d refs/heads/<branch> <base>`, in that order (update-ref would delete the branch of a folder that was kept). Anything else gives `{ removed: false, kept: true }`. Without `base` it refuses. `since` (with `onlyIfUnchanged`): the agent's last merged work commit. When it is given and is not `base`, it takes the place of `base` above, and the folder and branch also go only while a branch of the person's holds it (`git for-each-ref --contains <since> refs/heads/` lists a branch outside `refs/heads/workbench/`; Workbench's own branches do not count, since the same tidy may delete them): once they undid the merge, the agent's branch may be the only copy of its work. The engine calls it this way when an agent could not start, and at shutdown (see "Agent folders after Workbench stops"), with `base` and, once the agent was merged, `since`. Workspaces with changes are kept, with their branches. Without `onlyIfUnchanged`, `worktree remove --force` runs; if that fails and the folder is gone, the same removal runs once more for that one record. It never runs `git worktree prune`, which would also take away the records of the person's own worktrees whose folders are away right now (on a disk that is not mounted, say).
- `diffStats({ path, base })` -> `{ changed, adds, dels, list }`. The engine passes the run's `since` as `base`: the commit the agent started from, or its last merged work commit. Tracked changes come from `git diff --numstat <base>`. Untracked files come from `git ls-files --others --exclude-standard`, counted as additions by line count. Known limit: it counts in the agent's own folder, so after an agent merges the person's branch into its own, the lid's counts and the end-of-turn rule check can include the person's commits, and the agent's own `.gitattributes` can mark a text change as binary there. The merge card, the diff and what is merged count only what the merge brings in (see "Source control").
  - A .gitignore the agent adds or changes cannot hide its new files from the receipt or the rules. Files that the ignore rules hide now but the rules at `base` would not are listed too, marked `ignored: true`.
    - What they hide now: `git ls-files --others --ignored --exclude-standard --directory`. It is run without `--no-empty-directory`, which leaves out a hidden file in a new folder that also holds a visible one. Git may then list a folder and the files inside it, so the result is de-duplicated.
    - The rules at `base`: its .gitignore files on the way to each path, written to a scratch folder and read there by `git check-ignore --no-index`, with the repository's own `info/exclude` and the person's global excludes.
    - A folder git lists as `out/` is judged as `out`, made as a real folder in the scratch folder. Judged as `out/`, a rule such as `out/*` would match it, although git looks inside and judges each file. If the rules at `base` do not hide the folder itself, it is listed file by file, without what they hid inside it (a `node_modules`, say).
    - Paths go to `check-ignore` as `./<path>`, and to `ls-tree` with `--literal-pathspecs`, so a name such as `:!x` or `:/x` is that file, never pathspec magic. Folder lists go to git a few hundred at a time.
    - If git still fails here, `diffStats` rejects with a plain error, and the receipt does not run the checks: the agent's reason is that error's sentence ("Git could not compare the workspace with its starting point." or "Git could not list the files hidden by the agent’s own ignore rules."), or "Workbench could not check its work." for any error that is not a plain one.
    - The `.gitignore` files of the starting commit are read as bytes, in one `git cat-file --batch`, so one that is not UTF-8 is not mangled.
- `readRepoConfig({ repoRoot, ref })` reads `workbench.json` from the commit with `git show <ref>:workbench.json`, never from an agent's working copy. Default: `{ checks: [], rules: [], allow: [] }`.
  - `checks`: `[{ name, run, timeoutSec }]`
  - `rules`: `[{ say, paths: [glob] }]`
  - `allow`: `[command prefix]`
- Never git's own error text: every error of these functions is a plain sentence, and git's words go only in the error's `.detail`, for the log. "Git could not make a workspace for this agent." (`createWorkspace`) reaches the person when a launch fails; "Git could not compare the workspace with its starting point." and "Git could not list the files hidden by the agent’s own ignore rules." (`diffStats`) are the reason of a receipt that could not be built; "Git could not remove the workspace." (`removeWorkspace`) and "Could not read workbench.json from the commit." (`readRepoConfig`) are only logged by the engine. The source-control functions below never show git's words either.

`src/core/receipt.mjs`:

- `checkRules(rules, changedPaths)` -> `{ kept: [{ say }], broken: [{ say, paths }] }`. A built-in glob matcher handles `**`, `*` and `?`.
- `runChecks({ cwd, checks, onProgress, signal, env, keysEnv, mask })` -> `{ state: 'passed'|'failed'|'none', results: [{ name, ok, ms, tail }] }`. Each check runs through `/bin/sh -c` in `cwd`, in its own process group, with the scrubbed environment and a timeout (default 300 s), killed at the timeout. Aborting `signal` ends the running check's whole process group (SIGTERM, then SIGKILL after 2 s) and marks the rest "Not run".
  - The engine passes `env: { ...process.env, WORKBENCH_AGENT_ID: <the agent's id> }`. The scrub (`CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDE_AGENT_SDK*`, and the hook token) keeps that marker, so a live Workbench or `scripts/accept-real.mjs` started from a check refuses, as it does in the agent's own shell. It guards against accidents only: code that deletes the variable gets past it.
  - When the PATH has no `node`, the folder of the node running Workbench goes first (`withNodeOnPath`, exported from `receipt.mjs`: the same rule as for agents, kept as a copy because core does not import an adapter), so a check such as `npm test` works for a person whose own PATH lacks node.
  - `keysEnv` (with Connect): the keys of the agent whose work is checked, added after the scrub and node (`withKeys`, exported from `receipt.mjs`). Left out: names that are not variable names, `WORKBENCH_*` (so the engine's `WORKBENCH_AGENT_ID` stays), names the scrub removes, and values that are not text or hold a NUL.
  - `mask` (with Connect): each check's output is kept with 8192 bytes to spare beyond the 2048 shown, masked as a whole and, when earlier output was dropped, cut where a key may have been cut (`maskCut`, the rule agents' stderr follows); then the last 2048 bytes are shown. Without `mask`, nothing changes.
- `killChecksSync()` sends SIGKILL to every running check's process group at once, for the exit handler.

## Source control (`src/core/workspace.mjs`)

The engine's diffs, merges, throw-aways and commit graph rest on six functions of `workspace.mjs`. Each takes `repoRoot`, the top folder of the person's checkout (`prepareRepo().root`); anything else is refused ("The folder <root> is not the top folder of a git repository."). The agent's `path` must be a worktree that `git worktree list --porcelain` lists for that root, still on disk, on a `workbench/` branch (on `branch` itself when it is given). Otherwise: "No agent folder was given.", "That is your own folder, not an agent’s folder." and "Its folder is gone." (`why: 'gone'`); "Its folder is no longer on a workbench/ branch, so Workbench leaves it alone." and "Its folder is on the branch <b> now, not on <branch>." (`why: 'changed'`). `snapshotWork` and `workDiff` reject with a plain error (with `.why` and `.sentence` when it is a refusal); `mergeWork`, `discardWork` and `gitGraph` never reject: they answer `{ ok: false, why, sentence }`. Every sentence is built from facts; none is git's own text.

**The work set.** "The agent's work" is its folder as `git add -A` sees it, as one tree: every tracked change since `since` (committed, staged or not) and every new file no `.gitignore` hides. That tree is what a merge commits and merges, and what a throw-away keeps.

- It is read in a temporary index, a copy of the agent's own (which keeps what it staged, a file it added with `-f`, and git's record of unchanged files), never in the agent's index or files. The copy's file time is the original's, rounded down to the second and one second earlier, never 0: git then reads again every file it would have read with the original (a same-size edit made in the second the agent's index was written). Without an index of its own, `read-tree HEAD` starts it.
- Symbolic links are stored as links (their target text), never followed.
- Left out, and named in `left: [{ path, why }]`: repositories inside its folder (`why: 'nested-repo'`; `add -A` would fail on one with no commit, or record one as a link to its commit), and files that a `.gitignore` the agent added or changed hides, judged against the rules at `since` (`why: 'ignored'`: the receipt's `ignored: true` files).
- `since` is where its unmerged work starts: the commit it started from until its first merge, then the work commit W that merge joined in.
- Known limits: an assume-unchanged bit in the agent's index hides that file's change from the work set and the receipt; every snapshot hashes all untracked files again, so very large untracked outputs (files no `.gitignore` hides) make each diff, card and merge slow; file names that are not UTF-8 are read lossily, and their patch is null, never another file's; each keeps its own counts (git's records are read as bytes and paired by place). The assume-unchanged limit concerns the work set and the receipt only: the shutdown tidy is not fooled by it (see `removeWorkspace`).

**The review.** What the person reads before a merge (the diff, the files and counts on the card, the rules the card checks) is exactly what that merge would change in their branch: their HEAD's tree against the tree `git merge-tree --write-tree HEAD <work>` makes, which is the merge commit's own first-parent diff and what a merge reports. So commits of theirs that the agent brought into its branch are not shown as its work, and what its merge would undo of theirs is shown. Work not committed yet is handed to merge-tree as a commit on top of the agent's HEAD that nothing points at, by "Workbench <workbench@localhost>", dated as its parent (the agent HEAD's committer date; `@1000000000 +0000` only when git cannot read it). So the same work on the same HEAD always makes the same commit, and git's search for where the two histories met never walks all of the person's history first, as it would wherever there is no commit-graph for a commit dated before its parent. On a conflict, the review is the work against where its history and the person's branch last met (`git merge-base HEAD <agent HEAD>`); when the person's branch does not hold `since` (the merge would be refused) or git cannot say, the work against `since`. With nothing changed since `since`, there is nothing to review. The review's diffs run in the person's folder, so the attributes that decide what is binary are theirs, never the agent's (a `*.js -diff` in a `.gitattributes` the agent wrote). Side effect: `snapshotWork` and `workDiff` write objects to the repository's object database (that commit, and merge-tree's result), never a ref or a folder.

**`snapshotWork({ repoRoot, path, since })`** -> `{ head, tree, since, workId, changed, files, left }`

- `head`: the agent folder's HEAD; `tree`: the work set; `workId`: `<head>:<tree>:<into>:<merged>`, which binds a card to exactly what it showed. The first two parts are the work: the agent folder's HEAD and the work set's tree. The last two are the review it was shown with: the person's HEAD when the review was made, and the tree merge-tree made of that HEAD and the work. `<merged>` is empty when the review was not that merge: a conflict, a HEAD that does not hold `since`, or git could not say; `changed`: the tree differs from `since`'s tree.
- `files: [{ path, status: 'added'|'modified'|'deleted', adds, dels, binary?, large? }]`: the review's files, without rename detection; none when nothing changed. `large`: a blob over 2 MB, counted as nothing. A regular file that became a link counts +1 −0, never binary or large, so its patch shows where the link points.
- Its own refusals (`why: 'git'`), besides the folder checks above: "Workbench does not know which commit its work started from.", "The commit its work started from is no longer in this repository.", "Its folder has no commit checked out.".

**`workDiff({ repoRoot, path, since, maxFiles = 300, maxFileBytes = 200_000, maxTotalBytes = 2_000_000 })`** -> `{ workId, since, head, files: [{ path, status, adds, dels, binary?, large?, patch, cut? }], left, cut?, omitted }`

- `patch`: that file's unified diff between the review's two trees, from `git diff-tree -r -p --no-ext-diff --no-textconv --no-color --no-renames` with `core.quotePath=false`, its `diff --git` header included. A type change (a file that became a link, or the other way) is git's two parts, the old one deleted and the new one added, one after the other under the same header line. Patches are matched to paths by git's exact header line, quoted names included (asked for together, or one by one when they do not line up: a file that became a folder brings in the folder's files).
- `patch` is null for a binary or large file, and for a file past `maxTotalBytes` (then with `cut: true`), and for a file whose name is not UTF-8 (asked for by that name read as UTF-8, git would find another file, or none). `cut` on a file: its patch was cut, at a line end, at `maxFileBytes` or at what was left of `maxTotalBytes` (a patch cut to nothing is null, with `cut: true`); `cut` on the whole: `maxTotalBytes` was reached. `omitted`: the files past `maxFiles`, not listed.

**`gitIdentity({ repoRoot })`** -> `{ name, email } | null`: `user.name` and `user.email` from git config, both set and free of control characters and of `<` and `>`. Git's guessed identity (user@host) never counts, and neither does `GIT_AUTHOR_NAME` and the like in Workbench's own environment.

**`mergeWork({ repoRoot, path, branch, since, expect: { workId, into, intoHead }, message: { subject, body?, name? }, agentId, harness, name? })`** -> `{ ok: true, into, merge, work, files, adds, dels }` | `{ ok: false, why, sentence, paths? }`. `merge` is the merge commit M, now the person's HEAD; `work` is the agent's work commit W, M's second parent; `files` (a number), `adds` and `dels` count M's first-parent diff, the files the review showed. `why` is one of `detached`, `busy`, `identity`, `git-old`, `changed`, `moved`, `nothing`, `ancestry`, `conflict`, `blocked`, `gone`, `git`. An `agentId` that is not an agent id: "Workbench could not tell which agent this is, so nothing was merged.". Steps, in this order:

1. The person's folder, read afresh, judged in this order:
   - `detached` when HEAD is not on a branch;
   - `busy` when a merge, rebase, cherry-pick, revert or bisect is under way (`MERGE_HEAD`, `rebase-merge`, `rebase-apply`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, and `sequencer`, which marks a cherry-pick or revert of several commits waiting between two of them; each is found through `git rev-parse --git-path`. `CHERRY_PICK_HEAD` and `REVERT_HEAD` are also asked of the ref store with `git rev-parse -q --verify --symbolic-full-name`, because with reftable they are refs, not files. A branch or tag of that name does not count), or when its index has unresolved conflicts (`git ls-files -u`; a `git stash pop` that did not apply cleanly leaves them without any of those markers), then with their `paths`;
   - `identity` when `gitIdentity` is null;
   - `git-old` when git is older than 2.38 (`merge-tree --write-tree`);
   - `moved` when the branch or HEAD is not `expect.into` and `expect.intoHead`, or when HEAD is not the one the card's review was made against (the `<into>` of `expect.workId`: a folder that was on another branch while the card was drawn, and is back).
2. The agent's folder: a gone folder is `gone`; one in the middle of a merge or rebase, or with unmerged entries, is `git` ("Its folder is in the middle of a merge or rebase, so its work cannot be merged yet.": `add -A` would take its conflict markers as work). Then the work set: `changed` when its `<head>:<tree>` is not that of `expect.workId`, or `expect.workId` names no review, `nothing` when nothing changed since `since`.
3. **The ancestry guard:** `ancestry` when `since` is not an ancestor of the person's HEAD (`merge-base --is-ancestor`): the merge would bring in another branch's commits.
4. **The work commit W**, only when the work set differs from the agent HEAD's tree: `commit-tree <tree> -p <agent HEAD>`, then `update-ref refs/heads/<branch> W <agent HEAD>` (compare-and-swap: when the agent made a commit meanwhile, `changed`), then `git -C <path> reset -q`, so the agent's index matches W and its folder shows clean; its files are untouched. If that reset fails, the branch is put back by compare-and-swap and the answer is `git`: "Git could not update its folder, so nothing was merged. Try again in a moment.", or, when it could not be put back, "Git could not update its folder, so nothing was merged. Its work is safe as a commit on its branch <branch>.". Otherwise W is the agent's HEAD.
5. `nothing` when W is already in the person's branch (merged by hand, say).
6. `git merge-tree --write-tree --name-only -z <HEAD> <W>`, without `--merge-base`: git's own merge base, as `git merge` would take (an agent that merged the person's branch into its own would otherwise get false conflicts). Exit 0 with a tree: clean; exit 1 with a tree: `conflict`, with the conflicted `paths` from the `-z` records; anything else: `git`. Nothing is written to the person's folder. Then `changed`, "What merging it would change in <into> is no longer what you saw. Have another look.", when the tree is not the `<merged>` of `expect.workId`. That happens when something merge-tree reads changed since the card was drawn (the person's attributes, such as a merge driver or `merge=union`, or their merge settings), or when the review showed no merge (a conflict then, or a HEAD that did not hold `since`). W has the tree and the parent of the commit the review gave merge-tree, so a card that still matches makes the same tree. Like `conflict`, this leaves W on the agent's branch.
7. **The merge commit M:** `commit-tree <tree> -p <HEAD> -p <W>`, the person's HEAD first.
8. Checked again (`moved`, `busy`, unresolved conflicts), and `blocked`, with those `paths`, for a file M changes that the person deleted or renamed without staging it (`git ls-files --deleted`, compared by bytes; a skip-worktree file of a sparse checkout is not listed). Git takes a missing file for an unchanged one and would write M's version there; a file that M deletes too stays deleted. Then, in the person's folder: `git -c core.hooksPath=<empty folder> -c submodule.recurse=false -c maintenance.auto=false -c gc.auto=0 merge --ff-only --no-squash --no-autostash --no-overwrite-ignore --no-verify-signatures -q <M>`, with a 10-minute time limit (stopping git half-way through the person's folder would be worse than waiting).
   - Another git command holding the person's `index.lock`, `refs/heads/<into>.lock`, `HEAD.lock` or `reftable/tables.list.lock` (an editor's git, say): wait and try again, four tries in all, 0.2, 0.4 and 0.6 s apart, then `busy`. A held branch or HEAD lock is looked for before the merge starts: git takes it only after it has updated the files, and would stop half-way. A held `index.lock` is read from git's own words (exit 1 on newer git, 128 on older).
   - MERGE_MSG and MERGE_RR are read before each attempt: the message git prepared for the person's next commit (after `git cherry-pick --no-commit`, say) and rerere's record of the conflicts they settled. The fast-forward deletes them as if it had ended a merge, so any it deleted is put back afterwards, never over one written meanwhile. One that cannot be read: `git`, "Workbench could not read what git keeps for your next commit, so nothing was merged.". git's `AUTO_MERGE` ref still goes, as with git's own merge.
   - Exit 0: done, once the branch is at M (or holds it); else `git` with the unfinished sentence.
   - A branch at M after any other exit also counts as done.
   - Exit 1 with paths under git's headings for files in the way ("would be overwritten by …", "would be removed by …", "would lose untracked files in them", and a sparse checkout's "are not up to date"), with HEAD unmoved: `blocked`, with those `paths`. Git checks every path before it writes any, so nothing changed; W stays on the agent's branch. A path that already holds what M brings in there is never named as the person's own: a plain file where M has one, whose bytes, cleaned as git would store them, are M's blob (`git hash-object --stdin-paths` in the person's folder, each name in C-style quotes). Such files are left by a fast-forward that stopped part-way and put its index back. `blocked` names only the others. When none are left, the answer is `git`, "Files in your folder already hold what the merge brings in, and git will not write over them: a.js, b.js, c.js and 2 more. Undo those changes, then merge again." (for one file: "A file in your folder already holds what the merge brings in, and git will not write over it: a.js. Undo that change, then merge again."), with those `paths`.
   - Exit 128 with git's own words that it stopped before it began ("Not possible to fast-forward", "You have not concluded your …", "Exiting because of an unresolved conflict"): `busy` when an operation started meanwhile, or when unresolved conflicts appeared with the branch and HEAD unchanged; `moved` when the branch or HEAD moved; otherwise `git`, "Git could not finish the merge. Nothing in your folder changed.". Any other exit 128 is treated as below. Git also exits 128 after it wrote the files and the index, when it cannot move the branch: for example after a `git reset --soft` meanwhile, which the index lock does not keep out.
   - Anything else, once git began on the person's folder, may have stopped part-way: `git`, "Git could not finish the merge into <into>. Have a look at your folder before you try again.". Merging again finishes it. When git wrote its index, the next fast-forward goes through. When it put its index back, the files it wrote are named as already holding what the merge brings in (see exit 1 above); once they are undone, the merge goes through.
9. `{ ok: true, into, merge: M, work: W, files, adds, dels }`. From now on the engine counts the agent's work from W.

Refusals before step 4 change nothing at all. From step 4 on, W stays on the agent's branch (its index reset to match, its files untouched), and the person's folder changes only by the fast-forward of step 8 (with MERGE_MSG and MERGE_RR put back as they were).

Messages, authors and dates:

- **W:** `<subject>`, a blank line, the body when there is one and a blank line, then the trailers `Workbench-Agent: <agentId>`, `Workbench-Kind: work`, and `Co-authored-by: Claude <noreply@anthropic.com>` only for a Claude Code agent (`harness === 'claude'`).
- **M:** `Merge <name>: <subject>`, a blank line, `Workbench-Agent: <agentId>` and `Workbench-Kind: merge`. `<name>` is `name ?? message.name` (one line, at most 80 characters), else the agent's branch.
- `subject`: one line without control and direction-changing characters, cut at a word end to at most 72 characters; "Work by <name>" when it is empty. `body`: plain lines without control or direction-changing characters, at most 4000 characters.
- Author and committer: the person's `user.name` and `user.email`, never git's guessed identity. `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` are taken away, so the commits are dated now. `--no-gpg-sign`: W and M are unsigned, even when `commit.gpgSign` is set.

`mergeWork`'s own sentences (the engine names them after the agent, and uses its own words for most of them: see "Source control in the engine"):

| `why` | Sentence |
|---|---|
| `detached` | "Your folder is not on a branch, so there is nowhere to merge it." |
| `busy` | "Your folder is in the middle of a merge or rebase. Finish that first.", "Your folder has unresolved conflicts in a.js, b.js. Finish that first." (three paths at most, then "and 2 more"), or "Another git command is busy in your folder. Try again in a moment." |
| `identity` | "Git does not know your name and email yet, so Workbench cannot make the merge commit. Set user.name and user.email with git config, then try again." |
| `git-old` | "Workbench needs git 2.38 or newer to merge." |
| `changed` | "Its work changed since you looked. Have another look.", "What merging it would change in <into> is no longer what you saw. Have another look.", or a folder check's own sentence |
| `moved` | "<into> changed since you looked. Have another look." |
| `nothing` | "Its work is already in <into>." |
| `ancestry` | "It started from a commit that is no longer in <into>, so merging it would bring in other work." |
| `conflict` | "Its work does not merge cleanly into <into>." |
| `blocked` | "Your own changes are in the way: a.js, b.js, c.js and 2 more. Commit or put them aside, then merge again." |
| `gone` | "Its folder is gone, so there is nothing to merge." |
| `git` | "Git could not finish the merge. Nothing in your folder changed.", where that is known; "Files in your folder already hold what the merge brings in, and git will not write over them: a.js, b.js, c.js and 2 more. Undo those changes, then merge again."; "Workbench could not read what git keeps for your next commit, so nothing was merged."; otherwise one of the sentences in the steps above, the work set's own refusals, or "Git took too long and was stopped.", "Git is not installed, or it is not on the PATH.", "Git gave back more than Workbench can read at once." |

**`discardWork({ repoRoot, path, branch, since, expect: { workId }, agentId })`** -> `{ ok: true, saved: 'refs/workbench/discarded/<agentId>' }` | `{ ok: false, why: 'changed'|'gone'|'git', sentence }`. `branch` must be one Workbench made (`workbench/…`, a plain branch name of at most 200 characters), else "That is not a branch Workbench made, so nothing was thrown away."; an `agentId` that is not an agent id: "Workbench could not tell which agent this is, so nothing was thrown away.".

- Its folder there:
  1. the work set, and `changed` ("Its work changed since you looked. Have another look.") unless the work set's `<head>:<tree>` is that of `expect.workId` (the merge review it also names does not matter here);
  2. the hidden copy S: the agent's HEAD itself when the work set is its tree; else `commit-tree <tree> -p <head>` with the message `Thrown away: <branch>`, a blank line, `Workbench-Agent: <agentId>` and `Workbench-Kind: discarded`, by the person's identity or, when git has none, "Workbench <workbench@localhost>" (a throw-away needs no identity);
  3. `update-ref --create-reflog refs/workbench/discarded/<agentId> S`: with a reflog, so an earlier copy under that name is not lost;
  4. `worktree remove --force <path>` (`--force --force` when the worktree is locked). If that fails with the folder still there: "Git could not delete its folder <path>. A copy of its work is kept in git as <saved>."; with the folder gone, the same removal runs once more, for that record only;
  5. `update-ref -d refs/heads/<branch> <head>` (compare-and-swap). A branch that moved meanwhile: "Its folder is gone, but its branch <branch> changed meanwhile, so it was kept. A copy of its work is kept in git as <saved>.".
- Its folder already gone: the branch still goes, and its last commit is the hidden copy. A record git still lists for the folder is removed with `worktree remove --force` (`--force --force` when locked), which takes away only that record, and only when nothing at all is at that path (`lstat`); otherwise "Workbench cannot read its folder <path>, so it left the folder and its branch alone.". Then: with no branch left, `gone`, "Its folder and its branch are already gone."; with the branch checked out in another folder, "Its branch <branch> is checked out in another folder, so Workbench left it alone."; `expect.workId` may be null; otherwise its `<head>:<tree>` must be `${tip}:${the tip's tree}` (`changed`); then the hidden ref (with a reflog) and `update-ref -d` by compare-and-swap (`changed` when the branch moved).
- Once deleting has begun, an unexpected failure says "Git could not finish throwing its work away. A copy of its work is kept in git as <saved>."; before that, "Git could not throw its work away. Nothing was deleted.".
- The hidden copy holds the work set: files a `.gitignore` hides and repositories inside the folder go with the folder.

**`gitGraph({ repoRoot, limit = 200 })`** -> `{ ok: true, head, branch, commits, more }` | `{ ok: false, why: 'git', sentence }`

- `commits: [{ id, parents, subject, author, at, refs, agentId, kind }]`: `git log --topo-order` of HEAD and every `refs/heads/workbench/*` branch, newest first, at most `limit` (1 to 5000); `more` when there are more.
- `at`: the author time in ms. `subject` (at most 1000 characters) and `author` (at most 200) are passed on as they are: the page escapes them and shows their hidden characters.
- `refs`: the short names of the local branches at that commit, the person's branch first, then by name.
- `agentId` and `kind` come only from the commit's own `Workbench-Agent` and `Workbench-Kind` trailers (the last value of each), never from its subject. `agentId` must look like an agent id; `kind` is `merge` only with at least two parents, else `work` for a work commit, else `commit`.
- A repository with no commits: "The repository at <root> has no commits yet."; any other failure: "Git could not read the history of this repository.".

**Safety rules.** The person's folder only ever sees `git merge --ff-only` to a merge commit built in the object database (`merge-tree` and `commit-tree`): never a real merge, never conflict markers, never `update-ref` on a checked-out branch.

- **No hooks.** Every git command here runs with `core.hooksPath` set to a new empty folder (removed afterwards), and every hook set in git config (`hook.<name>.command` or `.event`, git 2.54 and newer) is switched off with `hook.<name>.enabled=false`. The names are read in the person's folder and in the agent's (`git config --name-only -z --get-regexp ^hook\.`), and the settings go to git as `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, after any Workbench's own environment already has. `commit-tree` runs no hook anyway. So no `pre-commit`, `post-merge` or `post-checkout` hook runs.
- **`--no-overwrite-ignore`:** an ignored `.env` in the person's folder is never overwritten by a merge that adds one; the merge is refused as `blocked`.
- **`--no-autostash`:** `merge.autoStash=true` in the person's config changes nothing: nothing is stashed, so nothing can come back with conflict markers.
- **`--no-squash`:** `branch.<into>.mergeOptions=--squash` would otherwise write and stage M's files and leave the branch where it was. Git reads `branch.<name>.mergeOptions` before the command's own flags, and each flag here outweighs its counterpart there.
- `submodule.recurse=false`, `maintenance.auto=false` and `gc.auto=0`: no submodule work and no automatic upkeep start in the person's repository.
- **The ancestry guard** (step 3), and **unresolved conflicts** refused as `busy` before anything is made.
- **Git detached from the terminal.** Every git command of `mergeWork` and `discardWork` (the hook-config read included) runs in a process group of its own (`git(…, { detached: true })`). A Ctrl-C or SIGHUP in the terminal goes to the foreground group: it reaches only Workbench, which waits for the git work under way, never git, which would stop part-way through the person's folder or the agent's. Time limits still stop git.
- **Scoped worktree removal.** Never `git worktree prune`, which would also take away the records of the person's own worktrees whose folders are away right now (on a disk that is not mounted, say): only the one record, and only when nothing is at its path.
- **The hidden copy:** a throw-away keeps the work set at `refs/workbench/discarded/<agentId>`, with a reflog.
- **The person's attributes:** the review's diffs run in the person's folder (see "The review").
- **Type changes:** a file that became a link, or a link that became a file, keeps both of git's parts in its patch, so neither half is hidden. A file that became a link keeps its patch even when the old file was binary or large (git then gives the old side one "Binary files … differ" line).
- **Documented limits.** Clean and smudge filters and merge drivers set in git config still run during the fast-forward, as they would for git itself: setting them needs the person's OK. The agent's HEAD is not required to descend from `since`: a branch reset onto other history (which also needs the person's OK) would bring that history in, and the review would show it. A half-done fast-forward (files updated, branch not moved) is still possible: on a lock race, on a command that moves only the branch while git writes the files (`git reset --soft`), or on a write failure. Workbench then says "Git could not finish the merge into <into>. Have a look at your folder before you try again.". Merging again finishes it, once any files it left that git will not write over are undone (step 8). These functions need git 2.38 or newer (`merge-tree --write-tree`); nothing here uses `--merge-base` or `--attr-source`. A held `index.lock` is recognised by git's own words, whatever the exit code, and so is a fast-forward that stopped before it began (exit 128).

**Connecting: name and email, sign-ins and cloning.** These functions of `workspace.mjs` serve Agents & keys (see "Connect") and the CLI's `--clone`. Each runs git from a new empty folder outside every repository (`outsideRepos`: made under the temporary folder, removed afterwards), with `GIT_CEILING_DIRECTORIES` set to that folder's parent, so no repository's own config is read: an agent can change a repository's config, and that config could name a credential helper, which is a program git runs. Git never asks the person anything here: `GIT_TERMINAL_PROMPT=0` comes from `git()`, an empty `GIT_ASKPASS` stops git looking for an askpass program, `SSH_ASKPASS` and `SSH_ASKPASS_REQUIRE` are taken away, and `GCM_INTERACTIVE=never` keeps Git Credential Manager quiet, so a refusal comes back at once, as an error. Git's own words go only in an error's `.detail`.

- **`gitConfigIdentity()`** -> `{ name, email }` from git's global config (`git config --global --get`; the file `GIT_CONFIG_GLOBAL` names counts too), each `''` when unset. A plain error (`why: 'git'`) when git cannot read its settings.
- **`setGitIdentity({ name, email })`** -> `{ name, email }`, what was saved: `git config --global --replace-all user.name <name>`, then the same for `user.email`. Both are trimmed. `GIT_CONFIG_GLOBAL` is honoured; that is how tests keep away from the person's own file.
  - The name: 1 to 100 characters on one line, with no control, line-separator or direction-changing characters, and no `<` or `>`. Refused: "A name for git must be 1 to 100 characters on one line, without < or >." (`why: 'name'`).
  - The email: shaped like `x@y.z`, at most 254 characters, with none of those characters. Refused: "That does not look like an email address." (`why: 'email'`).
- **`approveGitCredential({ host, username, password })`** -> `{ helper }`, **`rejectGitCredential({ host, username })`** -> `{ ok: true }`, and **`fillGitCredential({ host, username })`** -> `{ username, password } | null` run `git credential approve`, `reject` and `fill`, with the fields on stdin (`protocol=https`, `host`, `username`, `password`), never in argv.
  - The host must be `github.com` (`why: 'host'`), the user name a GitHub login (`why: 'username'`), and the password 1 to 1000 characters with no line break or NUL (`why: 'password'`), since a line break would start another field.
  - `helper` says whether git has a credential helper for https://github.com (`git config --get-urlmatch credential.helper`). With none, approving keeps nothing; this is common on Linux.
  - A failed `approve` is a plain error (`why: 'git'`) whose `.detail` has the token cut out, since a credential helper could repeat what it was given.
  - `fill` never rejects: it gives `null` when git keeps nothing (git then exits 128, since it may not ask), when what git gives is for another host or user, and on any failure. Nothing in Workbench calls it now: Connect reads its GitHub token back from the key store.
- **`cloneRepo({ url, into, name?, onProgress?, timeoutMs = 30 minutes, allowLocal = false, signal? })`** -> `{ root }`, the new folder's real path.
  - **Addresses.** Accepted: `https://host/path`, with no user, password, query or fragment; `ssh://[user@]host[:port]/path`; and `[user@]host:path` (scp-like). Hosts and users must not start with "-", nor may an scp-like path. Everything else is refused before git runs (`why: 'url'`): `ext::`, `fd::` and every other `transport::address` form, `file://`, `http://`, `git://`, anything that starts with "-", anything with spaces or control characters, and an empty address. The sentence is always "Workbench clones addresses like https://github.com/owner/repo or git@github.com:owner/repo.git.", the Mac app's own words: it never repeats the address, which may be a key pasted into the wrong field. `allowLocal` (tests only) adds `file://` addresses and absolute paths.
  - **The folder.** `into` is made when missing; `~` is the home folder. `name` defaults to the last part of the address's path, without a trailing `/` or `.git`; it may not be empty, `.` or `..`, hold `/` or control characters, or be longer than 255 bytes (`why: 'url'`). The new folder must not exist, or must be an empty folder. A file, a link or a folder with anything in it is refused: "There is already something at <folder>. Choose another folder, or move it away first." (`why: 'exists'`). An `into` that is a file, or cannot be made, is refused as `exists` too.
  - **Git.** `git -c protocol.allow=never -c protocol.https.allow=always -c protocol.ssh.allow=always [-c protocol.file.allow=always] clone --progress -- <url> <folder>`, with file allowed only with `allowLocal`. `GIT_ALLOW_PROTOCOL` is taken away, because it would override those settings.
  - **How git runs** (`gitStream`): with an argument array, as `git()` runs it (`-c core.fsmonitor=false` first, the scrubbed environment), in a process group and session of its own. Git then has no terminal, so ssh cannot stop to ask on one (a host key, a passphrase). At the time limit the whole group gets SIGTERM, then SIGKILL 5 seconds later.
  - **Stopping** (`signal`, an AbortSignal). The whole group gets SIGTERM, and SIGKILL a second later if anything is left; the promise settles once git is gone (or a second after that SIGKILL, when a process outside the group still holds git's output). What the clone made is removed (its new folder, or what it put in a folder that was empty), and `cloneRepo` rejects with `why: 'stopped'`, "Copying the repository was stopped.". A signal already aborted refuses before any folder is made, and a clone that finished just as it was stopped is removed too, so a stop always leaves things as they were. When Workbench exits while git copies, an `exit` handler kills git's whole group at once (SIGKILL) and removes what it made.
  - **Progress.** stderr is split on `\r` and `\n`, and `cloneProgressOf(line)` maps git's lines to `{ phase, percent }`: `counting` ("Enumerating objects", "Counting objects", also the server's), `compressing`, `receiving`, `resolving` ("Resolving deltas") and `checkout` ("Updating files", "Checking out files"). `percent` is 0 to 100, or null when git gave none. `onProgress` hears each change once; a listener that throws does not stop the clone.
  - **Failures**, with git's words only in `.detail`:
    - `auth` when git says "Authentication failed", "could not read Username" or "Password", "terminal prompts disabled", "Permission denied (publickey)", "Repository not found", "Invalid username or password", "HTTP Basic: Access denied", "Write access to repository not granted", or returns a 401 or 403. On github.com the sentence is "GitHub did not let Workbench read this repository. If it is private, connect your GitHub account, then try again."; on another host, "<host> did not let Workbench read this repository. If it is private, make sure git can sign in to <host>, then try again.". ssh's "Host key verification failed" is `auth` too: "SSH on this computer does not know <host> yet, so git did not connect to it. Use its https:// address, or connect to it once with ssh in a terminal."
    - `network` when git could not resolve the host, connect, or finish the transfer: "Workbench could not reach <host>.". This is checked after `auth`, because ssh prints "Could not read from remote repository" for both.
    - `exists` when git found the folder taken after all: "Something is already in the folder it would go into. Choose another folder."
    - `stopped` when `signal` stopped it (above).
    - `git` for anything else ("Git could not clone <address>."), for the time limit ("Git took too long and was stopped.") and for a missing git ("Git is not installed, or it is not on the PATH.").
  - A folder that did not exist before the clone and is still there after a failure is removed (git normally removes it itself). An empty folder that was there before is left.

## History

`src/core/history.mjs` keeps the root agents of one repository across restarts, so the next run can show them and pick them up. Live mode only; the demo keeps nothing.

- **Where.** `~/.workbench/history/<repo key>.json`, with the key the worktree folder uses (`<repo name>-<8 hex of sha1(real repo path)>`, from `workspacesFolder`). The folder is made private (0700) and the file 0600. `historyFile(repoRoot, { dir })`; tests use a temporary HOME, or `options.historyDir` on the engine.
- **What.** `{ version: 1, repo, agents: [record] }`, the last **50** roots by start time. A record is built field by field from the AgentView (`recordOf`), never copied whole: `id`, `name`, `task`, `harness` (`claude` or `codex`), `model`, `machineId`, `startedAt`, `endedAt`, `state`, `stateReason`, `says`, `files`, `checks` (names, results and times, never a check's output; one that was running is kept as not checked), `rules`, `approvals`, `usage`, `sessionId` (the Claude session id or Codex thread id), `workspace` (`path`, `branch`, `base`, `since`, `from`; `null` when the folder was removed or the work thrown away), `work` (as on the view: `branch`, `from`, `folder`, `merged`, `problem`, `thrownAway`), `budgetUsd`, `turns`, `toolCalls`, `savedAt`. Helpers are not kept. Nothing else gets in: no hook token, no page token, no environment, no command output. A launch that never started (failed with no turn and no session) is not kept.
- **Reading.** `load()` cleans every record again (unknown fields dropped, bad ids and harnesses refused, text clipped); an active state becomes `stopped` ("Workbench was closed while it was working."); a missing `endedAt` becomes `savedAt`. A file that is not JSON is renamed `<file>.damaged` and treated as empty. The git fields are cleaned field by field:
  - `workspace.path`: absolute, at most 4096 characters, no NUL; `base` and `since`: commit ids (40 or 64 lowercase hex), else null;
  - `workspace.branch` and `work.branch`: a plain branch name that starts with `workbench/` (`agentBranch`), else null. A plain branch name (`branchName`) is parts of `[A-Za-z0-9._+-]` joined by single `/`, no part starting with `.` or ending in `.lock`, no `..`, not starting with `-` or ending in `.`, at most 200 characters;
  - `from`, `merged.into` and `problem.into`: a plain branch name, else null. Known limit: a person's branch whose name has other characters (an `@`, say) loses them in the file and reads null after a restart; the git screen and merges still read the branch from git;
  - `merged` is kept only with a commit id as `merge`; `problem` only with a known `why`, at most 20 paths of at most 500 characters and a sentence of at most 600; `thrownAway.saved` only as `refs/workbench/discarded/<id>`; a thrown-away record has `branch: null` and `folder: false`.
- **Writing.** `schedule()` after meaningful events (a root or helper created, state, says, files, checks, rules, model, session, approval, usage, ended, resumed, work), debounced (1.5 s, `options.historyDebounceMs`), and `save()` at shutdown, after the folders were tidied (so a removed folder is recorded as gone), on a forced exit (`killAllSync`), when something is forgotten, and at once after every merge and throw-away (and when git finds an agent's folder and branch gone). Each write is atomic: a temp file in the same folder, then a rename. It reads the file first and keeps agents that another Workbench on the same repository wrote meanwhile (unless this one forgot them). A write that fails is logged and never stops an agent.
- **Wiring.** `deps.history` is the module; `engine.start()` calls `deps.history.open({ repoRoot, dir, debounceMs, log })`, loads the records and restores them (`store.restore(record, { ok, reason })`). Without `deps.history` (or in demo mode) the engine keeps no history. The engine's records come from `_historyRecords()`: the earlier agents nobody continued (their saved record, unchanged unless the engine rebuilt it from the view: after a merge, with `since` its work commit; after a throw-away or a tidy that removed its folder, with `workspace: null`; when a reason a merge did not go through clears) and this run's roots (rebuilt from their views and runs).
- **Views.** A restored root is an AgentView with `earlier: true`, `canContinue` and `continueReason` (see `events.mjs`), and its saved `work` with `folder` as it is on disk now (see "Agents from an earlier run"). It counts in `spendTodayUsd` like any root started today. Its `helpers` are empty.

## Keys (`src/core/keys.mjs`)

The key store keeps the keys a person gives their agents: API keys, cloud keys and tokens. Their values never go into `keys.json`, a log, the page or an argv: they are kept in the login keychain, a keyring, or, with neither, private files of their own.

```js
new KeyStore({ home, platform, backend = 'auto' /* 'keychain'|'secret-tool'|'file' */, securityBin = '/usr/bin/security',
               secretToolBin /* null: found on PATH */, log, runner /* (bin, args, { input, timeoutMs }) */, env /* process.env */ })
await list()      // -> [{ id, preset, label, vars: [{ name, shown, secret, missing? }], scope: { kind: 'all' } | { kind: 'repo', root },
                  //      agents: 'all' | [ids], kept: 'keychain'|'secret-tool'|'file', created }]
await add({ preset, label, values /* { NAME: value } */, secretNames?, scope, agents }) // -> { id }
await remove(id)  // -> { removed }
await load()      // -> { keys, missing }  reads every value once; never throws
envFor({ repoRoot, harness }) // -> { NAME: value }  synchronous, from memory; never throws
values()          // -> every secret value in memory (frozen, the same array until something changes), for masking
valuesOf(id)      // -> { NAME: value } of one key, or null
export function maskSecrets(text, values)  // pure
export function shownValue(value)          // "•••• 7QXA" or "••••"
export const FORBIDDEN_NAMES               // [{ name, why }]; forbiddenName(name) -> the entry, or null
```

- **What is kept where.**
  - `~/.workbench/keys.json` says what each key is, and never holds a value, secret or not. The folder is 0700 (made private if it was not); the file 0600, written as a new O_EXCL temp file, fsynced, then renamed. Each record is `{ id, preset, label, vars: [{ name, secret }], scope, agents, kept, created }`. A file that is not JSON, is a link, or is not a plain file (a FIFO, a folder) is set aside as `keys.json.damaged`; damaged records are left out, never widened to every repository or agent.
  - Both files are read with O_NOFOLLOW and O_NONBLOCK, then checked with fstat, so a FIFO put in their place (by anything running as the person) is refused at once and never blocks Workbench.
  - The values are kept where `kept` says:
    - `keychain` (macOS): the login keychain, through `/usr/bin/security -i`. Service `Workbench key`, account `<id>/<NAME>`, default access (no `-T ""`).
    - `secret-tool` (Linux, when a Secret Service answers): the value on stdin; argv holds the names only.
    - `file` (otherwise): `~/.workbench/keys/<id>.json`, 0600 in a 0700 folder, written through an O_EXCL temp file and read as above. A file that others could read, a link, anything but a plain file, or a folder that is a link or another account's, is refused.
  - `backend: 'auto'` picks the keychain on macOS. Elsewhere it uses `secret-tool` (found in PATH's absolute folders) when a lookup of a missing item exits 1 and says nothing; otherwise files. A key is always read back from where it was kept, whatever `auto` picks today.
- **`security -i`** (env-secrets.md 5.1).
  - One command per process, on stdin, then stdin is closed. Ids are `k` and 12 hex digits, names match `NAME_RE`; both are checked again before they go on a line (`securityLine`).
  - The value goes as `-X <hex>`. The item holds printable ASCII only: a plain value (letters, digits and `._~+/=-`) as it is, anything else as `wb1:<base64 of its UTF-8>`, so how `find-generic-password -w` prints other bytes never matters.
  - Every line of a key is measured before anything starts, and one of 4000 bytes or more is refused (`security` reads 4095 bytes at a time). Between 1,903 and 1,966 plain characters fit, by the length of the name.
  - The child's stderr is read only to sort a failure into not-found, no-window, canceled, locked or other. It is never logged, kept or shown, since `security` repeats the words it was sent.
  - Reading at start: the first value alone, so a locked keychain asks once, then four at a time. A store that cannot be opened is not asked again in that pass, and what could not be read is said once per store and reason, by the variables' names.
- **Checks.**
  - Names match `/^[A-Za-z_][A-Za-z0-9_]{0,127}$/` (`NAME_RE`), do not look like a key, and are not in `FORBIDDEN_NAMES`. These cover the sign-in tokens of subscriptions (`CLAUDE_CODE_OAUTH_TOKEN`, `CODEX_ACCESS_TOKEN`, …), program lookup and loading (`PATH`, `LD_*`, `DYLD_*`, `NODE_OPTIONS`, …), shells, proxies and TLS, `GIT_*`, `XDG_*`, `WORKBENCH_*`, Claude Code's and Codex's session markers and folders, and the editor's variables, each with why. Names are compared in upper case; a name ending in `*` stands for a prefix.
  - Values are trimmed, 1 to 2,000 characters (`MAX_VALUE`), one line, with no NUL.
  - Labels are 1 to 80 printable characters (`MAX_LABEL`), and must not look like a key.
  - At most 20 names per key (`MAX_NAMES`), and 50 keys (`MAX_KEYS`).
  - `add()` is tolerant of what callers leave out: the preset defaults to `custom`, the label to the preset's (for `custom`, the first name, "and N more"); an empty value of an optional field is left out; a field's `also` names get its value, and the other way round. A name is secret when its preset field is (a caller cannot make a preset's secret field visible), when `secretNames` lists it, when it is not a preset field and `secretNames` was not given, or when its value looks like a key. `scope` is `'all'`, `{ kind: 'all' }` or `{ kind: 'repo', root }` with an absolute root, kept as its real path; the bare string `'repo'` is refused. `agents` is `'all'`, ids, or `[]`: no agent ("git only", for GitHub); left out, it is the preset's.
  - Errors are `Error`s with `.plain = true`, `.why` (`name`, `value`, `forbidden`, `too-many`, `store`) and a plain `.message`. A name or label refused for its shape is never repeated: it may be a key typed into the wrong field. `.detail` holds facts only (`security save: no-window, exit 1`), never a program's stderr.
- **Use.**
  - `load()` reads every value once. It never throws, and with no keys it starts no program and writes nothing.
  - `envFor({ repoRoot, harness })`: the keys for this repository (compared after realpath) and for all repositories, given to this harness or to all agents; `repoRoot: null` gives the keys for all repositories only. On a clash the more specific key wins (one repository over all, one agent over all agents), then the later one. Forbidden names are skipped again, even if keys.json was edited by hand.
  - `values()`: the secret values in memory, and those of keys removed in this run (a running agent may still hold them).
  - `maskSecrets(text, values)` replaces each value of 8 or more characters, and its JSON-escaped form (so a raw line of JSON stays JSON), with `shownValue(v)`: "•••• " and its last 4 characters (values of 12 or more, when those 4 are plain printable ASCII), else "••••". It works longest first, in one pass, and returns `text` as it is when there is nothing to mask.
  - `add` and `remove` read keys.json again before writing, so two Workbenches on one home keep each other's keys; `list()` reads it and the values of keys it has not read yet. A value that cannot be deleted (a locked keychain or keyring) throws `why: 'store'` and keeps the key in the list, so it can be tried again; one already gone counts as removed.
  - `secret-tool clear` removes only unlocked items, and exits 1 saying nothing when it removed none, whether the item is locked or already gone (a lookup cannot tell them apart either: a dismissed prompt to unlock also finds nothing). So after a failed clear, `secret-tool search --all service "Workbench key" account <id>/<NAME>` (never `--unlock`: it lists items without unlocking them) decides: an item still listed refuses the remove ("… because your keyring is locked."), none listed with nothing said counts as removed, and anything else refuses it. Search prints an unlocked item's value, so its output is only looked at, never kept or logged. (Not yet run on Linux: the stand-in follows secret-tool's source.)
- **Limits.** The keychain and these files protect keys at rest, and keep them out of repositories, logs, history and the page. They do not protect keys from agents: any program of the person's can read a `security`-made item without a prompt (env-secrets.md 5.4), and an agent gets the keys it is given in its environment. The panel says so.

## Presets and shapes (`src/shared/keypresets.mjs`, `src/shared/secretshape.mjs`)

Both are pure, with no `node:` imports. The page loads them as `/shared/…`.

- `KEY_PRESETS`: `anthropic` (ANTHROPIC_API_KEY, for Claude Code), `openai` (OPENAI_API_KEY, also CODEX_API_KEY, for Codex), `gemini`, `aws` (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN optional, AWS_REGION not secret and optional), `google-cloud` (GOOGLE_CLOUD_PROJECT not secret, GOOGLE_API_KEY optional), `azure`, `github` (GH_TOKEN, also GITHUB_TOKEN), `stripe`, and `custom` ("Other", no fields: the person types names and values). Each is `{ id, label, fields: [{ name, label, secret, optional, also? }], agents /* 'all' or ids */, note, link }`; `link` is https or null (only GitHub's is set). `presetById(id)` returns one, or null. `ANTHROPIC_KEY_NOTE` is the Anthropic note: "Claude Code will use this key instead of your Claude subscription, and each request is billed to the key."
- `signInVariables`: `NAME → { agents, sentence }` for the variables an agent's own sign-in reads (ANTHROPIC_API_KEY, the `CLAUDE_CODE_USE_*` switches, CODEX_API_KEY, OPENAI_API_KEY, GEMINI_API_KEY, GH_TOKEN, …). Agents not run yet are named by their ACP registry ids. The panel uses it to warn.
- `looksLikeSecret(text)` returns `{ secret, kind }`, kind one of `anthropic`, `openai`, `aws`, `github`, `slack`, `stripe`, `private-key`, `jwt`, `generic`. Text shorter than 16 characters, or not text, is not a key.
  - Known shapes, anywhere in the text, links included, each needing enough characters after its prefix: `sk-ant-`, `sk-proj-` and older `sk-` keys with a digit, `AKIA`/`ASIA` followed by 16, `gh[pousr]_`, `github_pat_`, `xox?-`, `xapp-`, `sk_`/`rk_` live and test, `whsec_`, `-----BEGIN … PRIVATE KEY`, JWTs, `glpat-`, `AIza`, `npm_`.
  - Otherwise, a long random word of 32 or more characters. Hex counts when it has digits and letters; a 40-character word alone is a commit id, and `sha256:` and `sha512-` digests are checksums. Base64 counts when it mixes lower case, upper case and digits the way random text does: the kind of character changes often, few vowels, little of it reads as words.
  - The path of a web address is not searched for random words: documents and pages are named there by long ids (Google Docs and Drive, Notion). Its query, and what comes before its host, are.
  - Paths, identifiers, sentences, links and commit ids are not keys. A refusal cannot be overridden, so the rule leans towards letting text through: about 1 random 32-character key in 25 is missed, and so is a random token in a link's path.

## Connect (`src/core/connect.mjs`)

`Connect` is the service behind the page's Agents & keys panel. It answers the `/api/connect*` routes (see "HTTP server"), and its `agents` event keeps the engine's list of agents that can start current. Nothing it returns, logs or emits holds a secret value or a vendor program's own words: its sentences are built from facts Workbench found itself.

```js
new Connect({ home, platform, env, keys /* KeyStore, loaded */, workspace /* workspace.mjs */, adapters /* { claude, codex } */,
              flags /* { claude: the --claude path or null } */, settingsPath /* <home>/.workbench/settings.json */,
              openTerminal /* terminal.mjs */, fetchJson /* (url, { headers }) => { status, json } */, log,
              repoRoot /* the repository Workbench works on, or null */, probe = true })
// emits 'agents' ({ claude: info, codex: info }) and 'changed' (anything the panel shows may have changed)
```

`connect.mjs` imports `maskSecrets` from `./keys.mjs` and `KEY_PRESETS` from `../shared/keypresets.mjs`, both statically. From the Claude adapter's `args.mjs` it imports `scrubEnv`, `withNodeOnPath`, `onPath` and `shellQuote`; from the Codex adapter, `buildEnv` and `codexBin`. Sign-in is then checked with exactly the program and environment an agent gets. A renamed or removed export stops `connect.mjs` from loading at all, and Agents & keys then answers 404.

**The agents** are a list, `AGENTS`, in the order "the first ready agent" goes through: Claude Code, then Codex (agents spoken to over ACP join it later). Each entry holds its name, its vendor's installer (a fixed line, see "Rules for all code"), the arguments of its own sign-in (`claude auth login`, `codex login`), the key preset "Use an API key" saves (`anthropic` with ANTHROPIC_API_KEY; `openai` with OPENAI_API_KEY and CODEX_API_KEY), and its probe.

**Probing** (`recheck({ repoRoot })`). A new Connect starts one probe at once, with the keys kept for `repoRoot` as well as those for all repositories, so a sign-in kept "for this repository" counts from the start; `probe: false` waits for the first `status()` or `recheck()` (the CLI's GitHub helpers pass it: no agent starts there). Calls made while a probe runs share one more probe after it. `status()` uses the last probe, and waits for the one under way when none has ended.

- **Claude Code.** First the adapter's `available({ env, claudePath })`. Then `claude auth status`, with the agent's environment: `withNodeOnPath(scrubEnv(env))` plus the keys the key store gives Claude Code in this repository. It runs from the home folder, never from a repository, whose own `.claude` settings could name a program for it to run, and has 10 seconds.
  - Its JSON is read, never its exit code (exit 1 means only that there is no claude.ai login). In Claude Code's own order: an `apiProvider` other than `firstParty`, or `authMethod: 'third_party'`, is "a cloud provider"; an `apiKeySource` other than `none`, or `authMethod` `api_key` or `api_key_helper`, is "an API key"; `loggedIn: true` is "your Claude subscription"; `loggedIn: false` is not signed in. Anything else is `unknown` (`claudeSignIn`).
  - The email address and organisation in the answer are never kept, and its output is never logged. The keychain item is never read.
- **Codex.** First the adapter's `available()`. Then `codex login status`, with `buildEnv(env)` plus Codex's keys, from the home folder, for 10 seconds. Exit 0 is signed in, with "an API key" or "your ChatGPT account" read from its words, which are never passed on; exit 1 is not signed in; anything else is `unknown`. A CODEX_API_KEY in that environment (a key saved here, or the person's own) also counts as signed in with "an API key": `codex exec` uses it, and `login status` may not report it.
- A check that times out, or gives an answer Workbench cannot read, is `signedIn: 'unknown'`. The agent still counts as ready, since an older Claude Code without `auth status` works; its sentence says so.
- **Ready** means the program runs and is not known to be signed out (`signedIn !== 'no'`).
- **`'agents'`** carries `{ claude: info, codex: info }`: each the adapter's own `available()` answer, plus `found`, `signedIn`, `how`, `ready` and, when known, `version`. `ok` is `ready`, and `reason`, when it is not ready, is the agent's sentence, never an adapter's reason (which can quote a vendor program). It is emitted after every probe, and after `setDefaultAgent` once a probe has ended; never as an empty map. A listener added after a probe has ended hears the last map on the next turn of the event loop (a `once` listener hears it once), so the engine never misses the first probe, however late it is wired.

**`status({ repoRoot })`** -> ConnectStatus. Agents come from the last probe; git, GitHub and the keys are read afresh.

```js
{ agents: [{ id, name, found, version, from, signedIn /* 'yes'|'no'|'unknown' */, how, ready, isDefault, sentence, actions }],
  defaultAgent, platform, canOpenTerminal /* platform === 'darwin' */,
  git: { name, email, sentence }, github: { connected, login, agentsUseIt, sentence },
  keys: [/* KeyStore.list() entries, each with a sentence */], ready /* some agent is ready */ }
```

- `from`, in words: "the VS Code extension", "your PATH", "the path given with --claude", "WORKBENCH_CLAUDE_BIN" or "WORKBENCH_CODEX_BIN"; null when the program was not found. `version` is a version number or null. `how` is "your Claude subscription", "an API key", "a cloud provider", "your ChatGPT account" or null.
- The agent sentences: "Claude Code 2.1.322 is ready, signed in with your Claude subscription." ("… with an API key", "… with a cloud provider"); "Codex 0.166.0 is installed but not signed in."; "<Name> <version> is installed, but Workbench could not check whether it is signed in."; "Codex is not installed."; "Claude Code is at <path>, but it could not be started."; and, for a path given with `--claude`, `WORKBENCH_CLAUDE_BIN` or `WORKBENCH_CODEX_BIN` that is not there, Workbench's own "Claude Code is not at <path>, the path in WORKBENCH_CLAUDE_BIN." and the like.
- `actions`, in this order: `signin` when it runs and is not known to be signed in; `install` when it does not run; `key` when it runs; `default` when it is ready and not the default; always `recheck`.
- `git.sentence`: "Git knows you as <name>, <email>."; "Git does not know your name and email yet." (or "… your name but not your email yet.", "… your email but not your name yet."); "This repository has its own name and email for git. Save yours here to use them everywhere." when only the repository's config has them; "Workbench could not read git’s settings.".
- `github.sentence`: "Connected to GitHub as <login>." or "Not connected.". `agentsUseIt` is whether the connection's key goes to all agents.
- `keys` leaves out the GitHub connection's own key, which shows under GitHub. A key for one repository has `scope: { kind: 'repo', root, here }`, `here` saying whether it is the repository asked about, its real path compared as `envFor` compares it (a copy: the store's own entry is not changed). Each key's sentence reads "AWS for all repositories, given to all agents: AWS_ACCESS_KEY_ID •••• 7QXA, AWS_SECRET_ACCESS_KEY •••• 9f2b"; scope reads "this repository" (from `here`) or "the repository at <root>", agents "all agents", "Claude Code and Codex" or "no agent". (The page words keys itself, from the same facts.)

**The default agent.** `defaultAgent()` is synchronous: the person's choice when that agent is ready, else the first ready agent of the list, else null. Before the first probe ends it is undefined: Connect cannot tell yet, and the engine reads that as "use your own check", where null means no agent is ready. `setDefaultAgent(id)` keeps the choice in settings.json and answers "New work will go to Codex." or "New work will go to Codex once it is ready.".

**Install and sign in** (`agentAction(id, 'install'|'signin')`).

- On macOS, Terminal opens through `openTerminal`: the installer as `{ program: '/bin/sh', args: ['-c', <installer>] }`; the sign-in as `{ program: <the full path the probe found>, args: ['auth', 'login'] or ['login'] }`, since Terminal's shell has the person's own PATH. The answer is `{ ok: true, opened: true, sentence }`: "Terminal is installing Claude Code. When it finishes, come back here." or "Terminal is open for you to sign in to Claude Code. When you are done, come back here.".
- Elsewhere, or when Terminal could not be opened, the answer is `{ ok: true, opened: false, command, sentence }`: `command` is the line to run (the installer, or `claude auth login` with the bare name when the program was found on the PATH, else its full path, quoted for the shell where needed), and the sentence says to run it in a terminal, then check again.
- Refused: an unknown agent ("Workbench does not know that agent.", `why: 'agent'`, 404), an unknown action (`why: 'action'`, 400), and signing in to an agent that is not installed ("Claude Code is not installed yet, so there is nothing to sign in to.", `why: 'not-installed'`, 409).

**Keys.**

- `setAgentKey(id, value)` ("Use an API key") saves the trimmed value for all repositories, for that agent only, in place of the key this button saved before (the same preset, scope all, agents exactly `[id]`), probes again, and answers "Claude Code will use this API key from now on, and each request is billed to it." (or Codex's). An empty value is refused: "Paste the key first.".
- `addKey({ preset, label, values, secretNames?, scope, agents, repoRoot? })` passes the key to the key store, then probes again, since a key can change how an agent signs in. The preset must be one of `KEY_PRESETS` (`custom` when none is given): any other is refused, "Workbench does not know that kind of key." (`why: 'name'`). Values left empty are dropped; a field the preset needs and is missing is refused ("<NAME> is needed."); a field's `also` names get its value; without `secretNames`, secrecy comes from the preset (a field with `secret: false`, such as AWS_REGION, is shown), and names the preset does not know (custom keys) are secret. `scope` is `'all'`, `'repo'` (`repoRoot`, else the repository `status()` was last asked about) or the store's `{ kind, root }`. `agents` left out is `'all'`.
- `removeKey(id)` passes through and probes again. The GitHub connection's key disconnects GitHub; when that fails, the answer is `disconnectGithub()`'s, with `removed: false`.
- `envFor({ repoRoot, harness })` is the key store's `envFor`, synchronous, from its cache. `mask(text)` is `maskSecrets(text, keys.values())`.

**Git and GitHub.**

- `setGitIdentity({ name, email })` saves through `workspace.setGitIdentity` and answers "Git will make your merges as <name>, <email>.".
- `connectGithub(token, { agentsUseIt })`:
  1. It asks GitHub whose the token is: `GET https://api.github.com/user` with `Authorization: Bearer`, no redirects. The login must look like a GitHub login.
  2. It keeps the token in the key store under preset `github`, label `GitHub`, as GH_TOKEN and GITHUB_TOKEN, for all repositories. Agents get it (`agents: 'all'`) only with `agentsUseIt: true`; with `false`, `agents: []`: git only. Left out (undefined), it keeps what the connection has now (settings.json read afresh), and a first connection is git only.
  3. It records `{ login, keyId }` under `github` in settings.json; the token is never written there. When settings.json cannot be written, the key just kept is removed again (so no agent gets a token the panel does not show as GitHub's), and the refusal is thrown ("Workbench could not save its settings.", 500). An earlier connection's key goes, and git forgets an earlier login (`rejectGitCredential`).
  4. It gives the token to git with `approveGitCredential`.
  - The answer is `{ ok: true, login, sentence: 'Connected to GitHub as <login>.' }`. When git has nowhere to keep it, the sentence adds "Git on this computer has nowhere to keep sign-ins, so it cannot use the token to clone private repositories."; when git failed, "Git could not keep the token, so cloning private repositories may not work.". When the earlier key could not be removed, it adds "Workbench could not remove the token it kept before[, so agents still get it]: it is listed under Keys for your agents, where you can remove it."; when git could not forget an earlier login, "Git could not forget your sign-in as <login>, so it may still use that account’s token.".
  - A token GitHub refuses, or no network, keeps nothing and answers `{ ok: false, why, sentence }`: `token` ("GitHub did not accept that token. Check that you copied all of it, then try again."), `github` for a 403 or 429 ("GitHub refused the request for now. Try again in a few minutes.") or any other answer ("GitHub gave an answer Workbench did not expect, so the token was not kept."), `network` ("Workbench could not reach GitHub. Check the internet connection, then try again.").
  - A value that cannot be a token (empty, holding white space or control characters, or longer than 255) is refused: "That does not look like a GitHub token." (`why: 'value'`).
- **The connection's token** is read back from the key store, from memory (`keys.valuesOf(keyId)`: GH_TOKEN, else GITHUB_TOKEN), also when no agent gets it, and also in a run of its own (the Mac app's `--github-repos`). It is null when the store could not read it (a locked keychain, a missing file).
- `setGithubAgentsUseIt(on)` ("Let agents use this token") gives the connection's token to every agent, or to none, without asking for it again: it keeps the token again with the other choice, in place of the earlier key. It answers "Agents can use your GitHub token now, as GH_TOKEN." or "Agents no longer get your GitHub token. Git still uses it.". When the token cannot be read back: `{ ok: false, why: 'token', sentence: 'Workbench could not read the GitHub token it keeps, so this cannot change. Disconnect GitHub, then connect it again.' }`. When GitHub is not connected, it is refused ("GitHub is not connected.", `why: 'github'`, 409).
- `disconnectGithub()` reads settings.json afresh, makes git forget the sign-in (`rejectGitCredential`), then removes the key, then clears `github` in settings.json, and answers "GitHub is disconnected. The token itself still works until you delete it on GitHub.". Git goes first, and it stops at the first failure, keeping the key and `github` in settings.json: the panel then still shows GitHub connected, with Disconnect to try again (git's reject is safe to repeat). The answer is `{ ok: false, why, sentence }`, saying what is still kept:
  - `git`: "Git could not forget your GitHub sign-in. GitHub is still connected, and agents still get your GitHub token until it is removed. Try again." ("…, and Workbench still keeps your GitHub token." when no agent gets it);
  - `store`: the key store's own sentence (when it is `.plain`), such as "Workbench could not remove the key from your keychain, because your keychain was not unlocked.", then the same.
- `githubRepos()` -> `[{ fullName, cloneUrl, private, pushedAt }]`, most recently pushed first, from `GET /user/repos?per_page=100&sort=pushed`, asked with the connection's token. Entries must have a `full_name` like `owner/name` and the `clone_url` `https://github.com/<full_name>.git`; others are left out. No connection, no token, or any failure gives `[]`.

**Errors.** A refusal is thrown as an `Error` with `.plain`, `.why`, `.sentence` (its message) and `.status`: 400, 404, 409, or 500 for "Workbench could not save its settings.". The key store's own errors (`.plain`, `.why`, a plain message) pass through with a `.status` set by their `.why`: 400 for `name`, `value`, `forbidden` and `too-many`, 500 for `store` (the place keys are kept failed). Outcomes that are not the request's fault (`connectGithub`, `setGithubAgentsUseIt`, `disconnectGithub`) are answered as `{ ok: false, why, sentence }`.

**settings.json** (`~/.workbench/settings.json`, mode 0600, its folder made 0700 when missing, written to a temporary file then renamed) holds `defaultAgent` and `github: { login, keyId }`. Other keys are kept as they are.

## Terminal (`src/core/terminal.mjs`)

`openTerminal({ title, program, args }, { platform, tmpDir, open, keepMs })` -> `{ opened }`, for the steps only the person can do: a vendor's own sign-in, or its installer. The second argument is for tests.

- **On macOS** it writes a script into a new private folder (`mkdtemp` under the temporary folder, mode 0700): `<title>.command`, mode 0700, its name keeping only plain characters. The script runs `clear`, prints the title on one line (control and direction-changing characters become spaces), runs the program with every word quoted by `shellQuote` from `claude/args.mjs`, then prints "You can close this window.". `open -a Terminal <file>` opens it, with an argument array. Terminal reports nothing back: the page checks again when it gets focus.
- The folder is removed after 10 minutes (`KEEP_MS`) or when Workbench exits, whichever comes first, and at once when Terminal could not be asked.
- **Elsewhere** nothing is written or opened, and the answer is `{ opened: false }`: the caller shows the command.
- A program name or a word holding NUL, or arguments that are not strings, are refused before anything is written. `terminalScript()` builds the script on its own.
- Every word the script runs is quoted, so nothing in a title, a path or an argument is read as shell syntax. The one shell line that runs is an installer: Workbench's own fixed text, given to `/bin/sh -c` as one quoted word (the second exception in "Rules for all code").

## Simulator and machines

- `src/adapters/sim/simulator.mjs` exports `class Simulator { constructor({ emit, now, speed, seed }); seedWorld(); createRunner(opts); onAnswer(agentId, ask, answer); tick(now) }`, plus `harness = 'sim'` and `available()`.
  - `seedWorld()` emits a starting world close to the approved mockup. Roots: Checkout fix (needs your OK; 2 finished helpers), Search cleanup (question), Flaky test (maybe stuck; 1 helper), Invoice export (done and checked; one rule broken), Help pages (says it is done) and Onboarding (working, with 2 helpers working).
  - Every working agent keeps producing believable plain-language activity, tokens, cost, thinking blips, plan progress and helpers coming and going. It is deterministic for a given seed.
  - New tasks get a scripted tree: plan, 1 to 3 helpers, work, sometimes a permission ask, then a finish.
  - Answers move scripted agents on, by the engine's rules. `onAnswer` settles the agent's own ask only when `ask.id` names it; with no ask it is a message (`say`). A permission allows only on "Allow"; any other words are a no, so a yes with conditions is one. A stuck agent stops only on "Stop it" (or "stop"); other words are a hint.
  - A simulated agent that has stopped or failed cannot be picked up again: its runner's `send` rejects with a plain error ("Checkout fix has stopped, so it cannot take messages."), which the engine passes on as the reply ("Continue" and "Try again" in the demo), and the agent stays as it is.
  - **Its git repository** (made once, from its own seeded stream: the same seed and clock give the same graph; nothing touches a real repository). It is "storefront" on `main`, with 2 uncommitted changes and a name and email git knows: 25 commits by "you" over six days, and two agents from earlier today ("Payment retry", "New search page") whose work commits, authored with the agent's name, were joined into main by merge commits by "you". Every root gets a branch `workbench/<slug>-<id>` (seeded roots at the newest main commit at or before they started, new ones at main's tip) and an `agent.work` with `from: 'main'`; helpers get none. Messages and trailers are written as `workspace.mjs` writes them, and read back by the same rules; commit ids are 40 hex characters. Every demo root also emits `agent.files` (what it has not merged) just before each turn ends, as the receipt does in live mode.
  - **Its optional git methods**, which the engine calls in demo mode when they are there:
    - `gitGraph({ views?, limit = 200 })`: `{ ok: true, head, branch, repo: { name, branch, head, dirty, identity }, commits, more, agents }`, both the engine's shape and `workspace.gitGraph`'s at once; `views` (AgentViews, a Map of them, or an id-to-view function) give the name, state, files and work the page shows. Read-only: it emits nothing, uses no randomness and moves no time.
    - `changes(agentId, { maxFiles = 300 })`: `workDiff`'s shape, whose patches git reads (`git apply --numstat`) with exactly those counts, the same text for the same work; refusals `{ ok: false, reply }` ("That agent is not part of the demo.", "<Name>’s work was thrown away, so there is nothing to show.").
    - `proposeMerge(agentId, { state, view })`: the card's fields (`sentence`, `detail` in the engine's words ending "This is the demo, so nothing is really merged.", `yes`, `no`, `danger`, counts) and `expect: { workId, into, intoHead }`, or a refusal `{ ok: false, why?, reply }`; it never merges. `merge(agentId, { expect, view })`: W on its branch, then M with parents [main, W] even when a fast-forward was possible; main moves to M and `since` becomes W; it emits `agent.work` and `agent.files` as a real merge does. It always succeeds, except for Help pages: "Help pages’s work does not merge cleanly into main." (`docs/help/billing.md`), until a message that mentions conflicts, "bring in" or "merge" (the lid's "Ask it to bring in main") makes it merge main into its branch on its own; its next merge then goes through.
    - `proposeDiscard(agentId, { state, view })` and `discard(agentId, { expect, view })`: the throw-away card and the throw-away (an agent at work is stopped first, a finished one's idle process closed), with `agent.work` `{ branch: null, folder: false, problem: null, thrownAway: { at, saved } }`; after it, messages are refused ("<Name>’s work was thrown away, so it cannot continue.").
- `src/core/machines.mjs` exports `class Machines extends EventEmitter { constructor({ demo }); list(); setAwake(id, awake); refresh(agentCountsByMachine) }`.
  - "Your laptop" is real: CPU from `os.loadavg()[0] / os.cpus().length`, memory from `os.totalmem()` and `os.freemem()`.
  - Demo mode adds Cloud 1 (awake, idle), Cloud 2 (asleep) and Cloud 3 (awake, 1 agent), each at 0.40 USD an hour while awake, with `simulated: true`.

## HTTP server (`src/server/http.mjs`)

`createServer({ engine, store, token, hookTokenFor, connect, repoRoot, port, host: '127.0.0.1', rootDir, log, options })` returns `{ listen() -> Promise<{ url }>, close() }`. `hookTokenFor(agentId)` gives each agent's own hook token (64 hex characters). `connect` is the Connect service, for the Agents & keys routes (see below); without it (the demo, or when `connect.mjs` could not load) they answer 404. `repoRoot` is "this repository" for keys; without it the server uses the engine's `repoInfo.root`. `options.keyPresets` stands in for `src/shared/keypresets.mjs` in tests (`null`: it could not be read).

**Static files:**

- `GET /` serves `ui/index.html`.
- `GET /ui/<file>` serves from `ui/`.
- `GET /shared/<file>.mjs` serves from `src/shared/`.
- No directory listing and no path traversal (resolve the path and require it to stay inside the root).
- `Content-Type` comes from the file extension.

**API:** JSON in and out. The token goes in header `X-Workbench-Token`, or in query `t` for GET routes only.

| Route | Does |
|---|---|
| `GET /api/state` | `engine.snapshot()` |
| `GET /api/stream` | SSE. `event: snapshot` on connect (and again when an earlier agent is forgotten: the store's `removed` event), then `event: agents` (AgentView[] for changed ids, coalesced every 250 ms), `event: machines`, `event: notice` (`{ text }`), `event: repo` (the person's repository, `{ name, head, branch, dirty, identity }`, whenever the store emits `repo`: a merge moved their branch, or a refresh found a new head, branch, number of uncommitted changes or identity), and a `: ping` comment every 15 s. On Connect's `agents` and `changed` events every page gets a fresh `event: snapshot`, once per burst (`coalesceMs`), and only when the snapshot's `harnesses`, `harnessInfo`, `connect` or `meta.connect` changed since the last snapshot a page was sent: that keeps the top band's Agents & keys light and the lid current |
| `GET /api/git` | `engine.gitGraph()`: the git screen's data |
| `GET /api/agents/:id/changes` | `engine.changes(id)`: one agent's diff |
| `POST /api/agents/:id/merge` `{ state }` | `engine.proposeMerge(id, { state: optState(b.state) })`: a merge card, or a refusal |
| `POST /api/agents/:id/discard` `{ state }` | `engine.proposeDiscard(id, { state: optState(b.state) })`: a throw-away card, or a refusal |
| `POST /api/command` `{ text, focusId, confirmId, askId }` | `engine.command`. Each id that is not an id string (`[A-Za-z0-9_-]{1,80}`) is passed as null |
| `POST /api/confirm/:id` `{ go }` | `engine.confirm`: the only route that merges or throws away, after a card |
| `POST /api/agents` `{ task, harness, model, machineId, budgetUsd }` | `engine.startAgent` |
| `POST /api/agents/:id/answer` `{ askId, answer }` | `engine.answer`. An `askId` that is not an id string is passed as null |
| `POST /api/agents/:id/say` `{ text }` | `engine.say` |
| `POST /api/agents/:id/stop` | `engine.stop` |
| `POST /api/machines/:id/awake` `{ awake }` | `engine.setMachineAwake` |
| `POST /hook/pretool` `{ agentId, payload }` | `engine.hookPreToolUse`; may wait for minutes. Takes the page token, or that agent's own hook token |
| `GET /api/connect` | Agents & keys: `{ ok: true, sentence: null, status }` |
| `POST /api/connect/recheck` | `connect.recheck()`, then the status (`sentence: null`) |
| `POST /api/connect/agents/:id/install`, `…/signin` | `connect.agentAction(id, action)`. The answer adds `opened` (boolean), and `command` when Connect gave one (outside macOS, or when Terminal could not open), for the page to show. `:id` is `[a-z][a-z0-9-]{0,39}`, else 404; Connect refuses ids it does not know |
| `POST /api/connect/agents/:id/key` `{ value }` | `connect.setAgentKey(id, value)`, the value trimmed. A missing or blank value: 400 "Paste the key first." |
| `POST /api/connect/agents/:id/default` | `connect.setDefaultAgent(id)` |
| `POST /api/connect/git` `{ name, email }` | `connect.setGitIdentity({ name, email })`, each trimmed text (anything that is not a string becomes `''`). Without a sentence from Connect: "Git now has your name and email." |
| `POST /api/connect/github` `{ token, agentsUseIt }` | `connect.connectGithub(token, { agentsUseIt: agentsUseIt === true })`. The answer adds `login`. A missing token: 400 "Paste the code GitHub made for you first." |
| `POST /api/connect/github/agents` `{ agentsUseIt }` | `connect.setGithubAgentsUseIt(agentsUseIt)`, with no token. `agentsUseIt` must be a boolean, else 400 "Choose whether agents may use the GitHub token.". When the token cannot be read back the answer is `ok: false`, with `why: 'token'` and its sentence; 409 when GitHub is not connected |
| `POST /api/connect/github/disconnect` | `connect.disconnectGithub()`. The default sentence: "Workbench is no longer connected to GitHub." |
| `POST /api/connect/keys` `{ preset, label, values, scope: 'all'\|'repo', agents: 'all'\|[ids] }` | `connect.addKey(…)` (see below). The default sentence: "Saved <label>, for this repository." or "…, for all repositories." |
| `POST /api/connect/keys/:id/remove` | `connect.removeKey(id)`: "Removed the key.", or "That key was already gone." when `removed` is false |

`optState` gives a state name from `STATE` (`states.mjs`), else null: anything else is as if nothing was sent. The merge and throw-away routes only ever answer with a card or a refusal; the work moves only on `POST /api/confirm/:id { go: true }`. Every card in a reply (from these routes and from `/api/command`) is `{ id, sentence, detail, kind, yes?, no?, danger?, agentId? }` (`agentId` on merge and throw-away cards only), and a reply to `/api/command` may carry `review` (an agent id: the page opens the git screen on it). Replies to `/api/command`, `/api/confirm/:id`, `/say` and `/answer` may carry `openConnect: true`: the page opens Agents & keys. A wrong method on a known route gets `405` with an `Allow` header. `close()` also takes the stream's `repo` listener off the store, and its `agents` and `changed` listeners off Connect.

**The Agents & keys routes** (`/api/connect*`) carry keys, so:

- Each answers `{ ok, sentence, status }` with status 200, where `status` is a fresh `connect.status({ repoRoot })` and `ok` is false only when Connect answered `ok: false` (a refusal the panel says, with its status drawn). Otherwise the answer is `{ error }` with a plain sentence and a 4xx code, or 500 (see "Errors" below). Without Connect, every one answers 404: in the demo "The demo’s agents are simulated, so there is nothing to connect. Run Workbench on a repository to connect your own agents and keys.", otherwise "Agents & keys is not available in this Workbench. The details are in its log."
- Bodies are at most **16 KB** (a 413 says "The limit is 16 KB."). Keys come only in a POST's body, never in an address, and are never echoed or logged: before an answer or a log line goes out, every string of 8 or more characters the request carried as a key (`value`, `token`, each of `values`) is replaced with "••••". Bodies are never logged.
- Errors: an error with `.why`, `.plain` or `.expose`, or the server's own, is a refusal, answered with its message and its status (4xx, or 500 when the place keys are kept failed, which the log notes too), or 400 when it has none. `.detail` is never sent or logged. Anything else is logged ("Agents & keys could not do that: <stack>", keys cut out) and answers 500 with the usual sentence.
- **Adding a key** (`POST /api/connect/keys`). The server decides first, and in its own words, before Connect and the key store check again:
  - the preset: an id `[a-z][a-z0-9-]{0,39}` that `presetById` knows ("Choose what kind of key this is.", "Workbench does not know that kind of key.");
  - names `^[A-Za-z_][A-Za-z0-9_]{0,127}$` (never `__proto__`), each value text; values are trimmed and empty ones left out ("Fill in the key first." when none is left);
  - for a preset with fields, only its names ("AWS keys take only AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN and AWS_REGION."), every required field ("Fill in AWS_SECRET_ACCESS_KEY."), and a field's value under its `also` names when the page did not send them;
  - which values are secret comes from the preset, never from the page: each field marked secret, with its `also` names. A `custom` key, or any key when the presets could not be read, keeps every value as a secret;
  - `scope` is `'all'` or `'repo'`, which becomes `{ kind: 'repo', root: <the server's repoRoot> }`, the key store's own shape, with that root also passed as `repoRoot` (a root in the body is ignored; with no repository: "Workbench is not working on a repository, so the key can only be for all repositories."); `agents` is `'all'` or 1 to 20 agent ids; the label defaults to the preset's, else "Key".

**Safety, all required:**

- Listen on `127.0.0.1` only.
- The token is 32 random bytes as hex. Compare it in constant time.
- Every `/api` and `/hook` route needs the token. `/hook/pretool` also takes the asking agent's own hook token: once the body is read, it must equal `hookTokenFor(body.agentId)` (compared in constant time). Anything else gets `401 Missing or wrong token.` and the engine never sees it. A hook token never opens `/api`.
- `Host` must be `127.0.0.1:<port>` or `localhost:<port>`.
- POSTs need `Content-Type: application/json`, a body of at most 64 KB (16 KB on the Agents & keys routes), and an `Origin` that is absent or equal to the server's own origin.
- Every JSON answer carries `Cache-Control: no-store`.
- The page (any `.html` file served) with a query is served only when the query's `t` is the token. Anything else (`/?static=1`, `/?t=<wrong>`, `/ui/index.html?…`) gets `303` to `/` with `Cache-Control: no-store`. Any website can send the person's tab to an address here, so the address must not be able to change what the page does or replace the key the tab holds. Queries on other files (`/ui/app.js?v=2`) are unaffected.
- Responses carry `Content-Security-Policy: default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self'`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. No CORS headers.

## CLI (`bin/workbench.mjs`)

```
node bin/workbench.mjs --demo [--port 4317] [--no-open] [--app]
node bin/workbench.mjs --repo <path> [--budget 2] [--model <name>] [--claude <path>] [--port 4317] [--no-open] [--app]
node bin/workbench.mjs --clone <address> [--into <folder>] [the --repo options]
node bin/workbench.mjs --connect-github | --github-repos          (for the Mac app)
```

The repository root's `npm run demo` and `npm run dogfood` (Workbench on its own repository) run the first and the second. `npm run app` builds and installs the Mac app (see "The Mac app").

- Prints `Workbench is running at http://127.0.0.1:<port>/?t=<token>`.
- Opens the browser with `open` (macOS) or `xdg-open`, unless `--no-open`.
- `--port 0` picks a free port.
- **`--app`**, for the Mac app: no browser, as with `--no-open`. After "Press Ctrl-C to stop." it prints one more line, `WORKBENCH_APP {"url":…,"repo":…,"root":…,"demo":…}`: JSON with the page's address and its key, the repository's name and folder (null in the demo), and whether it is the demo. From then on it reads its standard input, and when that ends or fails (the app quit, or crashed), Workbench stops as on Ctrl-C. `test/workbench-cli.test.mjs` pins the line and the stop. `test/live-fake.test.mjs` checks that a crash, where the input ends and nothing reads Workbench's output any more, ends the agent and its hook as quickly as Ctrl-C does.
- Exits with a plain-language message when live mode has neither `--repo` nor `--clone`: "Workbench needs a git repository to work on. Run it with --repo <path to a git repository>, copy one with --clone <address>, or try it with simulated agents using --demo."
- **No Workbench inside an agent.** Every agent (and every check Workbench runs for one) has `WORKBENCH_AGENT_ID`. When it is set, even to an empty string, live mode, `--clone` and the GitHub helpers (which reach the person's keys and accounts) are refused before any module loads: "Workbench is running inside an agent. It will not start real agents from there." on stderr, exit code 2. An agent working on this repository could otherwise start a second Workbench whose real agents run on the person's login unseen. `--help`, argument errors and `--demo` still work, and `scripts/accept-real.mjs` refuses with the same sentence and exit code. It guards against accidents, not a determined agent: code it runs can delete the variable first.
- **`--claude <path>`**: the Claude Code program. Without it: `WORKBENCH_CLAUDE_BIN`, then `claude` on the PATH, then the newest Claude Code extension in VS Code, VS Code Insiders or Cursor (see "Binary" in the Claude Code adapter). The CLI wraps the adapter so that `available()` and `createRunner()` get it as `claudePath`, and every launch looks Claude Code up again from it. A missing value: "--claude needs a value."; a blank one: "--claude needs the path of the Claude Code program." (both exit 2, with the usage).
- **Start lines** (live mode): "Claude Code 2.1.322 is ready (from the VS Code extension)." ("(from --claude)" for the flag, "(from WORKBENCH_CLAUDE_BIN)" for the variable, nothing for the PATH; with `--verbose` the program's path is logged too), or "Claude Code is not available: <reason>"; the same for Codex. A reason gets a full stop of its own only when it does not already end in ".", "!" or "?", so no line ends in two. When neither can run, a third line follows, "No coding agent is ready yet. Open the page to connect one.", and Workbench starts as usual: the page's Agents & keys connects one. Every loaded adapter that is complete (it has `available` and `createRunner`) goes to the engine, ready or not; the engine asks each at `start()` unless Connect has spoken of it, and one installed or signed in later can start without a restart. After the spending line, when `gitIdentity` finds no name and email: "Git does not know your name and email yet. Agents can work, but Workbench cannot merge their work until you set them: git config --global user.name "Your Name" and git config --global user.email you@example.com".
- Agents and checks get node on the PATH when theirs has none (see the Claude Code adapter's "Node on the PATH"), so a Workbench started by a node that is not on the PATH still gives them a working `npm test`.
- **`~/.local/bin` on the PATH** (`pathWithLocalBin`). Right after the check for an agent, and before anything loads, `~/.local/bin` is added to the end of Workbench's own PATH when it is not on it yet, even before that folder exists; an empty PATH, or a home folder that is not an absolute path, leaves PATH as it is. Both agents' installers put their programs there, so Agents & keys' Check again finds a program installed while Workbench runs, and agents and checks can run it. It goes at the end, so a program the PATH already finds keeps its place. (The Mac app adds that folder too, when it exists.)
- **Keys and Agents & keys** (live mode). After `prepareRepo` and `gitIdentity`, the CLI loads `src/core/keys.mjs` and `src/core/connect.mjs` (`loadOptional`: either may be missing or fail to load, and Workbench then runs as before without them, saying so in its log).
  - It makes `new KeyStore({ home, platform, log })` and awaits `keys.load()`; a failure is logged, and agents start without keys.
  - It makes `new Connect({ home, platform, env: process.env, keys, workspace, adapters: { claude, codex }, flags: { claude: <--claude or null> }, log })`, with the raw adapter modules. Connect probes the agents at once.
  - From then on the log (`log.setMask`) and everything Workbench prints go through `connect.mask`.
  - `connect` goes to the engine and to `createServer` (with `repoRoot`), and `connect.on('agents', map => engine.setHarnesses(map))` keeps the engine's list of agents that can start current.
- **`--clone <address> [--into <folder>]`** (`cloneFirst`) clones first, then goes on as `--repo <the new folder>`.
  - `--into` defaults to the current folder, expands a leading `~`, and is made when missing. The clone runs through `workspace.cloneRepo({ url, into, onProgress, timeoutMs: 30 minutes, signal })`.
  - Progress in a terminal: "Cloning <address> into <folder>…", then "Counting what to copy: 10%", "Packing it up: …", "Copying: 30%", "Unpacking: …" and "Writing the files: …" (a line when a part begins, then every quarter), and last "Cloned <address> into <folder>.". With `--app`, progress comes only as `WORKBENCH_CLONE {"phase","percent"}` lines, one per change, the percent a whole number; "Cloning …" comes before them, and after a clone `WORKBENCH_CLONE {"phase":"done","percent":100,"root"}`, then "Cloned …".
  - The address is printed without any `user:password@` and with control characters shown as "?". A password in it (the part after "user:", or a user name alone, which may be a token), when it has 8 or more characters, is cut out of every sentence and log line; a shorter one would cut ordinary words out, and `cloneRepo` refuses an address with a password before git runs.
  - On failure: one plain sentence on stderr, with `--app` also `WORKBENCH_CLONE {"error","sentence"}`; exit 1, and nothing starts. `error` is `cloneRepo`'s `.why` when it is `auth`, `network`, `exists` or `url`, else `git`. An error with no `.why` reads "Git could not clone <address>. The details are in Workbench’s log.", git's words going to the log. Without `cloneRepo`: "This Workbench cannot clone a repository. Clone it with git, then open its folder."
  - **Stopping.** Ctrl-C, SIGTERM (the app's Cancel or Quit) or SIGHUP while git copies, and with `--app` standard input ending (the lifeline, from the clone on), stop the clone. Workbench says so once ("Stopped copying the repository.", or "The app closed, so Workbench stopped copying the repository."), aborts `cloneRepo`'s `signal`, which ends git's whole process group and removes what it made, and exits 1; nothing starts. Should that take longer than 4 seconds, Workbench leaves anyway, and its exit kills git and removes the folder (see `cloneRepo`). If standard input ends while Workbench starts after the clone, Workbench stops as soon as it has started.
  - **A busy port** after a clone: the page takes a free one and says "Port 4317 is already in use, so the page took a free one.", since a retry would clone again.
- **`--connect-github`** reads one line from standard input, the token (at most 8 KB, waiting at most 5 minutes), runs `connect.connectGithub(token, { agentsUseIt: false })`, prints `WORKBENCH_GITHUB {"ok","login","sentence"}`, and exits 0 when GitHub took the token, else 1. No token: "Paste a token from GitHub first."; a refusal with `.why`: its sentence; anything else: "Workbench could not connect to GitHub. The details are in its log.". Connect's mask does not know the token before it is kept, so while this runs the token is cut out of the log and of everything printed, Connect's own log lines included.
- **`--github-repos`** prints `WORKBENCH_GITHUB_REPOS [{ fullName, cloneUrl, private }]` and exits 0. The list is `[]` when GitHub is not connected, or anything fails (logged).
- Both helpers run on their own, before the other modules load: only the key store and Connect, made with `probe: false` and no adapters (Connect uses its own workspace module), so no agent program is asked anything. With `--demo`, `--repo` or `--clone` they are an argument error, and so is using both.
- **Argument errors** (exit 2, with the usage), besides the old ones: "--clone needs the address of a repository, like https://github.com/owner/repo.", "--into needs the folder to put the copy in.", "Choose one: --repo for a repository on this computer, or --clone to copy one first.", "Choose one: --demo for simulated agents, or --clone to copy a repository and run real agents on it.", "--into says where --clone puts the copy, so it needs --clone.", "Choose one: --connect-github or --github-repos.", "--connect-github runs on its own, without --demo, --repo or --clone." (and the same for `--github-repos`).
- Run as a program (the real path of `process.argv[1]` is this file), `bin/workbench.mjs` starts at once. Imported, it starts nothing and exports `parseArgs`, `createLogger` (with `setMask` and `getMask`), `displayUrl`, `pathWithLocalBin`, `cloneFirst`, `connectGithubMode`, `githubReposMode`, `readLine` and `USAGE`, for its tests.
- **Output nobody reads any more is let go:** stdout and stderr ignore write errors. When the Mac app crashes, or the program reading a pipe ends, each write fails (EPIPE). Unheard, each failure would be an unexpected error whose report is another failed write: a loop that kept the shutdown from running until the forced exit, 12 seconds later.
- Ctrl-C shuts down cleanly: it stops every agent and every check, then prints each folder that keeps an agent's work (`engine.shutdown()`'s `kept`) with its branch. A merge or throw-away under way finishes first: its git runs in a process group of its own, so the Ctrl-C does not reach it. A second Ctrl-C, or 12 seconds, forces the exit: `killAllSync`, then every folder still on disk (`engine.keptFolders()`, untouched ones too, since the tidying was skipped) under "The agent’s folder is still on this computer:" (or "The agents’ folders are…"). Either way it exits once the words have reached the terminal or pipe, or after half a second; a third Ctrl-C exits at once.

## The Mac app (`app/mac/`)

A native window around the page, for macOS 13.5 or later (as the bundled Node) on Apple silicon. Workbench does not depend on it, and it is not part of `npm test`: it is Swift, and needs a Mac to build.

- **`build.sh`** (the repository root's `npm run app` runs it with `--install`) compiles `WorkbenchApp.swift` and `MakeIcon.swift` with `swiftc`, draws the icon, and assembles `dist/Workbench.app`:
  - `Contents/MacOS/Workbench`, the window.
  - `Contents/Resources/node/`: Node's `bin/node`, and npm (`lib/node_modules/npm`, with `bin/npm` and `bin/npx` linking into it). Without `--node <folder>`, the pinned Node release is downloaded from nodejs.org into `~/Library/Caches/workbench-build` and checked against the release's published SHA-256.
  - `Contents/Resources/workbench/`: `bin/`, `src/`, `ui/`, `package.json`, `README.md` and `ARCHITECTURE.md`, as they are in this folder.
  - `Info.plist`: bundle id `ai.coasty.workbench`; local networking allowed; the microphone and speech recognition, for talking to Workbench; folders as documents it opens.

  It signs the app ad hoc (there is no Apple Developer ID), writes `dist/Workbench-<version>-arm64.dmg` unless `--no-dmg`, and with `--install` copies the app to `/Applications` (or `~/Applications` when that is not writable). `--install` is refused, before anything is built, while that copy of the app is open ("Workbench is open. Quit it first (its agents stop), then install again."), and when `WORKBENCH_AGENT_ID` is set, even to an empty string: an agent must not replace the app the person may be running it in. `dist/` is ignored by git.
- **Running Workbench.** The app runs `Resources/node/bin/node Resources/workbench/bin/workbench.mjs --repo <folder> --app --port 4317` in the person's home folder: `--demo` instead of `--repo` for the demo, `--clone <address> --into <folder>` instead of `--repo` for a clone (see "Cloning"), and `--claude <path>` while a Claude Code program chosen in an earlier version of the app is still there (UserDefaults `claudePath`). When Workbench says the port is already in use, the app tries once more with `--port 0`; after a clone it does that as `--repo <the new folder>`, since the folder is there now. It shows the page at the address in the `WORKBENCH_APP` line. Everything Workbench prints goes to `~/Library/Logs/Workbench/workbench.log`, with the page's key replaced by `<key>`, except a clone's progress lines. The app reports Workbench's exit once its output has ended (a second after the exit at most), so the last line, such as why a clone was refused, is never lost. One folder at a time: opening another stops the first.
- **The environment** is the app's own (launchd's, when it was opened from the Finder or the Dock), with:
  - PATH extended as a terminal would have it. The folders Claude Code's installer and Homebrew use (`~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin`, `/opt/homebrew/sbin`, `/usr/local/bin`), where they exist, go first when the PATH holds only system folders, and after it otherwise. Then come the folders in `/etc/paths` and `/etc/paths.d`.
  - USER, LOGNAME and SHELL, when missing.
  - LANG, a UTF-8 locale, when no locale is set.

  Node is not added: when the PATH has none, Workbench's own rule puts the bundled node's folder first, npm included (see "Node on the PATH" in the Claude Code adapter).
- **Stopping.** The pipe to Workbench's standard input is its lifeline. Closing the board window, opening another folder, and quitting first ask, when root agents are at work. The app counts them from `/api/state`: no parent, not from an earlier run, in a working state. It says, for example, "2 agents are still working." and "Quitting Workbench stops them. What they did so far stays in their folders." Then it closes the pipe, and Workbench stops as on Ctrl-C. If Workbench has not exited 20 seconds later, it gets SIGTERM, then SIGKILL 5 seconds after that. A crashed app closes the pipe too. Before the `WORKBENCH_APP` line no agent can have started, so a Workbench that is not ready (a clone under way, say) gets SIGTERM at once, right after the pipe closes, instead of the 20 seconds' wait.
- **No agent program.** Workbench starts its board even when neither Claude Code nor Codex can run, and the page's Agents & keys helps set one up, so the app has no words of its own for it.
- **Cloning.** File → Clone Repository… (⇧⌘O), above Open Folder…, and the first window's first button open the clone sheet ("Clone a Repository"): over the board when one is open, else over the first window.
  - **The address**, as typed and trimmed. The app checks only what must stay out of Workbench's command line (which other programs on the Mac can read) and out of the log; Workbench checks everything else (`cloneRepo`):
    - a name or password in it (`https://user@…`, `…://user:password@…`, `user:password@host:path`): "Leave your name and password out of the address. If the repository is private, connect your GitHub account instead.";
    - text shaped like no address (neither `scheme://…` nor `user@host:path`, or starting with "-", or holding spaces or control characters, such as a key pasted in the wrong field): "Workbench clones addresses like https://github.com/owner/repo or git@github.com:owner/repo.git.".
  - **Your repositories on GitHub.** When the sheet opens, the app runs `workbench.mjs --github-repos` with the bundled node and Workbench's environment, for 20 seconds at most, while the list says "Loading your repositories…". It reads the `WORKBENCH_GITHUB_REPOS [...]` line (`{ fullName, cloneUrl, private }`); that output is not logged, since it names private repositories. A filter narrows the list; a click fills in the address with `cloneUrl`, and a double click clones. An empty list says "Connect your GitHub account to choose from your repositories here.", with Connect GitHub…, or, once Connect GitHub… gave a login, "GitHub lists no repositories for <login>.". A list that did not come says so ("Your repositories on GitHub could not be listed.", "… did not load within 20 seconds."), also with Connect GitHub….
  - **Put it in:** `~/Developer` at first, made when the first clone needs it. Choose… (an open panel) picks another folder, kept in UserDefaults (`cloneFolder`). A chosen folder that has gone is refused in words, and never made again.
  - **Clone.** Like opening a folder, it first stops the Workbench that is open, asking when agents work ("Cloning a repository stops them."). Then the board's own process runs `--clone <address> --into <folder> --app --port 4317`.
    - Its `WORKBENCH_CLONE {"phase","percent"}` lines drive the sheet's line and bar: "Getting ready to download owner/repo…", "Downloading owner/repo: 45%", "Unpacking owner/repo: 80%", "Writing the files of owner/repo: 100%". Each phase has its own share of the bar, so the bar never runs backwards.
    - When Workbench says anything else after the progress (or sends phase `done`), the line says "Opening owner/repo…".
    - The `WORKBENCH_APP` line ends the sheet and shows the board. Its `root` goes in Recents; without one, the app uses `<folder>/<the address's last part without .git>`.
  - **Refused.** A `WORKBENCH_CLONE {"error","sentence"}` line (`auth`, `network`, `exists`, `url`, `git`) keeps the sheet open, with the sentence (or the app's own words for that kind when there is none) and the address, ready to try again; with `auth`, also Connect GitHub…. When Workbench ended without such a line, the sheet says "Workbench could not clone owner/repo. View → Show Log says why."; when the folder was made, "Workbench cloned owner/repo, but could not open it. View → Show Log says why.", and the folder goes in Recents.
  - **Cancel** stops a clone at once, with SIGTERM. The app never deletes a folder itself. If the folder that was open closed for the clone, the first window comes back.
  - While the sheet is up, Open Folder…, Open Recent and Try the Demo are off. A folder dropped on the icon cancels the sheet first. The question about agents at work appears on the sheet itself, since a sheet under another sheet waits for it.
  - **Connect GitHub…** is a small sheet on the clone sheet: a secure field, and "Create a token on GitHub", which opens `https://github.com/settings/tokens/new?description=Workbench&scopes=repo` in the browser. Connect runs `workbench.mjs --connect-github` for 30 seconds at most, with the token and a line break on its standard input, never in argv or the environment. The field is emptied as it sends, and the app keeps no copy; Cancel waits while GitHub checks the token. `WORKBENCH_GITHUB {"ok":true,"login","sentence"}` closes it: the clone sheet says the sentence ("Connected to GitHub as <login>.") and loads the list again, and when the last clone was refused with `auth`, it clones again at once. Otherwise the sentence, or "Workbench could not connect to GitHub.", stays in the small sheet.
  - Text from Workbench, git or GitHub (repository names, sentences, the login, folder names) is shown with control, bidirectional and zero-width characters as visible symbols, as the page shows them (`visible()`).
  - The app ignores SIGPIPE, so a Workbench that ended before it read the token only makes that write fail.
- **The window** is a WKWebView.
  - Only `127.0.0.1` and `localhost` load in it; any other link opens in the browser.
  - The microphone is granted to the page alone.
  - When WebKit's process for the page ends, the page loads again.
  - While Workbench runs, the app holds a macOS activity, so App Nap does not slow it down while its window is hidden. The Mac may still sleep.

  Closing the window closes the folder. The app stays open, like other Mac apps, and its Dock icon brings back the board or the first window.
- **Without clicks**, for checks: `Workbench --repo <folder>` or `--demo` opens it at once. `--self-test` checks that the page draws:
  - A page that cannot be seen does not draw, because its animation frames do not run, and a window started from a terminal opens behind the app the person is using. So the self-test's window, titled "Workbench self-test — …", comes in front of the others without taking the keyboard. It neither uses nor saves the board window's place.
  - It reads the page every half second until the lid has words, for 15 seconds at most. It writes what the page shows to standard output and the log (`SELF-TEST {…}`, with `hidden` and `drawn`), then quits.
  - Its exit code is 0 when the page drew, and 1 when it did not, or when the page did not load within 90 seconds.
  - `--self-test-shot <file.png>` also saves WebKit's picture of the page.

**Data.**
- The page reads the key from `?t=` once, keeps it in `sessionStorage` for this tab and removes it from the address bar with `history.replaceState`. Nothing in the address makes the page send anything.
- It opens `GET /api/stream?t=…`: a `snapshot`, then `agents` (changed views, coalesced), `machines`, `notice` and `repo` events. A `repo` event replaces `S.meta.repo` and redraws, so "Merge into <branch>" follows the person's branch and a button drawn for the old branch is stale. A reconnect gets a new snapshot; chips are kept by id, so nothing replays. Only a snapshot prunes lanes.
- Every action is a JSON POST with `X-Workbench-Token` (see Answers). The git screen also reads `GET /api/git` and `GET /api/agents/:id/changes`, with the same header, and the connect panel `GET /api/connect` and the other `/api/connect*` routes.
- The snapshot's `connect` (`{ ready, defaultAgent, agents: [{ id, name, ready }] }`; `snapshot.meta.connect` is read too) is kept in `S.meta.connect` by `connectMeta()`. It is null when absent, or when `ready` is not a boolean, and then nothing of Agents & keys shows (no button, no lid state, no opening by itself), so the demo, the mock's scenarios that send none, and the Mac app's self-test (`--demo`) see the board as before. Every answer the connect panel gets carries a fresh ConnectStatus, and outside the demo `S.meta.connect` is refreshed from it (`metaFromStatus()`), so the light and the lid follow the panel at once.
- A page put in the browser's back/forward cache closes its stream (`pagehide`) and opens a new one when it comes back (`pageshow`), so streams nobody sees never hold the browser's few connections to the address.
- **Link states** (`link.js`): *no key*; *connecting* (a key, no snapshot yet: the lid is blank, then "Connecting…"); *live*; *reconnecting* (the stream dropped and the browser retries: "reconnecting…" beside the mark; after 10 s the lid says "Workbench isn’t answering."); *stale* (a 401 on any request, or on the one `/api/state` probe after the browser gives up on the stream: "This page’s key no longer works."). Without a working key the input is hidden, typing and space do nothing, and spend and machines are hidden; a stale board dims and is inert. Errors read in plain words, never "token" or "fetch". (The connect panel keeps Workbench's own sentence even when it says "token": there it is the person's word for a GitHub token.)

**Layout: a circuit board.** You are the core in the middle; each root agent is a chip on its own lane.
- **Size classes.** `layout.js` picks S (narrower than 1180 px), M, or L (at least 1380×840) for type sizes, then lays everything out in CSS pixels from the room there is, so text never shrinks with the window.
- **Lanes for life.** Twelve lanes, six a side. The first time the tab sees a root it gets a lane (`Lanes`, kept in `sessionStorage`, pruned to live ids on each snapshot) and keeps it: laptop agents prefer the left, cloud agents the right, unless that side is full or two lanes fuller; rows fill top, bottom, then the middle, mirrored. A chip only slides along its lane:
  - beside the core when it, or one of its helpers, needs the person (`needs_ok`, `question`, `maybe_stuck`, or a failed check not set aside);
  - mid-board while it works;
  - at the board's edge, powered down (flat, dull leads, no copper to the core), once done, failed or stopped.
- **Traces.** Each lane is copper with 45° bends from a pin on the core to a via by the edge. A working chip's copper runs to the core. An asking chip's line is lit into the core (dashed when it might be stuck), with a numbered pad at the core in queue order (1 filled, the rest outlined). White corner brackets mark the agent the lid is showing. A failed agent's line is cut like a fuse.
- **The core** is a package (BGA balls, or one straight row of gold leads per side that stops short of the corners; pin 1; a courtyard; the designator YOU, at the courtyard's top-left corner, or its top-right one while a numbered pad sits by the left, or a little further left while pads sit by both). Its lid holds the lid's page and the one input. It grows for long content, within limits, and its edges always fall between rows, so no lane meets a corner: rows beside it are side lanes (the outer ones jog in at 45°), rows above and below come in from its top or bottom edge, nested so no two cross.
- **The DRAM** (git) sits centred under the core, wired to it: a DRAM package (`G.dram { x, y, w, h, cx, pin, pitch, pins, bus, busTop, wire: { x, y0, y1 }, label, git }`, sizes in `SIZES[*].dram`), a long rectangle with a half-round notch at pin 1's end, a fine row of pins along both long edges on a grid centred on the core's middle, the designator U2 at its left when there is room, and **git** large on its body. A bus of 8 thin traces (6 when it is narrow) joins the core's bottom edge to its top pins. One wire leaves a pin near its right end and runs straight down to the board's bottom edge, where a lone gold finger takes it off the board: the way to the git screen. The `#dram` button lies over the package (transparent, carrying the word git), so hovering or focusing it warms the DRAM's copper and outline. Its accessible name is "Git: your branch main and your agents’ branches. Opens the git screen." ("your folder (not on a branch)" when detached, "your branch" with no repository); it is inert without a working key and dims on a stale one.
  - **Its room.** In every size class and in dense mode, the core's bottom edge never comes lower than `G.coreBottomMax`: the DRAM, its bus, its lower pins and the lines kept for `#said` (3 in S, 2 in M and L) fit between it and the edge connector, and the core's tallest size shrinks by that room. The corner lanes that leave the core's bottom edge keep out of the DRAM's column (`G.downPins { inset, step }`): their pins move closer together first, never closer than their pads allow, then the DRAM narrows to its least width, and U2 goes when it does not fit. In dense mode, rows stop where the bottom edge of the smallest core can take no more corner lanes beside the DRAM (`bottomRanks(P)`).
  - **Checks.** `boardProblems()` also checks the DRAM's box and U2 against all copper, its bus and wire (`dramSegments()`) against every box but the DRAM and the core, its bus and wire within 4 px of other copper, and `#said` against the wire.
- **Helpers** are small parts on twigs from their chip: away from the core while the agent asks, towards it otherwise. They go in order of need (asking, working, latest ended), the asking one is always drawn, and those that do not fit fold into a "+N" button that pins the agent's card. A helper's ask lights core → agent → helper, and the brackets go on its agent.
- **Machines** are sections of the gold edge connector along the bottom: an LED, a moon when asleep. Each is a button that opens the machines menu (awake switches, the laptop's CPU and memory). Hovering an agent lights its machine's section. The connector leaves a gap of `wireGap` either side of the DRAM's wire: one machine stays centred when that clears the wire, and otherwise ends just left of it; several sit either side of it, balanced first. No section ever lies across the wire. Where the room runs out, `placeBands()` tries, in order: a smaller gap, no notes, sections as narrow as their names, then the done tray's shorter words ("12 done, 6 from earlier, 1 more", made in `layout.js` with the words of `trayWords()`; its list and its accessible name keep all of them), and only as the last resort equal sections on each side of the wire, as many on its left as gives the widest, their names cut with "…". `G.tray` is `{ x, y, w, h, lead, rest }`, `lead` and `rest` being the words `board.js` draws; a machine whose name was cut has `G.machines[i].label`, which `board.js` draws, with the whole name in the section's title (its accessible name has it already).
- **Agents from an earlier run** (`earlier: true`, restored from history) never take a lane or a chip, so a long history leaves the board to what runs now. They wait in the done tray, which then shows even when the board is not dense ("5 from earlier", with their marks; "2 done or stopped, 5 from earlier" when both are there). Its list has a section "From earlier runs": dimmed rows, each with the agent's mark, its name and how long ago it ended ("Invoice export · 2 days ago"); a row puts that agent in the lid. They are never in a queue: not "needs you" (an earlier `checks_failed` asks for no one), not "ready to look at". An agent that is continued stops being `earlier` and gets a lane like any new one.
- **Past twelve roots** the board goes dense: finished work moves to a done tray (a button that lists it; a row puts that agent in the lid), each lane splits in two so agents stay beside their old place on one-line chips, and helpers show as two marks and "+N". A one-line chip grows into the room on its lane (up to 1.3 times the usual width, keeping room to slide), so a name is cut only when the lane is full, and then to the chip's whole width at a word boundary. Rows are capped by what fits the window and by the room beside the DRAM (`maxDenseRows(H, P)`, never under 12), and agents that need the person get the free rows first; any working agent beyond them is counted in the tray, whose list names it.
- **The line under the DRAM** (`#said`) shows the hint "a lit line means it needs you" (its lit line inline before the words) until the person first answers anything, and otherwise what Workbench just said. It sits under the DRAM, left of its wire and clear of the corner lanes on the left (`G.said { x, y, w, maxY, lines }`), and wraps within that width: up to 5 lines where it is narrower than 170 px, up to 3 elsewhere, always within its room. Longer text is cut at a word by the lines it wraps into, not by a count of characters (`clipToLines()`), and screen readers get all of it. What it shows, and its copy on the git screen, is what Workbench said with line breaks, tabs and runs of spaces made into one space; every character the one rule covers (see "Rules") is shown by its code (⟦U+202E⟧) or its picture (␛), as in the lid, since replies and notices can name an agent's branch or paths. U+FEFF, U+2028 and U+2029 are shown by their code too, never turned into spaces (`say()` in `app.js`; `test/ui-said.test.mjs`).
- **The top band**: the workbench mark (it opens the look menu), DEMO in the demo, the repository's name (in full where the band has room before the fiducial left of the core, else cut, with all of it in its title), "reconnecting…" when it applies, and spend today ("about $0.62 today" while the snapshot's `spendTodayEstimated` is true: part of it is Workbench's estimate of cost not reported yet).

The lid's line about git (`.meta.git`) and the card's work words (`.wk`) use colours those pairs cover. The git screen and the diff have colours of their own in each look (`--g-trunk`, `--g-trunk-hi`, `--g-trunk-lo`, `--g-lane`, `--g-sel`, `--g-hover`, `--d-add-bg`, `--d-del-bg`, `--d-add-mk`, `--d-del-mk`, `--d-hunk-bg`). The pairs check the card's text on an added line, a removed line and a hunk's place, and the card's quiet text on a hunk's place, at 4.5:1; the "+" and "−" marks on their lines, the "−" mark's colour on the card, and the gold trunk and the copper lanes on the mask (`--mask-1` to `--mask-3`), at 3:1. `test/ui-gitgraph.test.mjs` checks the same colours, and a hidden character's mark on the card (it uses the "−" mark's colour) at 4.5:1. The rest of the git screen's text uses the board's and the card's colours. `--card-focus`, set in each look's first block, is the focus ring on the card's surface: the git screen's detail (its buttons, its heading, the card's sentence and the diff), the git screen's input (`#gitBar`) and the menus (`.pop`). The board's `--focus` is light in black and gold, where the cards are ivory (about 1.1:1 on them), so there `--card-focus` is dark. **Detail levels.** `data-detail` on `<html>`: `calm` (the default) or `more`.
- Calm: chips show the name and the state mark only; helpers are unlabelled parts (their names are in the card on hover or focus); machine sections show the name and the light; the lid keeps one sentence, a short meta line, at most two answers and the input (and, for an agent's work, its row of quiet links: "Review the changes", "Not now", "Merge anyway"); the card shows what the agent is doing now, its helpers, its plan, time and cost.
- More: status words under each chip, the names and doing-words of up to two helpers where they fit, machine notes ("memory almost full", "$0.40 an hour"), the meta line in full ("Claude · Cloud 1 · waiting 4 min"), the quiet links ("Answer in your own words", "Give it a hint", "What changed?") and the full card.
- Security over calm, in both: a permission always shows the exact command or path in small type under the sentence, cut in the middle past about 160 characters ("See all of it" opens all of it in its own scroll box), control characters shown as symbols, and the policy's reason (`ask.why`).

**Customising.** The workbench mark opens a small menu: "Look: Green · Black and gold · Ivory" and "Detail: Calm · More" (two radio groups). Typing or saying "black and gold", "ivory", "green board", "more detail" or "less detail" does the same: `pageCommand()` in `prefs.js` matches whole utterances only, so "make the button green" still reaches the agents, and these words are never sent to the engine. The choice is kept in `localStorage` (`wb-theme`, `wb-detail`) and applies at once, with a cross-fade (a view transition).

**The lid** holds one thing at a time. `currentFocus()` picks it, in this order:
1. an engine card: one a typed or spoken command brought (a launch, a stop or message whose words did not name the agent, a merge, a throw-away, a forget), or one a button asked for (Forget, Merge, Throw it away);
2. the agent the person picked, stepped to, or that the engine's reply named (`focusId`);
3. the most urgent thing that needs the person (`needsQueue()`: by `PRIORITY`, then oldest first; a failed check set aside with "Look later" waits until that agent finishes again, and one whose work is settled, merged anyway or thrown away, needs no one);
4. finished work not yet looked at (`reviewQueue()`: "2 of 3 to look at"; not what was set aside, and not work that is settled);
5. when nothing needs the person and no coding agent can start work (`S.meta.connect.ready === false`, outside the demo): "Connect a coding agent to start.", with the count line "Before you start" and the needs-you mark, the meta line "Sign in to Claude Code or Codex, or give one an API key." (the agents `meta.connect` names), and a primary **Connect** (`data-act="connect"`, not guarded: it opens Agents & keys and sends nothing; a set-aside item's link stays). It is the lit lid, its key is `connect`, and it is never held. `app.js` adds it around `currentFocus()` (`focusNow()`), so `model.js` is unchanged and `focusKey({ empty: true })` is still `empty`;
6. otherwise "Nothing needs you." (with "1 set aside" and "Look at … now" when something is set aside: a failed check, or a finished agent whose merge did not go through).
- A question's count line says who asks: "Search cleanup asks · 1 of 3", in the characters the lid has room for, with the name cut at a word boundary. A live question comes with what the agent changed so far (`files`, and `rules`, recorded before it is asked; no checks), so a question from an agent that changed files has a quiet "What changed?". "next", the → and ← keys when no control has focus, and a typed or spoken "next" step through the queue without sending anything.
- **Fitting.** The lid's words are measured before the board is laid out. When they do not fit, `fitSteps()` makes room in order: a smaller headline, a shorter meta line, no meta line, long texts cut at 190 characters with "Read all of it" (all of it in its own scroll box), then tighter buttons and a closer command. A permission keeps about 160 characters of its command and the whole of its reason through all of these; only the last step, a last resort, cuts both (all of both under "See all of it"). An agent's work keeps its words at every step: "Review the changes" and the other links about its work, the paths a merge named (3 of them, 2 at the last step, each cut in the middle at 48 characters, 32 at the last step), why git cannot merge it (only its first sentence at the last step), and what a merge or throw-away card says (under "See all of it" at the last step).
- **Answers.** Two answers sit side by side while each fits on one line, with tighter padding when that is what it takes, and otherwise one above the other at the lid's full width, the first still the primary one (`buttonRow()` in `words.js`). A label never wraps to squeeze a row.
- **Counters** say "asked just now" (or "just now") under a minute and then whole minutes ("waiting 4 min"), so nothing in the lid or the card changes every second.
- **Changing what it shows** takes three steps, so no words are ever outside the lid: the old page fades out (200 ms) at the size the core was laid out for; with the lid empty, the core takes the new item's size; then the new page rises in (360 ms). A page drifts only within the room its words leave in the lid. The new item's answers ignore clicks during the swap and for a moment after (about 760 ms from the change), and typed or spoken words begun in that window, or while the old page still shows, are bound to nothing: a "yes" then gets "Have a look at what … is asking first." instead of answering something unseen. The same item, updated, is patched rather than rebuilt: focus, an opened detail and a button whose answer is on its way all survive. What counts as the same item is the lid's key (`focusKey()`, which `app.js` uses too): the card shown, nothing, or an agent with its state, its ask and its work's signature (`workKey()`: merged, a problem, thrown away, its folder gone, unmerged work), so an outcome of a merge or throw-away swaps the page and arms the guard.
- **Holding.** While the pointer or keyboard focus is in the core, the input has text, voice is listening or a reply is open, the lid keeps what it shows (as long as that is unchanged) against what arrives on the stream, and adds "Another one needs you" (also for a launch question waiting behind it) instead of swapping. It swaps when the person leaves the core, or after 20 s without input. While the git screen shows, the lid holds too. The person's own moves are never held: a lid button ("next", "Look later", "Looks good", "Back", …), → and ←, a typed "next", picking a chip or a done-tray row, and the reply to their own command (a new card, or a `focusId`) show at once; an agent the reply names before the stream has brought it (the first agent of a launch just confirmed) comes to the core as soon as it arrives. Words typed or spoken before such a move are not bound to the item that comes in. A failed or refused answer is not a move: the core keeps what the person answered (still held) and its button can be tried again, with the keyboard back on it.

**An earlier agent in the lid** (picked from the tray; `lidView` case `earlier`): the count line says "From an earlier run"; the sentence says how it ended in plain words ("Invoice export was done and checked.", "… said it was done.", "… was done, but a check failed.", "… stopped with an error.", "… was stopped."); the meta lines say how long ago and what it said, then either "It would get a new spending limit of $2.00 for this run." (the budget is the snapshot's `defaultBudgetUsd`) or, when `canContinue` is false, its `continueReason` ("Its folder is gone, so it cannot continue."). The buttons are **Continue** (only when `canContinue`; primary) and **Forget**; "Back to what needs me" (or "Close") comes with any picked agent. An earlier root always keeps this lid, whatever became of its work, with a quiet **Review the changes** when its folder may hold unmerged work; merging it and throwing it away are in the git screen's detail.

**An agent's work in the lid.** The rules live in `queue.js` (*pure*) and are bound to `S.meta` in `model.js`, so the lid, the card, the queues and the git screen read an agent's work the same way (should `model.js` lack them, the git screen's detail falls back on `workActions()` in `gitgraph.js`, which follows `mergeApplies` and `discardApplies` below):

- `unmergedWork(a)`: its work is there (not thrown away, its folder there) and holds something not merged: `files.changed > 0`, or `files` unknown for a stopped, failed or earlier agent.
- `workSettled(a)`: thrown away, or merged with nothing unmerged since. A settled root needs no one (a `checks_failed` one is out of `needsQueue()`) and is out of `reviewQueue()`.
- `canReview(a)`: a root with its branch and its folder, not thrown away. **Review the changes** shows when `canReview` and (unmerged work, or `files` unknown).
- `mergeApplies(a)`: live mode (`S.meta.mode === 'live'`), a root that is not active, `canReview`, the person on a branch (`S.meta.repo.branch`), `repo.identity !== false` (unknown counts as known: the engine checks again), and unmerged work.
- `discardApplies(a)`: live mode, a root whose work was not thrown away, with its branch or its folder still there.
- `gitReason(a)`: when merge would apply but for git, the engine's own words: "Your folder is not on a branch, so there is nowhere to merge it." or "Git does not know your name and email yet, so Workbench cannot make the merge commit. Set user.name and user.email with git config, then try again."; else null.
- `workKey(a)`: the work's signature: `t` thrown away, `m<merge id>` merged, `p<why><at>` a problem, `g` its folder gone, `u` unmerged work. It is part of the lid's key, and buttons about the work carry it as `data-work`. How many files changed is not part of it: the engine's card says that.

What the lid shows for a root that is not earlier and not active: where its work went comes first (thrown away, then a merge that did not go through, then merged with nothing new), then its state:

- **`done_checked` and `done_claimed` when merge applies:** big **Merge into main** (primary; a branch past 16 characters is cut in the middle, with the whole label in `title`) and **Ask for a change**; under them, in one row of quiet links: **Review the changes** and **Not now** ("Not now" lets the finish go as "Looks good" does, in its own words: it answers "Not now", which leaves the agent as it is and sends it nothing, with the reply "OK. Search cleanup’s work stays on its branch for now.", and marks the finish looked at).
- **When merge does not apply** (the demo, no git, nothing to merge): **Looks good** and **Ask for a change**; when the reason is about git, `gitReason` is a line under the sentence (`<p class="meta git">`; its first sentence only at the last fit step); **Review the changes** when it can be reviewed, else "What changed?" in "more".
- **`checks_failed`:** **Ask it to fix that** and **Look later**, plus quiet **Review the changes** and **Merge anyway** when merge applies (the same card, whose detail names the failed check), else **Review the changes** when it can be reviewed.
- **`failed` and `stopped`:** their own buttons, plus quiet **Review the changes** when it can be reviewed.
- **Merged, nothing new** (count line "merged"): "Search cleanup’s work is in main."; meta "Merged 2 min ago · 3 files" ("Merged just now" under a minute); big **See it in git** (primary) and **Ask for a change**. It shows when the person picks it: it is out of the review queue.
- **A merge that did not go through** (count line "not merged" when picked), until `work.problem` clears:
  - `conflict`: "Search cleanup’s work does not merge cleanly into main.", where the branch is `problem.into`, else the person's branch now, else `work.from`, so the headline and the button always agree; meta "Both changed: src/search/index.ts, src/search/redirects.ts" (3 paths, then "and N more"); big **Ask it to bring in main**, which sends "Your work conflicts with the latest main in: src/search/index.ts, src/search/redirects.ts.   - `blocked`: "Your own changes are in the way."; meta "In the way: src/cart/total.ts" and "Commit or put them aside, then merge Price rounding again."; big **Try again** (it asks for the merge again) and **Not now**.
  - any other: the engine's first sentence as the headline and the rest as a meta line ("main changed since you looked." / "Have another look."), with **Try again** and **Not now**. Screen readers get the whole sentence.
  - **Not now** and **Look later** here set the item aside for this finish ("1 set aside").
- **Thrown away** (count line "thrown away"): "Search cleanup’s work was thrown away."; meta "Workbench keeps a hidden copy in git."; big **Dismiss**.

"Back to what needs me" (or "Close") comes with a picked agent, except when the lid already has its own way to let the item go ("Not now", "Look later", "Dismiss") and nothing else waits.

**Engine cards in the lid.** A card is `{ id, sentence, detail, kind, yes?, no?, danger?, agentId? }` (in `S.confirm`): a merge or throw-away card names its agent itself, and the page sets `agentId` on a card a button for that agent asked for, and keeps it on the card shown when a reply brings that card back. Going back reverses it. With `still=1`, reduced motion or a hidden tab, the screens swap at once (with reduced motion, without a transition on anything in them: see "Motion").
- **Going back:** "↑ Back to the board" (top left); Esc when no detail is open (a detail the screen was opened on goes straight back); a click on the wire's top end (`#gitWireEnd`, for the mouse only); or the words "board", "back", "go back", "the board", "back to the board" and the like, which the page acts on only while the git screen shows. The lit "<Name> needs you" button goes back too, with that item in the lid, as picking its chip does (`ctx.pick`: a card on screen is withdrawn first). Esc in the git screen's input, while it holds typed words, empties it first. While voice listens, Esc is not the git screen's: it throws away what was heard ("Stopped listening."), and the screen, its detail and its card stay (`gitEscape()` answers false while `ctx.listening()`).
- **Focus:** on the way down, the git screen's heading (`#gitTitle`), or the detail's heading when it was opened on an agent; on the way up, what opened it (the lid's link), else `#dram`; after "<Name> needs you", the lid's sentence. Each of these goes through `focusOn()`: when a screen that has only just become visible refuses focus, it is tried once more on the next frame, if focus is still on nothing.
- **While it shows:** the lid holds (`engaged()` is true); ← and → do not step the queue; letters typed go to the git screen's own input (`#gitSay`); what voice hears goes to the words of the screen the microphone turned on over (see "Words typed or spoken there"). The address never changes, and nothing in the address opens the git screen.

**The git screen** (`#gitScreen`, `gitscreen.js`) is another board, in the same three looks and the same JetBrains Mono: your branch as a thick gold trunk, each agent's branch a copper trace, newest commits at the top, where the wire from the DRAM arrives at HEAD.
- **Top band,** its two halves either side of the channel the wire comes down. On the left: "↑ Back to the board", DEMO in the demo, the git mark and `<repo> · <branch> · <short HEAD>` ("not on a branch" when detached; cut in the middle to fit, all of it in the title and for screen readers), and the person's folder, "2 uncommitted changes in your folder" or "Your folder is not on a branch", with "Git does not know your name and email yet, so Workbench cannot merge." when `repo.identity` is false. On the right: a lit "<Name> needs you" when anything needs the person (the first of `needsQueue()`; its name for screen readers adds ", and N more"; what comes while the screen shows is also said, in `#gitAnnounce`), the input, and what Workbench said (`#gitSaid`: at most two lines, cut at a word, all of it for screen readers). While voice listens, the input and its hint give way to a wave and the words heard so far (`#gitHeard`, all of them sent), as on the board's input (`gitListening()` sets the `listening` class on `#gitBar`); the wave is in `--c-fail`, which shows on the card's colours, and moves only without reduced motion and `still=1`. The wire comes in at the board wire's x (`G.dram.wire.x`), runs level just under the band with 45° bends, and goes down into the trunk at HEAD.
- **The graph** (`graphLayout({ commits, agents, branch, head, width, height, ACTIVE }, P)`, *pure*) returns `{ rows, lanes, nodes, edges, folds, trunkX, rowH, pitch, w, h, headRow, perSide, agentById }` in CSS pixels (`GRAPH_SIZES` S, M, L). `NEWEST_AT_TOP = true` is one constant: flipping it mirrors the drawing top to bottom.
  - Rows: one per commit, newest at the top, in the order git gave. Each agent with unmerged work gets one more row above its branch's tip (else above its `since` or `base`): its work node, a hollow, dashed via with its state mark, labelled "working" while it is active, else "not merged yet · 3 files" ("not merged yet" when no count is known). Merged with nothing new, its folder gone, or thrown away: no work node. When none of those commits is among the ones shown (its branch starts past the limit), its work node goes at the end, just above "Older commits are not shown here.", newest first by `startedAt` (else in the order given), with its stub pointing down, so it is never drawn above HEAD as if it were the newest; your trunk's stub runs on past them, and the row's name adds "Its branch starts in older commits, not shown here."
  - Lanes: the trunk is your branch's first-parent chain from HEAD, a thick gold bus. Every other line of work (a branch's run of commits, or a work node and its commits) is a copper trace on a lane of its own, placed outward and alternating right and left, shortest nearest the trunk so nested ones never cross: the tree branches downwards and spreads out. A line that leaves from or joins another line of work is placed after that line (cycles are broken), so it knows that line's side and keeps to it rather than cross your trunk. Of the free lanes, a line takes the one where it crosses the fewest lines; a level run over your trunk, from the top down to its last commit, counts as two. The lane pitch is 56 to 112 px, from the width. With no lane left of the trunk, the trunk keeps room for HEAD's silkscreen on its left (`HEAD_SILK`, 37 px: the label's 30 px in Chrome at 10.5 px, 5 px off the pad, and a little more), and the graph still keeps to its width. A trace changes lanes only with 45° bends (`bendsOk()` checks it). Past what the width allows, extra lines of work fold into the outermost lane of a side, with a "+N" marker.
  - Merges' lines: a merge's second parent on another lane is reached down the gutter beside the target's lane (`crossRoute`): at the gutter's middle, or at a place 6 px apart (3 px when those are all taken) where no other such line already runs at that height. Of the places that are free, it takes the one that crosses the fewest of those lines, then the one nearest the middle; its bends shrink to the room and stay at 45°. Between two commits on one lane with others in between, the line steps out into the gutter on the trunk's side of that lane and back, instead of running over the lane's own segments. So no two traces share a stretch, except lines meeting side by side at one commit and lines folded into one lane on purpose. Edges carry the ids of the nodes they join (`from`, `to`) and `folded`, and `sharedRuns(g, min = 13)` lists any shared stretch longer than `min` px, for checks. Known limit: lane choice weighs the lines that leave and join, not merges' lines, so in a criss-cross history (two agents merging each other's work, one on each side) a merge's line can still run level across your trunk.
  - Nodes: your commits are gold vias; an agent's commits off the trunk (commits with `agentId`) are small chips with the agent's mark; merge commits are square pads; HEAD is a pad with HEAD in silkscreen. HEAD's label goes where no trace runs (`headLabelPlace(g, W)` in `gitscreen.js`, on the laid-out graph): above the pad on its left, else above on its right, else below on the left, else below on the right: the first place that fits (within the graph's height, and short of the rows' text on the right) and that no edge or other node crosses. Left of the trunk, the drawing moves right by `dx` (on the SVG's group `.gshift`, its width, the rows' text, the selection ring and the wire), so the graph's edge never cuts it; when every place is crossed, the first that fits gets a halo of the board's colour (`.ghead.halo`).
  - Text, in a column right of the graph, as VS Code shows it: the subject, then "who · when · short id" muted (who is the agent's name for a commit with `agentId`), each cut at a word boundary with the full text in `title`. Branch badges come first: your branch in gold, an agent's branch in copper under the agent's name (a click opens that agent's detail), any other branch plain; badges that do not fit are counted ("+2").
  - The list (`#gitGraph`, `role="listbox"`, its own scroll box with `data-scroll`) is one tab stop, always exactly one: the selected row, or the first when no drawn row is selected (a row that is not drawn is never selected). Its rows are options. ↑ ↓ PageUp PageDown Home End move; Enter or Space opens the detail; with the detail open, it follows the selection. A badge selects the row it is on; a link to an agent in a commit's detail selects that agent's work row, else its branch's tip, else the merge that brought its work in (`rowOfAgent()`), and leaves the selection where it was when none of them is drawn. With no rows, the list's name says why ("Reading the history…", the error, "This repository has no commits yet."); past the limit, "Older commits are not shown here.".
- **The detail** (`#gitDetail`), a panel over the text column (the graph stays in sight; the rows' words under it are hidden), opened by a row or a badge:
  - An agent: its mark, its name and its state words ("from an earlier run · …"); "On its branch workbench/search-cleanup-a1b2c3, from main at 1a2b3c4"; "Merged into main 2 min ago · 3 files" once merged; in "more", who did the work ("Claude · <model> · Your laptop"); its counts, "3 files, +40 −2 · 1 file left out" (from the diff once it is here, else from its `files`; "Nothing changed since it started."); `problem.sentence` and up to 6 of its paths; then the actions or the engine's card; "It is still working, so its work may still change." while `live`; and the diff, in one scroll box.
  - The actions: **Merge into main** (primary, the whole branch in `title`) and **Throw it away**, each shown only when it applies (`mergeApplies`, `discardApplies`), carrying `data-act`, `data-agent`, `data-state`, `data-work` and (Merge) `data-into`, and handed to the lid's own handler (`actOn` in `app.js`), which checks them against what is current before it sends anything, and first withdraws a card already on screen (see "Withdrawing a card"). When git is why there is no Merge, `gitReason` says so. Without `model.js`'s rules, `workActions()` in `gitgraph.js` decides, by the same rules as `queue.js`: Merge needs its branch and its folder besides the rest of `mergeApplies`, and Throw it away its branch or its folder.
  - The engine's card shows in place of the actions when `S.confirm` is a merge or throw-away card for this agent (its `agentId`), with its own yes and no (`data-act="confirm"`, `data-confirm`, `data-go`); a danger card has no primary button. Its sentence, detail, yes and no go through `visibleControls`, as in the lid. Its sentence (`#gitCard`, `tabindex="-1"`, `data-key="card:<id>"`) is where the keyboard goes when the card comes.
  - **The guard,** as the lid's. The action block has a key: the agent, its state, its work's signature, and the card's id or the buttons shown. Whenever that key changes (an agent's detail opens, or another agent's takes its place; a card comes in place of the actions, or goes; the buttons change; the agent moves on), the detail's buttons ignore clicks for 760 ms, or 500 ms with `still=1`, reduced motion or a hidden tab, and are dimmed meanwhile (`#gitDetail.arming`); words begun before the change are bound to nothing; a card that comes is said in `#gitAnnounce`. Opening any detail, and the selection moving with it open, also arm the guard for 500 ms (600 ms when the screen opens on an agent), and the later end counts: an agent's detail that opens waits 760 ms with motion, 500 or 600 ms without. Only buttons with `data-act` (Merge, Throw it away and the card's answers) are guarded.
  - A commit: its subject; "A merge commit" or "An agent’s work, as a commit" when it is one; By, When ("2 hours ago (12 Nov 2026, 14:03)"), Id, Parent or Parents (links to the commits shown), Branch or Branches ("main (yours)", or "Search cleanup’s branch", a link to its detail), and "Made by Search cleanup" for a commit with `agentId`.
  - Esc closes the detail, with focus back on the selected row (else the list's tab stop, else the screen's heading); the next Esc goes back to the board. The detail has no Esc handler of its own: Esc is the page's (`escape()` in `app.js`), so while voice listens it throws away what was heard, and only otherwise reaches `gitEscape()`.
- **Words typed or spoken there** are bound when they begin, as the core's are: at the first keystroke in `#gitSay`, or when the microphone turns on over the git screen (`gitHold()`). The binding (`bindingNow()` in `gitscreen.js`) is `{ confirmId }` for the card in the detail, `{ agentId }` for an open agent detail, otherwise nothing (`{}`); it is nothing while the screen moves or the detail's guard is armed, becomes nothing when the action block or the detail's agent changes and when the screen closes, and goes when the input is emptied (typing, or Esc). `gitCommand(text, binding)` in `app.js` checks the page's own words first: the git words, the looks and the detail levels; "next" is not sent ("“Next” steps through what needs you, on the board. Say “back” to go there."). The rest goes to `POST /api/command` as `submit()` sends it: `confirmId` the bound card, `focusId` the bound agent, `askId` null. A card the reply brings shows in the detail when it is the card shown, or a merge or throw-away card whose own `agentId` is the bound agent; any other card takes the person back to the lid, where it can be answered. When a reply brings a new card while another card, one the words were not sent to, is on screen, that one is withdrawn (`go: false`), so none waits unseen. A reply's `review` opens that agent's detail. Voice is bound to the screen the microphone turned on over (`voiceOver` in `app.js`): a session begun on the git screen never takes the core's binding, and its words go to `gitCommand` with the binding taken then (`gitTake()`: nothing, if the action block changed or the screen closed meanwhile); one begun on the board goes to `submit()`. A session that ends with nothing heard, or is thrown away, leaves no binding behind (`gitRelease()`; on the board, when the input is empty).
- **Data:** `GET /api/git` when the screen opens; again when the repository (branch, head, uncommitted changes, identity) or any root's state or work signature changes while it shows; and once more when they changed during a read. An older answer is dropped. `GET /api/agents/:id/changes` when an agent's detail opens, and again when that agent's state or work, or your HEAD, changes. Every answer is cleaned field by field: what does not fit is dropped, never guessed. The diff's HTML is made once per answer. What Workbench says there (its notes, the list's name, refusals and errors from the engine, and `#gitSaid`) shows hidden characters by the one rule. The times move on with the clock, a word at a time: `app.js`'s 1 s tick calls `gitTick()`, which changes a row's "who · when · id", its title and its name only when its time words change, and draws the detail again only when its own time words change. Nothing repaints at rest.

**The diff** (`diffHtml(diff, { maxLines = 4000 })` in `diffview.js`, *pure*):
- one section per file, its header the path and then "+40 −2", "new file, +12", "deleted, −30", "binary file", "too large to show here", "new link", "deleted link", "link changed", "the file became a link" or "the link became a file, +3"; git's own header lines are never shown;
- lines with visible "+" and "−" marks in a gutter (hidden from screen readers, which hear "added: " and "removed: "), on add and delete colours that never carry the meaning alone; "line 12" before each hunk, with git's context words (`patchLines()` reads the hunk's header with the `s` flag, so a line or paragraph separator or a lone carriage return in git's function line keeps the line number, and shows as a symbol; a carriage return at its end is dropped); "no line break at the end of the file"; a link's lines read "→ <target>";
- long lines wrap (`white-space: pre-wrap; overflow-wrap: anywhere`), so nothing scrolls sideways;
- a file with no lines says why: "Only this changed: it can now run as a program.", "Only this changed: it can no longer run as a program.", "An empty file.", "It was empty." or "No lines changed."; a cut file ends "The rest of this file is too long to show here.";
- past `maxLines` every file still gets its header, and the rest is counted: "and 1,240 more lines"; then "and 3 more files, not shown here" (`omitted`) and "Some of the changes are too large to show here." (`cut`);
- files left out: "2 files not merged", each with "Not merged: hidden by a .gitignore it changed" or "Not merged: it is a separate repository inside its folder"; nothing at all: "No changes.";
- everything goes through `esc()`, and every character of the one rule (read with `hiddenParts()` from `words.js`: see "Rules") is a marked symbol with a title naming it ("Hidden here: a right-to-left override.", "… a soft hyphen.", "… a Hangul filler.", "… a tag character (U+E0041), which can hide text.", "… a variation selector (U+FE0F).", else "… a control character (U+0085)." or "… an invisible character (U+…)."): C0 controls as their pictures (␀ … ␟, ␍ for a carriage return, ⏎ for a line break, a tab as ⇥ that keeps its indentation), DEL as ␡, and every other one by its code (⟦U+202E⟧, ⟦U+E0041⟧), exactly as `visibleControls` shows them everywhere else. `hasHidden(s)` is true for any character shown as a symbol, the tab included.

  - **Add a key** shows the presets of `/shared/keypresets.mjs` as pressed buttons, then that preset's fields: a password field for a secret one, a plain one otherwise, "(optional)", the variable's name and its `also` names. Then "Name it", "For: this repository / all repositories" ("this repository" only in live mode with a repository), "Given to: all agents / <each agent>" (who the preset suits, first), the preset's note, what an agent's own sign-in reads (`signInVariables`, whatever its shape), its link (https only), Save and Cancel. "Other" takes the person's own names and values, a row at a time, up to 20. The page sends a field's value under its `also` names too. A refused name is never repeated, only its row: "The variable name in row 2 can use only letters, digits and _, and must start with a letter or _.". A name that looks like a key (one pasted into the wrong field) is refused first ("The variable name in row 2 looks like a key itself. Put the key in its value, and give it a name such as SENTRY_DSN."), and it is dropped (`keptNames()`) before the form keeps its names, and its field emptied, so it is never kept, drawn again or said.
- **Values:** password fields have `autocomplete="off"`, no `name`, and never a `value` in the markup, and there is no `<form>` (Enter sends a part's first button). A value is read when it is sent and its field emptied at once. It is never kept in `S` or in the panel's state, never said, never logged, never in an address. Every password field is emptied when the panel closes. The choices made in a form (git's name and email as typed, the GitHub box, a new key's name, place and agents, the person's own variable names, except one that looks like a key) stay while its save is on its way or was refused; its values do not. Each row and form is one keyed element (`data-k`) patched in place, so a re-check never empties a field someone is typing in; a button whose request is on its way carries `aria-disabled`, which keeps the keyboard.
- **Words:** everything outside Workbench's own words (agents' names, versions, where they were found, Workbench's sentences, labels, variable names, logins, commands) goes through `visibleControls` and `esc`. A secret shows only as "•••• " and its last 4 characters (values of 12 or more) or as "••••": a value shows as it is only when the store sent it masked, or when its preset field is not secret and it does not look like a key.

**Typing and voice.**
- Letters typed anywhere except a text field go to the input (on the git screen, to its own input), also after clicking a chip or a button: a mouse click never moves the keyboard focus.
- Space types in a text field and presses a control reached with the keyboard; anywhere else, holding it talks and letting go sends what was heard. While it listens, the words heard so far show in place of the input, the board's (`#heard`) or the git screen's (`#gitHeard`). Esc while listening ("Stopped listening."), on either screen, or the window losing focus, throws it away; on the git screen, the screen, its detail and its card stay.
- Text goes to `POST /api/command` with what the screen showed when the person began (the lid: see Answers; the git screen: see "Words typed or spoken there"), except the page's own words (the looks, the detail levels, "next", and the words that open the git screen). Anything that starts agents comes back as a confirm, shown in the lid, and so does a stop or message whose words did not name the agent, and every merge and throw-away (on the git screen, a merge or throw-away card for the agent whose detail the words were bound to shows in that detail).
- **Keys never go through the input.** Text that looks like a key (`looksLikeSecret` from `/shared/secretshape.mjs`, read as a whole) is never sent from the board's input or the git screen's: `submit()` and `gitCommand()` check it before anything else (replies, the page's own words, the binding), empty the board's input, say "That looks like a key, so it was not sent. Keys go in Agents & keys, where they are kept safe." and open Agents & keys with the same words. The text is not kept or logged. The engine checks again.
- "Tell it something", "Ask for a change", "Answer in your own words" and "Give it a hint" turn the input into a reply to one agent ("to Search cleanup:"). The reply keeps the agent, its ask and the state it was opened in: an answer goes only to that ask, and a message only while the agent is still in that state; otherwise the page says "That changed. Have another look." and keeps the words in the input.

**Answers: what the page sends.** Every answer names what the person saw, by id. The engine refuses anything else and the request keeps waiting, so a click or a "yes" can never land on something that took the old one's place.
- **Buttons** send the ids they were drawn for (keep them on the button: `data-agent`, `data-ask`, `data-confirm`, `data-state`, and for an agent's work `data-work` and `data-into`), never what the centre holds at click time; it may have changed during the fade. One handler (`actOn` in `app.js`) acts for the lid's buttons and the git screen's: it says "That changed. Have another look." and sends nothing when the agent, its ask, its state, its work's signature or the person's branch differs from what the button was drawn for.

  |---|---|
  | Permission "Allow" / "Deny" | `POST /api/agents/<asker>/answer { askId, answer: 'Allow' \| 'Deny' }`: the asker's own id (a helper's, when a helper asks). No other words are accepted |
  | A question's option | `POST /api/agents/<agent>/answer { askId, answer: <the option's exact words> }` |
  | Stuck "Stop it" / "Let it keep trying" | `POST /api/agents/<agent>/answer { askId, answer: 'Stop it' \| 'Let it keep trying' }` |
  | Background work "It is done" / "Keep waiting" (a stuck ask with `about: 'background'`: "<Name> has finished, but a command it started is still running.", `detail` says what the command does; it is not "might be stuck") | `POST /api/agents/<agent>/answer { askId, answer: 'It is done' \| 'Keep waiting' }` |
  | Finished work "Looks good" | `POST /api/agents/<agent>/answer { answer: 'Looks good' }`, no `askId` (a finished agent has no ask; if it has one by then, this is refused) |
  | A typed follow-up on finished work | `POST /api/agents/<agent>/answer { answer: <text> }`, no `askId`, or `POST /api/agents/<agent>/say { text }` |
  | "Ask it to fix that" (a check failed), "Try again" (failed), "Continue" (stopped) | `POST /api/agents/<agent>/say { text: <the button's message> }` |
  | "Continue" (an earlier agent) | `POST /api/agents/<agent>/say { text: 'Please continue where you left off.' }`: the engine resumes it in its folder and replies with the new spending limit; a refusal is `{ ok: false, reply }` ("… cannot continue. Its folder is gone, so it cannot continue.") |
  | "Forget" (an earlier agent) | `POST /api/command { text: 'forget it', focusId: <agent> }`: the reply carries a `confirm` ("Forget Invoice export?"), shown like a launch question; "Do it" / "Cancel" are the ordinary confirm buttons. The agent leaves the page with the fresh `snapshot` the stream sends |
  | Confirm card "Do it" / "Cancel", or its own `yes` / `no` ("Merge" / "Cancel", "Throw it away" / "Keep it") | `POST /api/confirm/<confirmId> { go: true \| false }`. After a yes to a merge or throw-away card, the page follows the reply's `focusId` (else the card's agent), so the outcome shows on that agent |
  | "Merge into main", "Merge anyway" (a check failed), "Try again" (a merge that did not go through) | `POST /api/agents/<agent>/merge { state }`, with the state it was drawn in: the reply is a merge card (`{ reply, confirm }`), shown in the lid (or in the git screen's detail), or a refusal (`{ ok: false, reply }`) that changes nothing, and the button can be tried again. A card already on screen is withdrawn first (`POST /api/confirm/<id> { go: false }`); if that fails, the card stays, nothing is asked, and the button can be tried again |

  `/say` and `/stop` carry no ask id, so the engine cannot tell what the person saw: the page sends them only for the agent the button was drawn for (`data-agent`), and only while that agent is still in the state it was drawn in (keep it on the button too). If it has changed, the page says so ("That changed. Have another look.") and redraws instead of sending.
- **The reply box** keeps the agent and the ask it was opened on. "Answer in your own words" on a question or a stuck ask sends `POST /api/agents/<agent>/answer { askId, answer: <text> }` (on a stuck ask, the text is a hint). "Tell it something" sends `POST /api/agents/<agent>/say { text }`, a message: it answers a question, but never settles a permission or a stuck ask. The reply box never posts text to a permission: words for a permission go through `/api/command`.
- **Typed or spoken text** sends `POST /api/command { text, focusId, confirmId, askId }`, all taken together at the first keystroke, or when the microphone turns on, not at Enter:
  - a confirm card on screen: `confirmId` is its id; `focusId` and `askId` are null (the engine ignores an `askId` that comes with a `confirmId`);
  - an ask on screen: `focusId` is the asker (the helper, when a helper asks) and `askId` is that ask's id;
  - an agent on screen with no ask: `focusId` is that agent; `askId` is null;
  - nothing on screen: all null.

  A typed or spoken "yes" allows only the permission whose `askId` came with it. Without it, the reply is "Have a look at what Checkout fix is asking first."; with an ask that has changed since, "Checkout fix is asking something else now. Have a look, then answer again." Both carry `focusId`, the asker. "yes but only in the tests folder" is a no, and the agent gets the words. A yes asked rather than said ("is it okay?", "do you allow it", spoken without a "?") answers nothing: the reply says exactly what it wants to run ("… It needs your OK."), with `focusId`, and the request keeps waiting. With a card on screen, "is that right?" keeps the card, as words not understood do. "stop it" with a helper's request on screen stops the helper (see the "Stop it" row above).
- **The reply to `/api/command`:**
  - `confirm` with a new id: show that card. It replaces any card shown, which the engine has already withdrawn.
  - `confirm` with the id of the card shown: the words were not understood (or were a look at the work it is about). Keep the card, still bound to the agent it was drawn for, and show `reply` with it; it is not sent as a notice.
  - no `confirm`: drop the card shown, if any, and do not post anything for it. The engine has already settled or withdrawn it, and a cancel would put "OK, I won’t start it." over the reply. Show `reply`.
  - `focusId`: put that agent in the centre: the asker after a refused answer, the stopped or told agent, or the first new agent after a typed "yes" to a launch.
  - `review` (an agent id): open the git screen on that agent's branch and diff, also when the reply carries the card shown ("show me the changes" before saying yes to a merge): the person looks at the work first, then answers the card.
  - A refused answer is an ordinary `reply` (status 200, no `ok` field).
- **Refusals from `/answer`** are `{ ok: false, reply }` with status 200 (`ui/api.js` throws them, marked `refused`). Show the reply and redraw from the current state; the request keeps waiting. So are refusals from `/merge` and `/discard`, and from the git screen's reads (whose reply the screen shows in place of the graph or the diff).
- **Withdrawing a card.** When the page drops a card for a reason that is not a command reply or one of the card's own buttons (the person picks an agent or presses "<Name> needs you" on the git screen, presses Esc, or presses Merge or Throw it away, in the lid or in the git screen's detail, while a card is on screen), it posts `POST /api/confirm/<id> { go: false }`, so no card waits unseen. If that post fails, keep the card (Merge and Throw it away then ask for nothing). Words typed or spoken on the git screen withdraw a card on screen that they were not sent to when their reply brings a new one. A reload or a second tab forgets the card without telling anyone; the engine's copy can then be answered only by its id and runs out after 10 minutes. A card the page still shows after that answers "That request is no longer waiting. Ask again if you still want it."

**Motion** (`board.js`). Things move only when something changes; with `still=1` nothing moves at all.
- A chip slides along its own lane (900 ms) and its copper follows. A line that lights charges from the chip into the core (600 ms), after the slide, and its pad pops in; a line that goes out drains back (500 ms); pads renumber; the brackets move to what the lid shows; a finished chip powers down after its slide. A slide that is interrupted starts again from where the chip is.
- One pulse runs along the copper towards the core per real step (a rise in `toolCalls`), at most one per agent every 1.1 s.
- Hover lifts the chip 2 px, warms its copper, lights its machine, fades the card in (220 ms) and draws its leader (260 ms).
- A new ask's line breathes three times and then rests: while something waits, nothing repaints (counters change at most once a minute).
- The lid's swap: the old page fades (200 ms), the core resizes while the lid is empty, the new page rises (360 ms); see "Changing what it shows".
- The way to the git screen and back: a pulse down the DRAM's wire, both screens sliding, a pulse down the git screen's wire to HEAD (see "Two screens"). Hovering or focusing the DRAM warms its copper.
- `prefers-reduced-motion`, watched live, turns travel off: chips and lines jump, and there are no pulses or breaths. The two screens swap at once, and they and everything in them have no transitions (`.screen, .screen *`), so nothing on the screen that comes in is still on its way from hidden when it takes the keyboard. The git screen's listening wave stands still.
- The first snapshot, a resize and a hidden tab draw without motion; a hidden tab queues at most one render and no step pulses.

Its words are announced through a separate live region; the lid itself is not live. Allow and Deny have equal weight.

What already needs the person when the screen opens is not said again, nor what changes in it while the screen moves.

**Rules.**
- The UI never shows a percentage of completion or an estimated finish time.
- Everything an agent controls is escaped (`esc` in `util.js`) before it reaches the page, and every character that hides text or changes the order it reads in is shown, never raw, by one rule: `visibleControls` in `words.js`, with `hiddenParts()` (a text in pieces, each hidden character on its own with how it is shown) and `hiddenPicture()`. `diffview.js` reads text with them, and its `visibleText` is `visibleControls`.
  - What the rule covers: the C0 and C1 control characters (`\p{Cc}`), every default-ignorable code point (zero-width spaces and joiners, direction marks, the byte-order mark, soft hyphens, Hangul fillers, invisible operators, tag characters, which can spell out words no one sees), the bidirectional controls, and U+2028 and U+2029. The regular expressions use Unicode's properties and the `u` flag, so characters past U+FFFF count, and no such character is in `words.js` raw.
  - How each shows: a control character as its picture (⏎ ⇥ ␍ ␡, and ␀ to ␟), every other one by its code, with at least four hex digits (⟦U+202E⟧, ⟦U+E0041⟧). A variation selector stays raw only as one U+FE0E or U+FE0F straight after an emoji; any other, and every one after the first, is shown, since a run of them can carry hidden text. The zero-width joiner is shown too, so an emoji sequence joined by it shows ⟦U+200D⟧, and a flag made of tag characters shows its tags.
  - Where the page applies it: the lid (names, paths, branches, what an agent says, does and asks, the words of its answers, its checks' and helpers' names; prose has its ordinary spacing evened out first, so a line break in a question reads as a space while a command keeps its ⏎, and a cut never goes through a code); the card, on hover and pinned; the chips, their status words and their helpers' names and words, and the names screen readers hear for them (`layout.js` lays them out as shown, and wraps and cuts them between codes, as `whoAsks` does); the done tray's list; the reply chip, its title and the input's name; what Workbench says under the DRAM and on the git screen; and the git screen itself (rows, badges, the detail, the engine's card, its notes, refusals and errors). A button still sends the agent's own words (`data-answer`, `data-text`).
  - Known gap: a helper's card names its agent ("helper of Checkout fix", its sub line in `card.js`) with `esc()` only, so the fit check's `taint` view fails on the pinned helper's card.
- When the tab is hidden and something starts needing the person, the tab title becomes "• Workbench".
